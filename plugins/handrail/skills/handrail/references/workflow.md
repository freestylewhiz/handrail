# Workflow

Use the stable absolute launcher and --repo order in [execution.md](execution.md). Preserve the user's implementation scope and verification instructions.

1. Consult active parent-board Instructions and relevant Summary Agent Context. Use [cards-and-instructions.md](cards-and-instructions.md) for bilingual presentation. Create the Plan with title, stable criterion IDs, presentation and a stable operation ID. Record the user's existing implementation approval using `plan approve`.
2. `work create PLAN` resolves its board before first projection: existing card, Work assignment, Plan assignment, shared registered default. Only implementation work creates a missing default child. Select an unrelated same-name board once with `board default BOARD --reason USER_SELECTION`. Existing cards stay pinned.
3. Record actual coordinator provider/model context or the user's worker selection. Grant agreed plan/cycle actions and exact resources using existing authorization; creation alone is not execution authority. Read [authorization.md](authorization.md).
4. `worker start WORK [--provider PROVIDER --model EXACT_ID --effort LEVEL] --instructions-file FILE --operation-id ID` checks capabilities, instructions and card readiness, then creates worktree, channel and worker. Omitted model uses a valid saved selection or observed coordinator. Start sends only readiness instructions.
5. The worker runs its sandbox probe and waits. `worker continue ATTEMPT`, also attempted by `coordinator tick`, checks readiness and sends implementation. Current project rules, selected Summary evidence and the report contract are included. A denied probe stays blocked.
6. Monitor during the active turn using `coordinator tick PLAN --owner SESSION` and its next-check/backoff guidance. Inspect blocking questions with `worker observe`, respond within scope and state the exact result awaited. No wakeup remains after the turn ends; reconnect explicitly and inspect the inbox.
7. The worker commits authorized work and uses `worker submit --contract FILE --report-file FILE`. Tick, `worker collect` or `worker receive` checks Plan/cycle/Work/Attempt, nonce, report hash, clean tree and actual HEAD before setting Work Review. This means coordinator review pending. Submission, receipt, processed review and integration are separate.
8. Inspect the candidate diff and instruction compliance. `work review WORK --verdict accept|revise|reject --notes TEXT` pins the candidate and processes the receipt. Revise/reject returns Work to Doing; send corrections and receive a new report. An old terminal Done never proves checks.
9. `worker integrate ATTEMPT` integrates the accepted candidate into a clean canonical tree. Prepare dependencies as authorized. `command PLAN --argv-file FILE --cwd PATH --purpose prepare|verify` requires exact command authority. Run checks only when authorized. Record criterion evidence independently, linking actual command logs where available.
10. `work complete WORK` finishes this integrated revision before another integration. When all work and final canonical evidence are ready, followthrough verifies and submits Plan Review; otherwise it returns the exact blocker. Continue remaining steps or report the real blocker and responsible resumer. Never end after merely starting workers.
11. Synchronize the board. `coordinator report PLAN` shows internal Review, board delivery, card URL and report draft. Send the outcome, verification, limitations and Review link to the user, then record the actual message using `coordinator report PLAN --message TEXT`. This is an attestation, not a chat send. Avoid duplicate reports already recorded for the submission.
12. Prepare/publish Summary during Review using [summaries.md](summaries.md). Explicit user acceptance authorizes `plan complete PLAN --approval ORIGINAL_REQUEST`. The coordinator supplies Summary JSON from evidence; do not ask the user to fill it in or approve again.
13. Ask close/keep only when absent. Use `plan cleanup` with its scope token and actual user choice. Worktrees remain. For failure use inspect, reconcile if necessary, then resume; preserve Done, Summary and valid close consent. Follow [recovery.md](recovery.md).

Feedback after Review uses `plan reopen` and new Work/cycle records. Final Done remains user acceptance. Administrative `card move --force` has separate semantics and cannot replace these gates.
