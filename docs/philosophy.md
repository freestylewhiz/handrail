# Handrail 설계 철학

Handrail의 목표는 조율자가 여러 작업자와 일하면서 사용자의 목표, 진행 상태, 검증 근거와 최종 판단을 연결하도록 돕는 것이다. 사용자가 같은 의도를 반복해서 설명하거나 이미 승인한 범위를 다시 승인해야 하는 부담을 줄인다.

반복적인 운영 승인은 사용자가 프로젝트 설계·구현을 Handrail에 일임하는 데 가장 큰 제약이다. 같은 범위의 작업이 보드 조회·작업자 실행·관측·검토·병합·테스트마다 다시 멈추지 않도록 하는 것을 핵심 제품 수용 기준으로 삼는다. 이미 받은 유효한 의도와 호스트 규칙은 재사용하고 실제로 달라진 범위만 확인한다. 최초 준비 후 동일 허용 범위의 추가 운영 질문·호스트 승인 0회를 목표로 하되 실제 클릭·자동 허용·거부·미지원은 구분해 측정한다. 최종 사용자 수락과 정리 선택을 생략하거나 거부된 권한을 우회한다는 뜻은 아니다.

## 사용자 의도를 계속 유지한다

목표와 완료 기준을 계획에 기록하고, 구현 승인과 실행 범위를 연결한다. 사용자가 이미 승인한 범위는 재사용한다. 모델, 동작, 경로 또는 대상이 달라지면 달라진 부분을 설명한다. 승인 문구가 있다는 사실만으로 호스트 권한이나 더 넓은 작업 권한이 생기지는 않는다.

## 도구의 관찰과 개발 결과를 구분한다

소켓 연결 성공, 지시 제출, 작업자의 입력 대기, 코드 검증과 사용자 수락은 각각 다른 사실이다. Handrail은 어느 사실을 언제 관찰했는지 기록한다. 오래된 관찰을 현재 상태처럼 표시하거나 화면의 Done을 업무 완료로 해석하지 않는다.

## 조율자가 다음 행동을 알 수 있게 한다

진행 상태에는 대상 작업자, 관련 작업, 마지막 관찰 시각과 다음 행동을 함께 보여준다. 응답을 기다린다면 누구의 어떤 결과인지 설명한다. 오류에는 실패 경계와 불확실성을 남기며, 사용자가 이미 제공한 정보를 다시 요구하기 전에 저장된 기록을 확인한다.

조율 책임은 작업자 실행으로 끝나지 않는다. 완료 제출을 수신하고 실제 변경을 검토·통합·검증한 뒤 사용자에게 Review를 요청할 때까지 이어진다. 제출, 수신, 검토 처리, 보드 반영, 사용자 보고는 별도로 남긴다. 자동 깨우기 수단이 없는 호스트에서는 활성 대화의 감시와 재접속 복구를 제공하고 감시 중단을 사실대로 표시한다.

기본값은 확인된 정보에서 정한다. 조율자가 직접 구현할 범위도 같은 제공자·정확한 모델의 작업자로 넘기며, 사용자의 명시적 모델 선택이 우선한다. 모르는 모델이나 추론 설정을 추정하지 않는다. 작업보드는 첫 구현 요청 때 준비하고, 이미 연결된 서버·부모 보드·사용자 선택을 재사용한다.

## 이력은 보존하고 현재 판단은 갱신한다

과거 실패는 이력에 남고, 현재 상태는 복구 결과를 반영한다. 검증은 해당 기준과 Git revision에 연결한다. 추가 요청은 새 작업과 회차에 기록해 이미 완료한 작업과 승인 이력을 보존한다.

## 외부 도구의 책임을 존중한다

Vikunja는 카드와 협업 보드를 제공하고, Herdr는 터미널과 작업자를 제공한다. Handrail은 이를 연결하는 워크플로우와 실행 기록을 소유한다. 외부 서버의 설치나 구현을 맡지 않으며 외부 성공 응답을 도메인 검증으로 대체하지 않는다.

### 보드 구성은 Handrail의 관리 기능이다

사용자에게 Vikunja의 project는 **보드(board)**로 부른다. 부모 보드·하위 보드는 관리 계층이며, 칸반 뷰와 열은 보드의 표시·상태 구성이다. 외부 API에서 사용하는 project 명칭은 어댑터의 프로토콜 용어로 유지한다.

연결된 부모 보드 아래 하위 보드를 추가하는 요청은 Handrail이 직접 처리해야 한다. 이 요청 때문에 Plan/Work 카드를 생성하거나 작업자 실행·모델 선택·Git 통합을 요구하지 않는다. 생성 결과, 부모 관계, 칸반 구성과 관리 이력을 확인하여 보드 구성 완료를 보고한다. 보드와 실제 개발 작업의 연결은 별도의 명시적 관계로 관리한다.

사용자가 특정 카드의 상태 전환을 명시적으로 요청하면 관리 기능으로 수행한다. 요청과 변경 전후 상태를 기록하고, 자동 동기화가 이를 덮어쓰지 않도록 보류한다. 카드 상태 전환이 개발 검증이나 통합을 수행했다는 의미를 갖게 해서는 안 된다. 개발 상태와 사용자 지정 카드 상태를 함께 설명하고, 자동 동기화는 사용자가 재개를 요청할 때 다시 연결한다.

## 실패 후 다시 이해할 수 있어야 한다

외부 부작용 전에 의도를 기록하고, 응답이 불명확하면 같은 작업을 무작정 반복하지 않는다. 작업 공간은 Review 동안 유지한다. 자원 정리는 계획 수락과 별도로 기록해 정리 실패로 결과나 이력을 잃지 않는다.

## 구조가 책임을 드러내야 한다

설정, 워크플로우, 실행 공간과 외부 연동을 폴더로 구분한다. 파일 이름을 옮기는 데 그치지 않고 상태 전이와 부작용의 소유자를 구분한다. 각 컴포넌트의 공개 계약으로 연결해 하나의 제품 흐름을 유지한다.

승인을 줄이는 방법은 고정 실행 경로, 좁은 동작별 규칙, 필요한 자원의 사전 준비, 실제 작업자 경계의 진단이다. 전역 sandbox 해제나 질문 생략을 권한 문제의 해결로 부르지 않는다. 구현 코드와 실제 호스트에서 관측한 개선은 다른 근거로 기록한다.

## 공통 지침은 명시적인 카드로 유지한다

부모 보드의 Instruction은 사용자와 조율자가 관리하는 현재 프로젝트 지침이다. 기획·배정·검토에서 원본과 참조 버전을 확인하고, 변경 영향과 예외를 해당 작업에 기록한다. 과거 Summary는 참고 근거이며 사용자 요청 없이 전역 규칙으로 승격하지 않는다. 사람은 자기 언어의 완결된 영역을 읽고, 에이전트는 필요한 언어·영역만 읽는다. 지침 카드는 호스트 권한이나 정리 동의가 아니다.

## 완료된 결정이 다음 개발의 근거가 된다

기획 완료는 사용자 수락을 기록하는 workflow 전이다. 카드 표시 상태만 바꾸는 관리 요청과 구분한다. 조율자는 기획·작업·리뷰의 근거를 Summary로 종합한다. Summary 원본과 이전 버전은 부모 보드의 카드와 댓글에 두고, 로컬에는 연결·전송·참조 메타데이터만 둔다.

사용자는 분리된 자기 언어 영역에서 읽고, 에이전트는 Agent Context에서 관련성을 판단한 뒤 한 언어의 필요한 항목만 읽는다. 과거 결정은 해당 범위의 이력이며 새 권한이나 영구 금지가 아니다. 결정이 바뀌면 이전 결정을 대체하는 근거를 기록한다. 사용자 수락과 자원 정리 선택은 분리하며, 보존을 선택해도 개발 완료는 유지한다.

Summary에는 사용자 요구에 따른 프로젝트 결과와 Handrail 수행 이슈를 구분해 남긴다. 분류는 발견자가 아니라 영향받은 책임을 기준으로 한다. 수행 이슈의 단계·기대와 실제 동작·영향·복구·현재 상태·근거는 이후 Handrail 개선 판단에 사용한다. 업무 재개와 원인 해결은 구분하며 관측이 없다는 이유로 문제없음을 선언하지 않는다. 이 기록을 제품 결함·개발 backlog·영구 지침으로 자동 승격하지 않고 개발 책임자가 채택·축소·제외를 판단한다. 외부 제품의 책임이나 구현 프로젝트의 문제를 Handrail 기능으로 무조건 확장하지 않는다.
