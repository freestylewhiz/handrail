# 프로젝트·전역 권한 정책 검토

작성일: 2026-10-01

상태: **백로그 수집 당시의 설계 검토 기록. v0.4의 실제 구현·명령·제약은 [권한 사용법](permissions-v0.4.md)을 기준으로 한다.** 아래 후보 중 deny 우선 합성, 목적지별 네트워크 제한, 실효 권한 자동 검사와 상주 조율자는 아직 구현하지 않았다. 이 문서가 실행 권한을 부여하지 않는다.

관련: [백로그](../handrail-dev-spec/v0/BACKLOG.md), [실제 실행 피드백](../handrail-dev-spec/v0/FEEDBACK_RC4_EXECUTION.md), [RC4 실행 권한 계약](worker-authorization-policy.md).

## 1. 목표와 권장 방향

사용자가 구체화된 계획을 위임하면, 사전에 준비한 권한 안에서 구현·검증·검수·통합·카드 동기화를 이어가고 사용자는 계획 Review에서 결과를 확인한다. 동일 권한에 대한 반복 승인 때문에 장시간 작업이 시작되지 않는 경험을 줄인다.

권장 구조는 다음 세 요소다.

1. **재사용 가능한 권한 정책:** 이 프로젝트 또는 사용자의 여러 프로젝트에서 어떤 자원·동작을 허용하는지 기록한다.
2. **계획 위임:** 그 권한을 사용해 이번에 수행할 계획·회차·한도를 정한다. 권한이 있다고 새 개발 작업까지 자동으로 시작하지 않는다.
3. **CLI별 적용 계층:** Codex·Cursor가 지원하는 설정으로 변환하고 실제 적용 범위를 확인한 뒤 실행한다.

여러 계획 카드를 한 번에 의뢰하는 경우 선택된 계획·회차 목록을 하나의 위임 묶음으로 기록한다. 사용자가 그 묶음의 개발과 필요한 권한을 이미 승인했다면 **각 부모 계획이나 하위 작업으로 넘어갈 때 다시 승인하지 않는다.** 카드별 검증·Review·사용자 최종 Done은 각각 유지한다. 위임에 없는 새 계획 추가나 권한·한도 확대는 변경분으로 처리한다. 범위 안에서 조율자가 구체화한 하위 작업 명세는 상위 위임에서 파생됐다고 기록하며 사용자에게 개별 명세 동의를 받았다고 꾸미지 않는다.

기본 정책은 최초 도입 시 묶어서 확인할 권한 템플릿이다. 승인 전 자동 허용을 뜻하지 않는다. 이미 승인한 범위에 포함되면 재확인 없이 재사용하고, 범위가 넓어지면 추가분만 확인한다.

## 2. 현재 구현과 변경 후보

| 구분 | RC4 현재 구현 | 검토 중인 변경 |
| --- | --- | --- |
| Handrail 실행 승인 | 정확한 입력에 묶인 one-run 미리보기와 동의 | 프로젝트·전역 정책에서 계획 및 run 권한 파생 |
| 작업자 자동 실행 | `workspace-auto`에서 provider별 확인 억제 옵션 사용 | 허용 범위·실제 설정 점검과 결합 |
| 추가 경로·네트워크 | 일반적인 extended 권한 흐름 미완성 | 요구 수집·동의·기록·적용·재사용 절차 |
| 조율자 권한 | worker 옵션으로 조율자 승인까지 제어하지 못함 | 조율자 세션의 준비 상태와 적용 방법도 안내 |
| 재시도 | 새 run은 새 미리보기; 동일 run revise는 다른 경로 | 재시도 종류별로 기존 위임 재사용 여부 판정 |
| 전체 계획 진행 | worker supervisor와 개별 workflow 명령 | 계획 진행 지속·재개 후보와 연결 |

현행 계약의 one-run 동의, worker 권한과 통합·동기화 결정의 분리는 그대로 배포되어 있다. 이 검토안을 채택할 때 코드·스킬·도움말·현행 계약을 함께 개정해야 한다.

## 3. 승인·권한의 네 계층

| 계층 | 확인할 내용 | Handrail의 역할 |
| --- | --- | --- |
| 작업 위임 | 어떤 계획을 어디까지 수행할지 | 계획 회차·검증·한도와 사용자 의사 기록 |
| Handrail 동작 | 카드 갱신, 실행 준비, 로컬 통합 등 | 역할별 허용 범위 판정 및 실행 이력 |
| 조율자·작업자 CLI | 도구 승인, 파일·명령·네트워크 설정 | CLI별 어댑터로 적용하거나 설정 변경 안내 |
| 상위 환경 | 조직 정책, OS, 컨테이너, 부모 프로세스 제한 | 제약 진단; 하위 설정만으로 해제된다고 판단하지 않음 |

조율자가 Handrail을 실행하는 단계에서 막히면 worker 설정을 바꿔도 해결되지 않는다. 작업자가 자신의 세션 상태를 만들지 못하는 문제 역시 어느 계층에서 거부했는지 확인해야 한다.

권한 기록에 `approved`가 있어도 설정 반영이 실패했다면 실행 준비가 끝난 것이 아니다. **동의 여부, 적용 여부, 적용 검증 결과를 따로 기록**한다.

## 4. 저장 범위와 신뢰 경계

아래 경로는 제안이며 아직 제품 파일 규격이 아니다. 실제 구현은 기존 config/data 경로 및 XDG 설정을 따른다.

| 자료 | 저장 위치 후보 | 성격 |
| --- | --- | --- |
| 프로젝트 요구 정책 | 저장소 `.handrail/permissions.request.json` | 팀 공유 가능; 필요한 권한 선언이며 승인 증거가 아님 |
| 프로젝트 승인 | 사용자 Handrail data 아래 `projects/<workspace_id>/permission-grants.json` | 사용자·호스트·저장소에 귀속된 비공개 승인 |
| 전역 승인 | 사용자 Handrail config 아래 `permission-policy.json` | 명시적으로 전역 적용을 선택한 규칙 |
| 계획 위임·실행 기록 | 기존 계획/run 비공개 상태 | 사용한 grant ID·revision, 실제 입력, 적용 설정 해시 |
| CLI 적용 자료 | 실행별 관리 디렉터리 또는 provider가 지원하는 설정 위치 | 승인 정책에서 생성한 산출물; 별도의 승인 원본이 아님 |

전역은 **동일 사용자·호스트에서 Handrail이 관리하는 실행**을 뜻한다. 시스템 전체 사용자나 임의의 미래 저장소에 자동으로 적용하는 의미가 아니다. CLI 자체의 사용자 전역 파일을 바꾸면 Handrail 밖의 세션에도 영향이 생길 수 있으므로 실제 영향 범위를 따로 표시한다.

전역 재사용은 provider 세션 경로처럼 프로젝트 간 동일한 기반 권한에 적합하다. 프로젝트 소스·Git·Vikunja 쓰기는 프로젝트 승인에 두는 것을 기본으로 제안한다. 사용자가 전역 템플릿을 선택한 경우에도 새 프로젝트 등록 시 저장소 신원과 템플릿 적용 대상 여부를 확인한다.

저장소 ID만 복사해서 승인을 얻을 수 없도록 사용자 로컬 등록, 실제 경로, Git common directory의 연결을 확인한다. worktree는 등록된 저장소와 Handrail이 생성한 실행 소유권을 확인해 파생한다. 다른 clone·사용자·호스트로 승인을 자동 이전하지 않는다.

프로젝트 파일, 카드·첨부파일, 모델이 생성한 지침은 요구 권한을 제안할 수 있지만 승인 기록을 직접 확대할 수 없다. 승인 원장은 worker 쓰기 범위에서 제외하고 비밀 토큰을 담지 않는다. 파일 권한만으로 같은 OS 사용자 아래 모든 도구의 접근을 차단한다고 보장하지 않으며 실제 sandbox 경계를 함께 확인한다.

## 5. ‘동일 범주’의 판정

문장이 비슷한지 대신 정규화된 권한 요청이 기존 허용 범위의 부분집합인지 판정한다.

| 비교 축 | 예시 |
| --- | --- |
| 주체 | 조율자 / Handrail 관리 프로세스 / worker |
| provider | Codex / Cursor / 향후 CLI, 검증된 어댑터 의미 |
| 대상 | 저장소, 실행 소유 worktree, 경로, 서비스 endpoint·프로젝트 ID |
| 동작 | 읽기 / 쓰기 / 프로세스 실행 / 리슨 / 원격 API 변경 |
| 조건 | 명령 인자·cwd, 목적지·포트, 작업 종류, 실행 한도 |
| 유효성 | 정책 revision, 만료, 취소, 호환성 점검 결과 |

예시:

- 같은 저장소의 새 Handrail worktree: 승인한 생성 규칙과 소유권에 맞으면 재사용 가능. 경로 접두사만 같은 외부 디렉터리는 제외.
- 테스트 명령: 인자·cwd·파일/네트워크 경계 안이면 재사용 가능. `node`, `python`, `sh`, `rtk` 전체 허용으로 일반화하지 않는다.
- 실제 #9 재시도에서는 복구용 임시 스크립트와 새 worktree를 인자로 받은 독립 검증 명령에 각각 ‘항상 허용’이 기록됐다. run마다 달라지는 이름·절대 경로 대신 안정적인 관리 인터페이스가 등록된 실행 경로와 권한을 판정하는 방안을 검토한다. 고정 명령 이름만 허용한다고 안전한 범위가 생기는 것은 아니며 provider 규칙과 내부 검사 양쪽이 필요하다.
- 소스가 달라지는 것은 개발의 정상 흐름이다. 모든 변경마다 사용자 승인을 다시 요구하지 않고 실행 입력·검증 fingerprint를 새로 기록한다. 실행 스크립트가 요구하는 권한·설치 hook·외부 목적지가 확대되면 변경분을 점검한다.
- 검수 중 추가한 오류 재현·회귀·복구 검증도 기존 위임 및 실행 권한 범위 안이면 재사용 대상으로 본다. 동일 run의 `handrail-review-quiz.cjs` 이후 `handrail-review-quiz-recovery.cjs`에 새 승인이 발생한 실제 피드백이 있다. 스크립트 추가와 권한 확대를 구분하고 검증 근거는 새로 기록한다. 실제로 관찰하지 않은 추가 접근을 파일명만으로 허용하지 않는다.
- 패키지 설치: 승인한 registry·캐시·설치 스크립트 실행 범위 안에서 재사용. 새로운 외부 다운로드와 임의 원격 스크립트 실행까지 포함하지 않는다.
- Vikunja 카드 변경: 연결된 인스턴스와 등록된 프로젝트에서 허용 동작만 재사용. 서버 전체 관리나 다른 프로젝트 변경은 별도 범위.

명시적 거부·취소와 상위 제약을 먼저 적용한다. 그 다음 유효한 전역·프로젝트 승인을 합성하고 계획 위임 범위로 제한한다. 프로젝트의 명시적 제한은 전역 허용보다 좁힐 수 있다. 단순히 “더 구체적인 allow가 deny를 덮는다”는 규칙을 쓰지 않는다.

CLI가 이 의미를 정확히 구현하지 못하면 `unsupported` 또는 `requires_setup`으로 표시한다. 조용히 더 넓은 설정으로 변환하지 않는다.

## 6. Handrail 기본 권한 템플릿 후보

‘기본 포함’은 최초 일괄 미리보기에 넣는다는 의미다. 사용자의 기존 권한과 위임으로 충족되면 새 동의 없이 적용한다.

| 권한 범주 | 주체와 범위 | 기본 정책 제안 |
| --- | --- | --- |
| 프로젝트 소스·명세 읽기 | 조율자, worker; 해당 저장소와 전달된 자료 | 기본 포함; 관리 자격증명 제외 |
| 구현 파일·산출물 쓰기 | worker; 자신의 worktree와 실행 임시 경로 | 기본 포함; 승인 원장·플러그인 캐시 제외 |
| 실행 자료·복구 snapshot | 관리 프로세스; 해당 workspace의 run/worktree 자료 | 기본 포함; worker에는 필요한 입력만 전달 |
| CLI 세션 상태 | 각 CLI; 버전별 확인된 필요한 세션 경로 | 사전 발견 후 포함; 사용자 전역 재사용 선택 가능 |
| 로컬 구현 명령·검증 | worker/검증 주체; 격리된 프로젝트 환경 | 기본 포함; 셸 문자열 허용과 OS 경계는 별개 |
| 의존성·빌드 캐시 | 준비 주체; 지정 캐시·worktree | stack 탐지 후 제안; lockfile·hook·네트워크 범위 표시 |
| 브라우저 테스트·로컬 서버 | 검증 주체; loopback와 실행 소유 프로세스 | 필요 시 포함; 포트 범위·임시 데이터·정리 책임 명시 |
| 모델 서비스·인증 | 각 CLI 자체 | 기존 로그인 재사용; 모델 통신과 worker shell 네트워크를 구분 |
| Vikunja 조회·카드·관계·댓글·상태 변경 | 조율자/관리 프로세스; 부모와 등록된 하위 프로젝트 | 계획 위임 안에서 포함; 토큰은 worker에 전달하지 않음 |
| 부모 Review 열 생성 | 관리 프로세스; 선택된 부모 Kanban view | 연결 준비 단계에 포함; 하위 보드에는 생성하지 않음 |
| Git worktree·로컬 기준 커밋·통합 | 관리 프로세스/조율자; 해당 저장소 | 필요 동작을 묶어 제안; Git 메타데이터의 별도 제약 확인 |
| 상태 조회·취소·복구 | 관리 프로세스; 기록된 자신의 프로세스 | 기본 포함; 임의 PID 조작으로 확장하지 않음 |
| 추가 외부 경로·도메인·MCP·Fetch | 필요한 주체만 | 실제 필요에 따라 추가분 승인 |

원격 Git 게시·릴리스는 기존 제품 범위에 따라 이 기본 정책에서 다루지 않는다. 계획 최종 Done은 사용자 직접 처리나 명시적 지시로 유지한다. 하위 프로젝트 생성은 연결된 부모 아래의 별도 후보 권한이며 기존 카드 관리 승인에 자동 포함하지 않는다.

## 7. 구현 시작 전 절차

1. **대상 확인:** workspace 신원, 연결된 보드, 계획 회차, CLI·모델, 검증 명령을 수집한다.
2. **실제 환경 확인:** 조율자·worker의 버전, 실행 경로, 기존 설정과 조직 제약, 세션·캐시 경로, 의존성·테스트 조건을 확인한다. 설정 전체나 토큰을 로그에 출력하지 않는다.
3. **권한 계산:** 기본 템플릿에서 필요한 권한만 선택하고 저장된 승인과 비교한다. 결과를 `covered / needs_consent / requires_setup / unsupported / denied`로 구분한다(이름은 제안).
4. **한 번에 안내:** 새로 필요한 권한과 적용 범위, 지속 기간, 실제 설정 변경을 요약한다. 선택지는 이번 실행 / 계획 회차 / 프로젝트 / 사용자 전역으로 제공한다. 추가 권한이 없으면 다시 묻지 않는다.

   복수 계획 의뢰라면 모든 선택 계획의 예상 권한을 함께 계산한다. 계획별 미리보기를 차례로 제시해 사용자 응답을 반복 요구하지 않는다. 프로젝트 권한과 이번 의뢰가 충분하면 ‘계획 묶음 승인’이라는 추가 관문도 만들지 않는다.
5. **기록·적용:** 실제 사용자 선택을 기록하고 CLI별 설정을 생성·병합한다. 설정 저장의 성공과 실제 적용의 성공을 구분한다.
6. **준비 완료 확인:** 경로 쓰기, 제한된 네트워크·테스트 실행 가능성 등 필요한 확인을 수행한다. 준비 명령 역시 기록된 권한 범위 안에서 실행하며 원격 카드를 시험 삼아 변경하지 않는다.
7. **실행:** worker를 시작하기 전에 의존성과 실행 패킷을 준비한다. 각 run에 권한 출처·정책 revision·적용 설정 해시를 연결한다.

사용자가 이미 구체적인 계획에 대해 구현·검증·통합을 위임했고 정책 범위가 충분하면 별도의 확인 코드 왕복을 추가하지 않는 것이 목표다. 미리 알 수 없는 모든 요구를 완벽히 탐지한다고 약속하지 않으며 다음 절차로 처리한다.

## 8. 실행 중 추가 권한 처리

`차단 탐지 → 요구 정규화 → 기존 승인 대조 → 필요한 추가분 동의 → 정책 갱신 → CLI 적용 확인 → 재개`

- **기존 승인 안인데 적용이 빠진 경우:** 설정을 보정하고 재적용한다. 권한 범위가 같다면 사용자에게 같은 질문을 반복하지 않는다.
- **기존 승인 밖인 경우:** 무엇을 위해 어떤 권한이 필요한지와 저장 범위를 제시한다. 사용자의 승인 후 원장을 새 revision으로 갱신한다. 차단을 관측했다는 사실이나 모델의 요청만으로 allow를 추가하지 않는다.
- **플랫폼에서 직접 승인한 경우:** provider가 검증 가능한 승인 이벤트·내역을 제공할 때만 해당 범위로 가져오는 기능을 검토한다. 이벤트가 없으면 승인 기록을 추정·조작하지 않고 다음 실행 준비에서 처리한다.
- **설정 재로딩이 안 되는 경우:** 현재 실행을 보존·정지한 뒤 준비를 마쳐 재시작한다. 파일 갱신만으로 기존 프로세스의 권한이 바뀌었다고 보고하지 않는다. 과거 동의는 유지하고 실행 입력은 다시 고정한다.
- **사용자가 자리를 비운 경우:** 해당 작업을 이유가 있는 차단 상태로 기록한다. 기존 순차 실행·잠금·의존성 규칙 안에서 가능한 다른 작업을 진행한다. 알림은 사용자가 설정한 채널이 있을 때만 제공한다.

재시도는 입력 자료 준비 → worker 시작 순서를 지킨다. 제출 전 실패는 같은 카드의 시도 이력으로, 완료 후 수정은 신규 하위 작업 카드로 연결하는 후보 정책을 따른다.

## 9. Codex·Cursor 적용 검토

2026-10-01 로컬 CLI 도움말 확인: Codex `0.157.1`, Cursor Agent `2026.09.28-64d2043`. 도움말과 공식 문서 확인이며 권한 강제 동작의 실험 검증은 이번 문서 작성에서 수행하지 않았다. OpenAI 관련 설명은 OpenAI Docs 공식 문서와 로컬 CLI를 기준으로 한다.

### Codex

로컬 도움말에는 `--sandbox workspace-write`, `--ask-for-approval never`, `--add-dir`, `--approve-for-me`가 있다. `never`는 실패를 모델에 반환하는 정책이며 필요한 경로·네트워크 접근을 자동으로 허용하지 않는다. 자동 리뷰도 사용자 승인 원장과 같은 의미로 취급하지 않는다.

공식 문서의 permission profiles는 beta이며 legacy sandbox 설정과 함께 조합하지 않는 규칙이 있다. 현행 Handrail의 `--sandbox` 방식과 새 profiles 중 버전별로 하나의 적용 경로를 선택하는 검토가 필요하다. 명령의 sandbox 밖 실행을 다루는 rules와 파일·네트워크 경계도 구분한다. [Permission profiles](https://learn.chatgpt.com/docs/permissions), [Rules](https://learn.chatgpt.com/docs/agent-configuration/rules).

프로젝트 정책을 Codex 전역 prefix rule로 바꾸면 다른 저장소에도 영향을 줄 수 있다. 작업 경로 조건을 표현하지 못하는 규칙은 프로젝트 전용 권한을 구현한 것으로 인정하지 않는다. 특히 `rtk`, `python`, `node`, `git` 전체 prefix 허용을 생성하지 않는다.

### Cursor

CLI 문서는 사용자 `~/.cursor/cli-config.json`과 프로젝트 `.cursor/cli.json`의 permissions, 명령·파일·Fetch·MCP별 규칙과 deny 우선 처리를 설명한다. 설정 문서에는 approvalMode와 sandbox 설정이 구분되어 있다. [CLI Permissions](https://cursor.com/docs/cli/reference/permissions), [CLI Configuration](https://cursor.com/docs/cli/reference/configuration).

로컬 도움말의 `--force`는 명시적으로 거부되지 않은 명령의 허용 모드다. 이것을 특정 명령만 허용한 것으로 표현하지 않는다. `--sandbox enabled`를 유지하고 설정된 도구·MCP·Fetch 범위도 확인한다. `--add-dir`만으로 필요한 세션 경로 쓰기가 가능하다고 단정하지 않는다.

공식 sandbox 문서는 추가 읽기·쓰기 경로와 설정 소스 간 병합을 설명하며 경로가 합쳐질 수 있다. 따라서 Handrail의 프로젝트 제한이 이미 넓어진 사용자 설정을 좁힌다고 가정하지 않는다. 해당 설치 CLI가 이 설정을 어떻게 소비하는지는 별도 검증 대상이다. [sandbox.json](https://cursor.com/docs/reference/sandbox).

세션 디렉터리 예외는 실제 필요한 하위 경로를 발견한 뒤 적용한다. `~/.cursor` 전체나 사용자 홈 전체 쓰기를 기본 권한으로 제안하지 않는다.

### 공통 어댑터 계약

- 버전·실행 파일·설정 출처를 확인하고 각 capability에 대해 적용 방법과 지원 여부를 반환한다.
- 가능한 경우 실행별 설정을 우선한다. 사용자의 기존 설정을 보존하고 적용 diff를 기록한다.
- user-level 설정만 지원하면 다른 세션에 미치는 범위까지 표시한다. 전역 설정을 임시 교체했다 복원하는 방식은 동시 세션과 충돌하므로 기본안으로 채택하지 않는다.
- provider 설정과 상위 host가 허용하는 범위를 확인한다. 실제 권한이 더 넓거나 확인 불가하면 그 사실을 표시하고 준비 완료로 단정하지 않는다.
- sandbox 해제나 모든 도구 허용을 조용히 추가하지 않는다. 새 CLI는 동일 의미의 제한을 확인한 뒤 무인 실행에 포함한다.
- CLI 버전 변경은 호환성 재검사를 유발한다. 같은 의미가 검증되면 재승인하지 않고, 의미가 넓어지는 경우에만 추가 동의를 요청한다.

## 10. 기록·갱신·취소

승인 레코드 후보 필드:

| 필드 묶음 | 내용 |
| --- | --- |
| 식별 | schema_version, grant_id, revision, scope, 사용자·호스트·workspace 식별 |
| 권한 | actor, provider, capabilities, 대상·동작·조건, 제외 항목 |
| 사용자 의사 | 승인 시각, 실제 승인 답변, 전달된 미리보기 해시, 승인 출처 |
| 수명 | 만료·취소·대체 revision, 사용자가 선택한 재사용 범위 |
| 적용 | provider/adapter 버전, 설정 해시, 적용 성공·실패, 검증 결과 |
| 감사 | 관련 plan/run, 이전 revision, 추가·삭제 이유 |

대화 답변은 조율자가 전달한 승인 근거이며 암호학적 사용자 인증이 아니다. 확인 코드 역시 요청 연결 값이다. 실제 승인 문구를 바꾸거나 누락된 코드로 새로운 범위를 만들어내지 않는다.

갱신은 잠금과 revision 비교, 원자적 쓰기로 처리한다. 두 프로젝트가 전역 파일을 동시에 변경해도 승인이나 기존 사용자 설정을 잃지 않아야 한다. 생성된 설정이 사용자의 수동 수정과 충돌하면 자동 덮어쓰기하지 않는다.

사용자는 승인 목록·범위·사용 중인 run을 조회하고 취소할 수 있어야 한다. 취소 이후 신규 실행·재시도에는 적용하지 않는다. 이미 실행 중인 프로세스는 권한이 즉시 사라진다고 보장할 수 없으므로 별도 중지·재시작 처리가 필요하다. 설정 복원은 Handrail 소유 변경분만 대상으로 하고 다른 세션의 설정을 덮지 않는다.

## 12. 검증 후보와 미결정 사항

개발 범위 확정 시 다음을 수용 시나리오로 구체화한다.

1. 첫 프로젝트 준비에서 필요한 권한을 묶어 확인한 뒤 동일 범주의 여러 worker 실행·재시도에 사용자 질문이 반복되지 않는다.
2. 전역 기반 권한은 재사용하면서 A 저장소의 승인으로 B 소스·카드를 변경하지 않는다.
3. 새로운 목적지·경로만 추가 승인하고, 승인 취소·만료·거부를 준수한다.
4. worker가 요구 정책을 수정해도 승인 원장이 자동 확대되지 않는다.
5. 같은 의미의 CLI 업데이트에는 재승인 없이 적용하고 호환성 변화는 명확히 진단한다.
6. 저장 성공·설정 적용 실패, 프로세스 재로딩 불가, 조율자 외부 sandbox 차단을 구분한다.
7. 신규 worktree·의존성·브라우저 검증·Vikunja 동기화를 실제 두 CLI에서 검증한다. MCP/Fetch는 별도 통제 범위를 확인한다.
8. 여러 세션의 동시 갱신·취소·재시작에서 권한과 실행 이력을 잃지 않는다.
9. 계획 #4–#6을 한 번에 위임하고 하위 #7–#12를 실행·수정·검증할 때, 다음 계획이나 작업 카드로 이동했다는 이유로 동의를 다시 요구하지 않는다. 선택되지 않은 계획 #13은 자동 포함되지 않는다.
