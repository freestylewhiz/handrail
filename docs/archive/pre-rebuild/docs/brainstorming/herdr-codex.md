# Herdr와 Codex 브레인스토밍 기록

- 시작일: 2026-10-02
- 상태: 진행 중
- 목적: 대화에서 나온 아이디어와 결정, 미해결 질문을 누적해 이후 개발 타당성을 검토한다.
- 기록 원칙: 대화 내용을 주제별 요약과 결정 로그로 갱신한다. 확정되지 않은 아이디어는 결정으로 표현하지 않는다.

## 잠정 주제

조율자가 사용자와 브레인스토밍해 계획을 세우고, 계획에 딸린 구현 카드를 에이전트에게 위임해 지속 개발하는 도구를 브레인스토밍한다. Herdr와 Codex/Cursor는 가능한 실행 환경 후보이며, 제품 범위는 대화에 따라 조정한다.

## 제품 방향

조율자는 사용자의 아이디어를 함께 구체화하고 합의한 내용을 계획 카드로 만든다. 계획을 구현 가능한 작업 카드로 나누고 Codex 또는 Cursor 에이전트에게 맡긴다. 결과는 조율자가 검토한 뒤 리뷰 상태로 제출하고, 사용자가 최종 확인한다.

이 과정을 반복하면 프로젝트의 요구사항과 개발 근거가 카드로 축적된다. 작업 카드와 연결된 계획, 구현, 검토 기록을 통해 무엇을 왜 개발했는지 추적할 수 있어야 한다. 이후 기능 추가나 수정 요청이 들어오면 과거 결정과 결과를 근거로 삼아 맥락 손실과 에이전트의 근거 없는 추정을 줄이고, 사람도 프로젝트 이력을 따라갈 수 있게 하는 것이 목표다.

환각을 완전히 없앤다고 단정하기보다, 계획·작업·검증·사용자 확인을 연결해 근거 없는 변경을 줄이고 추적 가능하게 만드는 방향으로 이해한다.

## 확인된 배경

- Herdr는 에이전트 터미널 세션을 관리하는 도구이며 Codex 연동을 제공한다.
- Herdr는 Codex 연동 설치 명령으로 `herdr integration install codex`를 문서화하고 있다.
- Herdr를 조작하는 agent skill이 있으며 `npx skills add herdrdev/herdr --skill herdr -g`로 설치할 수 있다.
- Herdr 안에서 실행 중인 에이전트만 제어하도록 스킬은 `HERDR_ENV=1` 가드를 사용한다.
- Herdr plugin과 Codex plugin은 서로 다른 확장 체계다. Herdr plugin은 Herdr를 확장한다.

## 현재 구현에서 확인한 간극

- 일반 `task comment` 명령으로 댓글을 쓰는 기능과 작업 맥락에서 댓글을 읽는 기능은 있다.
- 계획 카드를 사용자 Review로 제출할 때 요약 댓글을 남기고 Review 상태로 옮기는 경로도 구현되어 있다.
- 하지만 계획에 연결된 관리형 작업 카드는 `run sync` 시 작업 완료 상태와 내부 근거를 기록할 뿐, 에이전트 결과를 작업 카드 댓글로 게시하지 않는다. 구현 결과(`RESULT.md`, `result.json`, journal)는 로컬 run 이력에 저장되므로, Vikunja 카드만 보는 사람에게 작업 과정과 결과가 충분히 보이지 않을 수 있다.
- 기존의 구형 단일 카드 `run sync` 경로에는 댓글 게시가 있지만, 계획/작업 카드 중심의 새 workflow와 댓글 동작이 일관되지 않다.
- 이는 코드 경로를 읽어 확인한 구현 간극이다. 실제 사용 중 실패한 구체 사례와 빈도는 아직 이 기록에서 수집하지 않았다.

## 아이디어 모음

- 조율자와의 브레인스토밍 결과를 합의된 계획 카드로 남긴다.
- 조율자가 계획을 구현 카드들로 분해하고, 각 카드를 Codex 또는 Cursor 에이전트에 배정한다.
- 구현이 끝난 카드는 조율자 검토를 거쳐 리뷰 상태로 전환한다.
- 사용자가 결과를 확인하고 완료를 결정한다.
- 계획·구현·리뷰 이력이 쌓여 프로젝트의 결정 근거와 변경 이력을 재사용할 수 있다.
- 향후 기능 추가·수정은 관련 과거 카드와 근거를 따라 계획한다.

## 결정 사항

- 2026-10-02: 목표 workflow는 브레인스토밍 → 계획 카드 → 구현 카드 → Codex/Cursor 에이전트 작업 → 조율자 리뷰 → 사용자 확인 순서다.
- 2026-10-02: 카드 이력은 할 일 상태만이 아니라 개발 배경과 작업 결과를 추적하는 프로젝트 기억으로 취급한다.

## 미해결 질문

- 작업 카드 댓글에는 어떤 시점과 단위로 기록할까: 위임 시작, 의미 있는 진행 이정표, 최종 결과, 조율자 검수/통합까지 각각 남길지?
- 에이전트의 전체 대화 transcript가 아니라 재현 가능한 요약·산출물·검증 근거를 남기는 것이 적절한가?
- 댓글 게시가 실패해도 로컬 run과 작업은 계속 진행하고, 별도의 pending/conflict 상태로 재시도할 수 있어야 하는가?
- Plan 제출 댓글과 work 카드 댓글에 각각 어떤 필드(계획/작업 ID, worker/provider/model, run ID, 변경 요약, 검사 결과, 통합 commit, 후속 조치)가 필요한가?

## 대화 기록

### 2026-10-02 — 세션 시작

- 사용자 요청: 브레인스토밍을 시작하고, 이후 개발 검토에 활용할 수 있도록 별도 파일에 대화를 계속 기록한다.
- 진행 방향: 아이디어, 결정, 미해결 질문을 분리해 이 문서를 대화에 맞춰 갱신한다.

### 2026-10-02 — 제품 workflow와 목적

- 사용자 설명: 조율자와 브레인스토밍해 계획 카드를 만들고, 조율자가 계획의 구현 카드를 생성해 Cursor 또는 Codex 에이전트로 구현한다. 조율자는 결과를 리뷰 상태로 넘기고 사용자가 확인한다.
- 사용자 설명: 이런 개발을 지속하면 요구와 작업 이력이 충분히 쌓이고, 이후 변경에서 과거 근거를 참조해 에이전트의 환각을 줄일 수 있다. 사람도 수행한 작업과 이유를 카드로 추적할 수 있다.
- 정리: Handrail은 계획·구현·검토·사용자 확인을 연결해 지속 개발의 근거와 이력을 쌓는 도구다.

### 2026-10-02 — 작업 카드 댓글 이력 문제

- 사용자 관찰: 실제 구현 과정에서 조율자가 Codex/Cursor에 작업을 의뢰하고 그 실행 이력을 카드 댓글로 돌려 기록하는 흐름이 현재 잘 되지 않는다.
- 코드 확인: 댓글 작성 API와 수동 명령은 존재하고, plan Review 제출은 요약 댓글을 남긴다. 그러나 관리형 work card의 `run sync`는 댓글 게시 없이 `kanban.complete_work`로 이어져 로컬 완료 근거만 기록한다. 반면 legacy 단일 카드 `run sync`에는 댓글 동기화가 구현되어 있다.
- 영향: 작업 카드에서 요청·결과·검증을 따라가는 사용자 가시성이 부족하며, 로컬 run 파일을 별도로 열어야 할 수 있다. 이는 사용자가 말한 추적 가능한 프로젝트 이력 목표와 충돌한다.
- 아직 정하지 않음: 댓글의 상세도, 진행 중 업데이트 빈도, 실패/재시도 표현, 에이전트 대화 원문 보존 여부.
# Herdr 기반 워커 협업 아키텍처 논의

## 2026-10-02 — Herdr 워커 협업 제안

### 사용자 제안

조율자가 Herdr 안에서 실행될 때, 같은 Herdr 스페이스에 워커별 터미널을 할당한다. 조율자는 Herdr 기능을 이용해 각 워커에게 구현 지시와 수정·검수 의견을 보내고 응답 및 상태를 확인한다. 사용자는 나중에 Herdr 터미널에서 실제 에이전트 대화와 진행을 확인할 수 있다. 이를 통해 조율자와 워커 사이의 구현 협업을 단순화하고 싶다.

### 현재 평가: 기술적으로 가능

Herdr는 워크스페이스·탭·패널과 에이전트 수명주기를 다루며, Codex 및 Cursor 같은 에이전트를 터미널 패널에서 시작하고 프롬프트를 전달하며 출력과 상태를 읽는 기능을 제공한다. 따라서 조율자가 여러 워커를 관리하는 실행 어댑터로 사용할 수 있다.

### 제안 아키텍처 (아직 결정되지 않음)

1. 조율자와 사용자가 브레인스토밍하고 부모 계획 카드를 확정한다.
2. 조율자가 계획을 구현 카드들로 나누고 사용자 승인 조건을 확인한다.
3. Handrail 실행기가 카드별로 Herdr 작업 공간/패널과 워커를 준비하고, 카드에 연결된 작업 디렉터리 또는 Git worktree를 할당한다.
4. 조율자가 Herdr를 통해 워커를 지시하고, 진행 상황·질문·결과를 확인한다. 필요하면 리뷰 피드백을 보내 수정 라운드를 진행한다.
5. Handrail이 결과물, Git diff, 검증 결과를 확인하고 구조화된 실행 요약 및 워커의 주요 메시지를 Vikunja 카드 댓글과 로컬 실행 기록에 남긴다.
6. 카드가 Review로 이동하고 사용자가 결과를 검수한다.

Herdr는 에이전트 실행과 상호작용을 담당하고, Handrail은 카드 상태·권한·작업 범위·검증·Git 통합·지속 가능한 이력의 기준 시스템으로 남기는 구성이 유력하다. 이는 제안이며 아직 사용자 결정이 아니다.

### 설계상 주의점

- Herdr의 터미널 출력과 상태 표시는 Vikunja 카드 이력의 대체물이 아니다. Handrail이 지시, 응답 요약, 상태 전이, 변경 파일, 검증, 리뷰·수정 라운드를 카드와 로컬 run 기록에 명시적으로 동기화해야 현재의 댓글 누락 문제를 해결할 수 있다.
- Herdr가 에이전트 상태를 표시해도 상태 판정만으로 작업 완료를 선언해서는 안 된다. 산출물, diff, 승인된 검증을 Handrail이 확인해야 한다.
- 터미널에서 대화를 다시 볼 수 있다는 점은 유용하지만, 모든 에이전트의 전체 대화가 항상 완전한 스크롤백으로 남는다고 가정해서는 안 된다. Handrail의 구조화된 실행 기록을 감사 가능한 기준으로 유지한다.
- 여러 쓰기 에이전트가 동시에 작업하면 같은 파일이나 체크아웃을 건드릴 수 있다. 카드별 분리 worktree/브랜치와 통합 정책이 필요하다. 초기 구현은 카드별 단일 작성 에이전트로 제한할 수 있다.
- 워커는 최소 권한으로 실행하고 Vikunja 전체 접근 토큰이나 조율자 자격 증명을 공유하지 않는다. 지시·응답 동기화는 재시도해도 중복 댓글이 생기지 않도록 실행/메시지 ID를 사용해야 한다.
- Herdr 설치 버전, Codex/Cursor 통합 상태, 현재 프로세스 환경에서 Herdr 제어 CLI 사용 가능 여부를 실행 전에 확인해야 한다.

## 2026-10-02 — 계획 단위 Herdr 스페이스와 사용자 검수 루프

### 사용자 제안

- 각 계획 카드 ID에 대응하는 Herdr 스페이스를 만들고, 그 계획을 수행하는 동안 조율자와 초대된 워커가 그 안에서 협업한다.
- 조율자가 하위 작업 카드를 만들고 Herdr 메시지 기능으로 워커에게 위임한다. 조율자는 메시지로 진행을 확인하고 결과를 검수하며, 필요하면 오류 수정이나 추가 작업을 반복 요청한다.
- 구현 작업이 끝나면 조율자는 계획 카드를 Review로 전환한다. 사용자가 판단하기 전까지는 워커들이 해당 스페이스에 남아 있고 계획 카드는 Done이 아니다.
- 사용자가 완료를 승인하면 조율자에게 완료 지시를 내려 계획 카드를 완료 처리하고 스페이스를 종료한다.
- 사용자가 수정이 필요하다고 하면 조율자에게 수정 지시를 내린다. 계획 카드는 Review에서 Doing으로 돌아가고, 수정용 하위 작업 카드를 새로 만들어 기존 초대 워커들과 작업을 진행한다.
- workflow의 공식 이력 관리는 조율자가 맡는다. Herdr에는 실제 워커와 조율자가 주고받은 실행 대화 이력이 남고, 나중에 사용자가 해당 계획의 스페이스에서 확인할 수 있다.

### 평가

이 구성이 앞서 말한 목표와 잘 맞는다. **계획 카드가 사용자 승인과 스페이스 수명을 결정하고, 하위 작업 카드는 구현 단위이며, 조율자는 두 흐름을 연결하고 기록하는 책임자**가 된다. Herdr 스페이스는 계획 ID를 통해 실제 에이전트 협업 맥락을 모으는 역할을 한다.

특히 사용자 검수 후 수정이 발생할 때 기존 계획을 다시 열고 새 하위 작업 카드를 추가하는 방식은, 과거 구현과 새 수정 근거를 같은 계획에 연결하면서 수정 이력을 별도 작업 단위로 남길 수 있다. 완료 전에는 같은 스페이스와 워커 맥락을 재사용하므로 수정 때 협업 참여자를 다시 구성할 필요도 줄어든다.

### 제안된 상태 흐름

```text
계획 Doing
  ├─ 조율자 생성 → 하위 작업 카드 → Herdr 워커 위임/메시지/검수/수정 반복
  └─ 계획 범위의 구현 완료 → 계획 Review (Herdr 스페이스 유지, 워커 세션 유지)
       ├─ 사용자 승인 → 조율자 완료 처리 → 계획 Done → 스페이스 종료
       └─ 사용자 수정 요청 → 조율자 재개 → 계획 Doing
             → 새 수정 작업 카드 → 기존 스페이스 워커들에게 위임/검수 반복
             → 다시 계획 Review
```

하위 작업 카드의 완료가 곧 계획 완료를 뜻하지 않는다. 계획은 조율자 자체 검수와 사용자의 최종 확인을 거쳐야 Done이 된다. 계획 Review 상태에서도 워커 세션을 살아 있게 유지하는 것은 사용자가 빠르게 수정 요청을 보낼 수 있게 하지만, 유휴 세션의 비용·자원·보존 기간 정책은 별도 결정이 필요하다.

### 이력의 역할 구분

- **Herdr 스페이스:** 조율자와 워커가 실제로 주고받은 메시지 및 터미널 세션을 사용자가 확인하는 작업 공간.
- **Handrail 조율자 기록:** 계획/작업 카드 ID, 위임한 워커, 메시지 라운드의 요약·참조, 상태 전이, 산출물·diff·검증 결과, 사용자 검수와 수정 지시를 구조화해 남기는 workflow 기준 이력.
- **Vikunja 카드:** 계획 및 하위 작업의 상태·범위·완료 결과·리뷰 근거를 사람이 읽고 이어서 작업할 수 있게 남기는 프로젝트 이력.

원문 대화의 시각적/운영적 확인은 Herdr에서 제공하고, 장기적인 검색·workflow 감사 및 재개에 필요한 사건과 결과는 Handrail과 카드에 구조화해 남기는 구성이 적절해 보인다. 조율자가 메시지를 보내기만 하고 응답과 결론을 기록하지 않는다면 “workflow 이력 관리는 조율자”라는 요구를 만족하지 못한다.

### 구현 시 반드시 정할 세부 규칙

- `plan_id ↔ Herdr workspace_id`를 안정적으로 매핑하고, 이미 존재하는 스페이스를 재실행 시 재사용한다.
- 각 워커 초대와 하위 작업 위임을 해당 작업 카드 ID에 연결한다. 수정 요청은 이전 작업 카드를 덮어쓰지 않고 새 카드와 새 라운드로 기록한다.
- 워커가 스페이스에 남아 있다는 것과 에이전트 프로세스/세션이 계속 실행 중이라는 것을 구분한다. Review 중 세션 유지, 일시정지, 종료 후 재개 동작을 명시해야 한다.
- 계획 Done과 스페이스 종료는 사용자의 명시적 승인 뒤에만 실행한다. 수정 요청은 계획을 Doing으로 되돌리고 새 작업을 만든다.
- 대화 이력을 사용자에게 보여줄 수 있어야 하며, 실행 식별자와 메시지 라운드를 Handrail 기록에서 Herdr 세션/패널로 찾아갈 수 있어야 한다.
- 사용자 완료/수정 지시는 조율자에게 전달되는 명시적 이벤트로 모델링하고, 재시도나 중복 메시지가 중복 카드·상태 변경을 만들지 않도록 한다.

### 아직 결정되지 않은 점

- Review 단계에서 워커 프로세스/세션을 계속 살려 둘 것인지.
- 수정 요청을 어느 범위까지 같은 계획으로 유지할지, 새 계획 카드가 필요한 기준을 무엇으로 할지.
- 사용자는 조율자에게 어떤 UI/메시지 경로로 완료 또는 수정 지시를 내리는지.

### 대화 기록

- 사용자 제안: 실제 조율자/워커 메시지 이력은 Herdr 스페이스에서 확인하고, workflow 이력 관리는 조율자가 담당한다. 각 계획 ID에 대응하는 스페이스를 유지하고 워커와 메시지 기반으로 구현·검수·수정을 반복한다.
- 사용자 제안: 조율자 검수가 끝나면 계획을 Review로 넘기되, 사람이 승인하기 전에는 Done 처리하거나 스페이스를 닫지 않는다. 사용자 승인 시 조율자가 계획을 완료하고 스페이스를 종료한다.
- 사용자 제안: 사용자가 수정 요청을 하면 계획은 Review에서 Doing으로 복귀하고, 조율자가 신규 하위 작업 카드를 만들어 기존 스페이스의 워커들을 활용한다.
- 평가: 계획 카드를 사용자 승인 경계와 스페이스 생명주기의 기준으로 두고, 하위 작업 카드는 각 구현/수정 라운드의 이력으로 관리하는 구조가 자연스럽다. 실제 구현 전 Review 중 세션 보존/정지 정책과 조율자에게 완료·수정 지시를 전달할 경로를 결정해야 한다.

## 2026-10-02 — Review 중 에이전트 대화 이력 보존

### 사용자 확인

Review 단계에도 워커 프로세스들은 같은 Herdr 스페이스에 남아 있어야 한다. 그래야 사용자가 Herdr 터미널에서 에이전트들의 협업 이력을 직접 볼 수 있다. Herdr가 같은 스페이스의 에이전트 CLI 대화 이력을 저장하거나 내보내는 기능을 제공하는지도 확인이 필요하다.

### 현재 확인한 Herdr 동작

- Herdr는 `herdr agent read`와 `herdr pane read`로 패널의 보이는 화면 및 최근 터미널 출력을 읽을 수 있다. 현재 공식 문서는 idle 상태의 일부 인식된 alternate-screen 에이전트에 대해 transcript 화면을 스크롤해 더 많은 텍스트를 읽는 기능도 설명한다.
- Herdr 설정에는 실험적 pane screen history 저장 기능이 있다. 활성화하면 최근 pane 화면 내용을 `session-history.json`에 저장해 서버 재시작 후 복원할 수 있다. 이 기능은 기본 비활성화이며, pane 출력에 토큰·프롬프트·명령 출력 같은 민감한 내용이 들어갈 수 있어 주의가 필요하다.
- 이 기능은 터미널 화면/스크롤백 보존이지, 모든 에이전트의 내부 대화 transcript를 별도 파일로 완전하고 정규화된 형태로 내보내는 기능이라고 확인되지는 않았다. 에이전트가 alternate screen을 사용하거나 Herdr 세션이 재시작되는 경우, 보존 범위와 완전성이 에이전트·설정에 따라 달라질 수 있다.
- Herdr의 session snapshot은 workspace/tab/pane 레이아웃과 에이전트 세션 참조를 담지만 실행 중인 프로세스나 pane 화면 이력을 그 자체로 담지는 않는다. 따라서 “같은 스페이스가 남아 있음”과 “워커 프로세스가 계속 실행 중임”과 “대화 원문이 영구 보존됨”은 별도 속성으로 모델링해야 한다.

### 설계 반영

따라서 사용자 검수(Review) 중에는 계획에 묶인 Herdr 스페이스와 워커 세션을 유지하는 것을 요구사항으로 반영한다. Herdr의 pane history는 재시작 대비 보조 수단으로 검토하되, CLI 대화의 완전한 영구 보관/내보내기를 보장한다고 전제하지 않는다. 조율자는 Herdr 대화 이력을 그대로 확인할 수 있게 하고, Handrail은 주요 메시지 라운드와 workflow 결과를 구조화해 자체 기록에도 남겨야 한다.

실제 구현 시 다음 동작을 Herdr 버전과 Codex/Cursor 각각에서 확인해야 한다: Review 중 에이전트 프로세스 생존, 앱 내 transcript 탐색 가능성, `agent read`가 읽어오는 범위, pane history 재시작 복원, 세션 종료 후 다시 열람 가능한지.

## 2026-10-02 — Luna low 워커 메시징 실험

### 실험 구성

- Herdr `0.9.1`에서 기존 작업과 분리된 `handrail-messaging-test` 워크스페이스(`wE`)를 `/tmp` 경로로 만들었다.

- Herdr 호스트 조율자가 `herdr agent prompt luna-a ...` 및 `herdr agent prompt luna-b ...`로 각각 메시지를 보냈고, 두 워커 모두 각각 `LUNA_A_RECEIVED`, `LUNA_B_RECEIVED`라고 응답했다. `agent read`로 해당 답을 각자의 패널에서 다시 읽었다. 호스트 조율자 → 워커 → 패널 출력 회수 경로가 실제 동작함을 확인했다.
- luna-a에게 자기 Herdr CLI로 luna-b에게 메시지를 보내도록 시켰을 때, `herdr agent prompt luna-b ...` 호출은 `Cannot open audit interface - aborting`와 `PermissionDenied: Operation not permitted`로 실패했다. 따라서 워커가 서로 직접 Herdr CLI로 메시지를 전달하는 경로는 이 Codex 샌드박스에서는 동작하지 않았다.
- 앞선 진단의 “`HERDR_ENV`가 없다”는 결론은 새 실험에서 정정됐다. 새로 시작된 Luna 워커에는 `HERDR_ENV=1`이 있었다. 환경변수는 주입되지만 Codex 프로세스의 sandbox/seccomp 경계가 Herdr CLI의 audit/IPC 접근을 막는 것으로 보인다.
- Luna 워커가 `HERDR_ENV` 존재를 확인한 경로는 `rtk proxy env | rg '^HERDR_ENV='`였다. 화면의 Codex 상태에도 실제 선택 모델 `GPT-5.6-Luna low`가 나타났다. 워커가 `/status` 출력으로 reasoning effort를 별도로 확인하지는 못했으나, Herdr start argv에 low 설정을 전달했고 실행 상태 표시가 low였다.

### 아키텍처에 주는 결론

- Herdr 호스트 제어면을 사용할 수 있는 조율자는 에이전트를 시작하고 메시지를 보내며 응답을 수집할 수 있다. 이 실험에서는 조율자가 Herdr CLI를 직접 호출해 성공했다.
- 각 워커가 자기 샌드박스에서 Herdr CLI를 호출해 옆 워커를 직접 조율하는 구조는 권한 정책을 바꾸지 않는 한 사용할 수 없다.
- 초기 구현은 중앙 조율자가 모든 워커 간 메시지를 라우팅하는 구조로 설계할 수 있다. 이때 워커 응답은 Herdr 패널에서 읽고, 조율자가 다음 워커/라운드로 전달한다. 실제 Handrail 내 조율자 Codex 프로세스에서 이 제어면을 호출할 수 있도록 실행 경계/권한 설정은 별도 해결 과제다.
- 테스트 워크스페이스는 사용자가 터미널 대화 이력을 직접 확인할 수 있게 유지한다. 종료는 별도 요청이 있을 때 한다.

### 대화 기록

- 사용자 요청: 직접 Herdr를 실행해 GPT-5 Luna low 에이전트를 여러 개 불러 메시지를 보내 테스트한다.
- 실험 결론: 호스트 Herdr 조율자는 같은 테스트 워크스페이스의 두 Luna low Codex 워커에게 메시지를 보내고 응답을 읽을 수 있었다. 워커 내부에서 Herdr CLI를 이용한 워커 간 직접 메시징은 현재 Codex 샌드박스에서 차단된다.

- Herdr 조율자가 Codex에게 `CODEX_LUNA_LOW_RECEIVED`, Cursor에게 `CURSOR_AUTO_RECEIVED` 응답을 요청했고, 두 에이전트가 각각 그 문자열로 응답했다. 조율자가 `herdr agent read`로 두 패널의 응답을 회수했다.
- 화면상 Codex는 `GPT-5.6-Luna low`, Cursor는 `Auto`로 표시됐다. Herdr 에이전트 목록에서는 각각 `codex`, `cursor` 유형으로 인식됐다.
- 이 테스트도 워커가 직접 Herdr CLI를 호출한 것이 아니라 호스트 조율자가 Herdr 제어면으로 각 워커에 메시지를 보냈다. Cursor/Codex의 자체 Herdr CLI 권한 경계 테스트는 앞선 실험 결과를 따른다.
- 테스트 대화는 `handrail-codex-cursor-test` workspace에 남겨 두었다. 첫 `/tmp` trust-prompt 시도의 Cursor 패널은 별도 탭에 남아 있을 수 있으며, 실제 검증 응답에 사용된 것은 `cursor-auto-test` (`/tmp/handrail_cursor_auto_test`, `--trust --mode ask`)이다.

### 대화 기록

- 사용자 요청: GPT-5.6-Luna low와 Cursor Auto 두 에이전트를 이용해 메시징을 다시 시험한다.
- 사용자 관찰/수정: Cursor가 특정 경로를 신뢰하지 않아 대기하는 것으로 보이며, 실행 옵션을 확인해 재시도한다.
- 확인 결과: `--trust`가 Cursor CLI의 현재 workspace 신뢰 프롬프트를 건너뛰는 옵션이다. 격리된 전용 경로와 Ask 모드에서 적용해 두 에이전트의 메시지 송수신을 검증했다.

## 2026-10-02 — 사용자 수정 요청 시 워커 재구성

### 사용자 우려

사용자 리뷰에서 수정이 나오면 필요한 영역과 워커 수는 원래 계획과 다를 수 있다.

- 기존에 프론트엔드와 백엔드 워커 둘이 일했더라도, 이번 수정이 프론트엔드에만 해당하면 백엔드 워커는 더 이상 필요하지 않을 수 있다.
- 원래 프론트엔드만 작업했던 계획이어도, 검수 수정은 백엔드까지 영향을 줄 수 있어 워커를 추가해야 할 수 있다.
- 따라서 과거 워커 구성을 수정 라운드에 자동으로 그대로 복제하는 것은 부적절하다.

### 권장 모델: 계획 스페이스는 유지하고, 라운드별 워커는 재산정

사용자에게 “스페이스를 닫고 재시작해도 될까요?”라고 매번 묻는 것이 기본 흐름일 필요는 없다. 계획 단위의 Herdr 스페이스는 사용자 리뷰와 수정 이력을 보존하는 컨테이너로 유지하고, 각 수정 라운드마다 조율자가 수정 요청을 분석해 필요한 작업 카드와 워커를 다시 구성하는 편이 자연스럽다.

- 수정 범위가 프론트엔드만이면 새 프론트엔드 작업 카드와 해당 워커만 활성화한다.
- 수정 범위가 백엔드까지 넓어지면 해당 영역의 작업 카드 및 워커를 새로 추가한다.
- 이전 라운드에만 필요했던 워커는 기존 메시지·세션 이력을 보존하되, 새 라운드에는 참여시키지 않거나 유휴 상태로 둔다.
- 새 워커는 같은 계획 스페이스에 새 패널/세션으로 추가해 계획의 전체 협업 이력을 한 곳에서 볼 수 있게 한다.

즉 “같은 스페이스를 재사용”하는 것과 “같은 워커 집합을 유지”하는 것을 분리한다. 수정 라운드 전환은 스페이스 재시작이 아니라 **필요 인력/역할의 재구성**으로 모델링한다.

### 조율자의 자동 산정과 사용자 확인

수정 요청을 받은 조율자는 먼저 영향 범위를 분석하고, 작업 카드 초안과 필요한 역할/워커 수를 제안할 수 있다. 예를 들면 “프론트엔드 1개 작업, 백엔드 영향 없음, 기존 FE 워커 재사용” 또는 “API 계약과 화면 변경이 함께 필요해 FE/BE 작업 2개”처럼 제안한다.

- 낮은 위험이고 범위가 명확한 수정은 조율자가 자동으로 작업을 쪼개고 기존 적합 워커를 재사용할 수 있다.
- 새 워커 추가, 비용/시간이 큰 병렬 작업, 범위가 불명확하거나 충돌 위험이 있는 경우에는 조율자가 산정 근거와 선택지를 사용자에게 보여주고 확인을 받는다.
- 사용자는 제안된 작업 분해·워커 수를 승인하거나 조정할 수 있다. 승인이 필요한 경계는 위험도, 추가 비용, 사용자 정책으로 설정 가능해야 한다.
- 워커 수는 독립적으로 진행 가능한 작업 단위와 전문성에 따라 정한다. 단순히 워커를 많이 두는 것이 병렬성이나 품질을 높인다고 가정하지 않는다.

### 상태와 이력의 제안

사용자 수정 지시가 들어오면 계획 카드는 Review에서 Doing으로 돌아간다. 조율자는 수정 라운드 ID를 만들고, 수정 사유·영향 분석·새 작업 카드·참여 워커를 연결한다. 수정 작업이 조율자 검수를 통과하면 계획은 다시 Review로 이동한다. 최종 승인 전까지 계획 스페이스는 유지된다.

스페이스 컨테이너의 종료 시점은 기존 계획의 최종 승인/취소 시점으로 두는 것이 수정 이력 가시성에 유리하다. 단, 실행 중이지 않은 에이전트 프로세스는 정지/종료할 수 있으며, 이는 스페이스와 기록을 닫는 것과 별개로 다뤄야 한다. 사용자가 보존 비용이나 보안 때문에 전체 스페이스 종료를 원할 때만 별도 확인을 고려한다.

### 사용자 질문에 대한 현재 결론

수정이 발생할 때마다 스페이스 종료 여부부터 묻는 것보다는, 조율자가 수정 영향과 워커 수를 먼저 산정해 제안하는 방식이 좋다. 기본은 계획 스페이스를 보존하면서 필요한 워커만 활성화/추가하고, 결정에 영향이 큰 경우에만 사용자에게 작업 분해와 리소스 구성을 확인받는다.

### 남은 정책 질문

- 워커 추가나 병렬 분할 때 항상 사용자 승인을 받을지, 특정 작업 위험도/비용 기준부터 승인받을지.
- 기존 워커를 재사용할 때 해당 에이전트 세션의 문맥을 이어갈지, 같은 역할의 새 세션을 열고 관련 카드/결정만 전달할지.
- 계획 최종 완료 후 Herdr 스페이스를 닫되, 터미널 이력/구조화 로그는 얼마 동안 보존할지.
- 조율자가 수정 요청에 대해 영향 분석을 자신 있게 할 수 없을 때, 자동 분할 대신 사용자에게 범위 질문을 먼저 할 기준은 무엇인지.

### 대화 기록

- 사용자 질문: 사용자 리뷰 후 수정이 필요한 경우 필요한 워커 수와 역할은 원래 계획과 달라질 수 있다. FE만 고치면 되는 경우 기존 BE 워커는 불필요하고, FE 계획도 BE 수정이 추가되면 워커가 더 필요할 수 있다. 이때 스페이스를 닫고 재시작할지 사용자에게 물을지, 조율자가 필요한 워커 수를 산정할 수 있을지 검토 요청.
- 제안: 계획 스페이스는 이력 컨테이너로 유지하고 수정 라운드마다 범위·작업 카드·워커 구성을 재산정한다. 조율자는 근거가 포함된 워커/작업 분할안을 제안하고, 비용·위험·모호성이 큰 경우 사용자 확인을 받는다.

## 2026-10-02 구현 범위 확정 — 이전 제안보다 우선

사용자가 이번 개발의 핵심과 실행 시나리오를 구체화했다.

- Handrail 조율자가 계획 카드를 관리하고, Herdr space 안의 워커에게 개발을 의뢰하며 메시지로 지휘한다.
- 배정, 착수, 수정 지시, 조율자 검토 및 통합, 완료 등 의미 있는 행위는 부모 계획 카드 댓글에 남긴다. 반복적인 상태 조회는 제외한다.
- 공간 이름은 소스 디렉터리 이름 (계획 카드 ID), 워커 이름은 작업 카드 ID를 기준으로 한다.
- recommend 정책은 이번에 c만 구현한다. 사용자에게 카드별 에이전트/provider/model 지정 방법과 예시 프롬프트를 안내한다. 자동 추천 승인(a), 자동 배정(b)은 이번 범위에서 제외한다.
- Review 동안 워커 프로세스와 공간을 유지한다. 사람이 Done을 지시하면 계획을 완료하고 공간을 닫는다.
- 수정 요청 시 계획은 Review→Doing, 추가 변경은 새 작업 카드로 기록한다. 완료된 과거 작업 카드를 재사용하지 않는다.
- 수정 시 공간 clear 여부를 묻는다. 프로젝트 설정 clear_on_reopen 기본값은 ask이며 always/never로 확장할 수 있다. 무응답은 승인으로 취급하지 않는다.
- 테스트 대상: 포트 58821의 handrail_v0.5 및 frontend/backend 하위 보드. Express 사원 CRUD API와 웹 UI를 Cursor Auto 두 워커로 개발한다. Done과 수정 재개를 각각 검증한다.
- 반복 테스트에서는 테스트 바인딩을 해제하고 지정 프로젝트의 하위 테스트 보드만 정리한다. 관련 없는 프로젝트는 대상이 아니다.
- 구현 보조 에이전트는 사용자가 지정한 GPT-6-LUNA low를 사용한다.

구현 브랜치: support-herder. 테스트 설계와 실제 관측 결과는 docs/testing/herdr-acceptance.md에 구분하여 기록한다. 토큰은 문서나 구현에 기록하지 않는다.
