# 프로젝트 관리 workflow와 용어

상태: 제품 정책. 부모 보드의 계획 카드가 목표·범위·완료 기준을 관리한다. 추가 구현이나 보완이 필요하면 기존 완료 카드를 재사용하지 않고 새 작업 카드로 기록한다. 실제 명령과 현재 범위는 [사용 설명서](../../docs/manual.md)와 [구현 현황](../../docs/status.md)을 따른다.

## 1. 핵심 규칙

- Git 저장소 하나에는 Vikunja 부모 프로젝트 하나만 바인딩한다. 한 호스트에서 여러 저장소를 관리하면 각 저장소가 자기 부모 프로젝트를 가진다.
- 부모 프로젝트 아래의 하위 프로젝트·보드는 필요할 때 workspace에 명시적으로 등록한다. Vikunja에서 보인다는 이유만으로 모든 하위 프로젝트를 자동 관리 대상으로 삼지 않는다.
- 계획 카드는 부모 프로젝트에 두고, 구현·조사 작업 카드는 적절한 등록 하위 보드에 둘 수 있다.
- 모든 요청은 계획 카드로 관리한다. 추가 작업이 필요하면 그 계획에 연결된 새 작업 카드를 만든다. 부모 프로젝트만으로도 이 정책을 따를 수 있으며 하위 보드는 선택 사항이다.
- 하위 보드 작업 카드는 실행 상태와 이력을 보존한다. Review 열은 필요하지 않으며 Todo/Doing/Done만 필수다. 계획 카드의 Review는 사용자 검토 단계로 유지한다.
- 보드 소속과 카드 간 작업 관계는 서로 다른 정보다. 작업 카드는 계획 카드의 **실제 하위 task 관계**로 연결되어야 한다. 다른 보드에 있다는 이유만으로 계획의 하위 작업이라고 추정하지 않는다.
- Handrail이 카드 상태를 기본 관리한다. 사람이 Vikunja에서 상태를 직접 바꾸면 이를 외부 변경으로 감지하고 자동으로 덮어쓰지 않는다.
- 작업 카드는 작업자 CLI의 종료만으로 완료하지 않는다. 조율자가 결과를 검수하고, 필요한 변경을 통합하고, 통합된 결과를 검증한 다음 완료 처리한다.
- 계획 카드는 필수 작업 및 최종 검증이 완료되면 Review로 제출한다. 사용자의 검토가 끝나기 전에는 Done으로 바꾸지 않는다.
- Review 이후 수정 작업은 항상 새 작업 카드로 추가한다. 완료된 작업 카드는 이력으로 보존하고 다시 열어 재사용하지 않는다.

## 2. 용어 사전

| 용어 | 뜻 | 구분해야 할 점 |
| --- | --- | --- |
| Handrail 프로젝트 / workspace | Git 저장소, Vikunja 연결, 명세, 작업 이력을 묶는 관리 단위 | Vikunja 프로젝트 하나와 같은 말이 아니다. |
| 부모 프로젝트 | workspace가 바인딩하는 유일한 최상위 Vikunja 프로젝트와 기본 보드 | 한 저장소의 기준 프로젝트다. 다른 저장소는 다른 부모 프로젝트를 바인딩할 수 있다. |
| 하위 프로젝트 / area / 하위 보드 | 부모 프로젝트 아래에 두고 workspace에 명시적으로 등록한 컴포넌트 프로젝트와 Kanban 보드 | 계획 카드의 하위 task 관계와 동일한 개념이 아니다. |
| 계획 카드 (요구사항 카드) | 사용자의 목표, 범위, 제약, 완료 조건을 담는 상위 카드 | 아이디어·요구사항을 실행 계획으로 합의한 뒤 작업 카드들을 소유한다. |
| 작업 카드 | 계획 카드의 하위 task 관계로 연결된 구체적인 구현·조사·문서화 작업 카드 | 하위 프로젝트 보드에 있을 수 있지만, 카드 관계도 별도로 연결해야 한다. |
| 하위 task 관계 | Vikunja에서 작업 카드를 계획 카드에 자식으로 연결하는 관계 | 단순 관련 카드 링크, 같은 프로젝트 소속, Handrail 내부 참조와 혼동하지 않는다. 대상 서버 API가 교차 프로젝트 관계를 허용하는지 검증해야 한다. |
| 조율자 (orchestrator) | 사용자와 대화하고 범위를 합의하며 작업자 실행, 검수, 통합, 검증, 카드 동기화를 책임지는 에이전트 | 현재 기본 조율자는 Codex다. Vikunja 관리자 토큰을 작업자에게 넘기지 않는다. |
| 작업자 (worker / 구현 CLI) | 조율자가 위임한 단일 작업을 격리된 작업공간에서 수행하는 Codex CLI 또는 Cursor CLI | 작업자 완료 응답은 결과 제출이지 Vikunja 카드 완료 권한이 아니다. |
| 로컬 통합 | 검수된 작업 변경을 사용자의 checkout에 적용하는 단계 | Git remote push, PR, 원격 병합을 뜻하지 않는다. |
| 통합 검증 | 전체 변경을 최종 통합한 상태에서 승인된 자동·수동 검사를 수행해 증거를 남기는 단계 | 각 작업을 개별 검증한 기록만으로 대체할 수 없다. |
| Review (계획 카드) | 조율자가 전체 결과와 검증 근거를 제출해 사용자의 제품 검토를 기다리는 상태 | 작업자 코드 리뷰와 같은 말이 아니다. 계획 카드는 이 상태에서 `done=false`여야 한다. |
| Done (작업 카드) | 조율자가 검수·통합·검증을 마친 작업 카드의 완료 상태 | 작업자 CLI의 종료 직후 자동으로 설정하지 않는다. |
| Done (계획 카드) | 사용자가 Review 결과를 확인하고 최종 완료를 결정한 상태 | 사용자가 직접 설정하거나, 사용자의 명시적 대화 지시를 받은 조율자가 설정한다. |
| Review 회차 / 제출 기록 | 계획 카드가 Review로 제출된 시점의 계획 개정, 하위 작업 집합, 통합 commit/fingerprint, 검증 결과를 묶은 불변 기록 | 이후 새 작업이 추가되어도 과거 제출 기록을 덮어쓰지 않는다. |
| 외부 상태 변경 / 강제 전환 | Handrail 동기화 밖에서 사람이 Vikunja UI/API로 카드 상태를 변경한 사건 | 자동으로 원복하지 않는다. 재조회 후 조율자가 사용자의 의도에 맞춰 동기화한다. |

## 3. 정상 개발 workflow

### A. 프로젝트 연결과 보드 범위

1. 현재 Git 저장소를 확인하고 기존 Vikunja 부모 프로젝트 하나에 바인딩한다.
2. 하위 프로젝트를 추가로 관리할 필요가 있으면 조율자가 현재 workspace의 부모 아래에서만 보드를 확인·등록한다.
3. 부모 보드는 Todo/Doing/Review/Done을 사용하고, 하위 보드는 Todo/Doing/Done을 필수로 하며 Review는 선택 사항으로 저장한다.
4. 다른 workspace의 부모·하위 보드를 자동으로 가져오거나 섞지 않는다.

하위 프로젝트 생성 및 기존 보드 등록은 [PROJECT_HIERARCHY.md](PROJECT_HIERARCHY.md)의 operation·권한·복구 규칙을 따른다.

### B. 계획과 작업 카드 구성

1. 조율자는 사용자의 아이디어를 계획 카드로 식별하고, 목표·범위·제약·완료 조건·검증 방법을 합의한다.
2. 필요하면 계획 카드를 부모 프로젝트에 생성한다. 사용자가 준 기존 카드가 있으면 그 카드를 사용한다.
3. 조율자는 작업을 구현 가능한 단위로 나누고 각 작업을 적절한 등록 하위 보드에 생성한다. 하위 보드가 불필요하면 부모 보드에 둘 수 있다.
4. 각 작업 카드를 계획 카드에 실제 하위 task 관계로 연결한다. 카드 생성만 성공하고 관계 설정에 실패한 경우 전체 작업이 완료된 것처럼 보고하지 않는다.
5. 작업 카드에는 담당 worker/provider/model, 선행 조건, 산출물, 완료 검증 기준을 기록한다. 계획에는 필수 작업 목록과 개정 번호를 고정한다.

### C. 작업 실행·검수·완료

1. 조율자는 작업 카드와 승인된 계획/명세를 확인한 후 작업자를 선택한다. 같은 Git 저장소에는 활성 write run 하나를 허용하므로 기본 실행은 순차적이다.
2. Handrail은 작업 시작을 기록하고 해당 작업 카드를 Doing으로 이동한다.
3. 작업자는 격리된 worktree에서 구현하고 결과를 제출한다. 작업자 스스로 카드를 Done으로 이동하지 않는다.
4. 조율자는 실제 diff, 결과물, 명세 및 작업별 검증 결과를 확인한다. 실패하면 새 작업자 실행으로 수정한다.
5. 승인 가능한 작업은 로컬 통합한다. 모든 필수 작업을 순차 통합한 뒤 최종 통합 상태에서 계획의 전체 검증을 다시 수행한다.
6. 검수·통합·검증이 통과한 작업 카드를 Done으로 이동하고 근거를 남긴다. 일부 원격 쓰기가 실패하면 현재 상태를 다시 읽고 operation 기록을 따라 복구한다.

조사·분석처럼 코드 변경이 없는 작업도 승인된 완료 기준, 결과물, 검수·검증 기록이 필요하다. 통합 단계에서 변경이 없음을 확인해 `no_change`로 기록하며, 불필요한 Git 커밋은 생성하지 않는다.

### D. 계획 카드 Review 제출과 사용자 결정

1. 계획에 고정된 필수 작업들이 모두 완료 상태이고, 각 완료 근거가 현재 계획 개정과 연결되어야 한다.
2. 최종 통합 상태의 종합 검증이 최신 fingerprint에서 통과해야 한다. 미완료·삭제·접근 불가 작업, 실패한 검사, 검증 후 변경이 있으면 제출을 막는다.
3. 조율자는 계획 카드에 구현 요약, 검증 근거, 통합 식별자, 사용자가 확인할 방법을 기록한다.
4. 조율자는 계획 카드를 Review로 이동하고 해당 제출 회차를 불변 기록으로 남긴다. 계획 카드는 Done이 아니다.
5. 사용자는 실제 동작을 확인한 뒤 직접 Done으로 표시하거나, 대화에서 조율자에게 명시적으로 Done 처리를 지시한다.
6. 조율자는 상태 변경 직전에 원격 상태를 읽고, 사용자 확인과 계획 카드 identity가 맞는지 확인한 뒤 반영한다.

### E. Review 이후 오류·개선 요청

사용자가 Review 결과에 수정이나 개선을 요청하면 기존 완료 작업 카드를 다시 열지 않는다.

1. 조율자와 사용자는 기존 계획을 개정할지, 별도 후속 계획 카드를 만들지 결정한다.
2. 같은 계획을 보완한다면 새 계획 개정/Review 회차를 시작하고 계획 카드는 Doing으로 되돌린다. 별도 요구사항이면 새로운 계획 카드를 만든다.
3. 수정·개선 내용마다 새 작업 카드를 생성해 적절한 등록 보드에 배치하고 원래 계획 카드의 하위 task 관계로 연결한다.
4. 기존 완료 작업과 Review 제출 기록은 보존한다. 새 계획 개정에서 영향을 받는 기존 완료 근거만 stale 처리한다.
5. 새 작업 실행 후 전체 통합 상태를 다시 검증하고, 계획 카드를 새 Review 회차로 제출한다.

새 계획 카드로 분리한 후속 작업은 원 계획의 Review/Done 이력을 보존하면서 후속 관계를 기록한다. 기존 계획을 수정한 작업과 별도 후속 요구사항을 한 카드에 혼합하지 않는다.

## 4. 사람이 Vikunja에서 상태를 직접 바꾼 경우

Handrail은 상태 변경 전에 기대한 현재 상태와 Vikunja의 최신 상태를 비교한다. 값이 다르면 자동으로 쓰지 않고 `external_change` 충돌을 기록한다.

조율자는 카드 ID, 보드, 이전 Handrail 기록, 현재 원격 상태, 진행 중인 계획/작업/Review 회차에 미치는 영향을 보여주고 다음 중 선택 가능한 조치를 안내한다.

- **사람의 변경을 채택:** 현재 Vikunja 상태를 새 기준으로 기록한다. 이 상태가 workflow 조건과 맞지 않으면 계획/작업을 차단 또는 재개 상태로 표시한다.
- **Handrail 상태를 다시 적용:** 왜 기존 workflow 상태가 맞는지 설명하고 목표 상태를 미리 보여준 뒤, 사용자가 승인하면 조건부 상태 변경을 수행한다.
- **작업을 새로 계획:** 직접 전환으로 생긴 상태가 기존 작업 흐름과 모순되거나 추가 구현이 필요하면 계획을 보완하고 새 작업 카드를 만든다.

“동기화”는 외부 상태를 다시 읽어 조율 기록을 맞추는 **가져오기**와, 사용자가 선택한 목표로 Vikunja 상태를 바꾸는 **적용**을 구분한다. 가져오기는 읽기 동작이며, 적용은 충돌과 목표 상태를 사용자에게 알린 뒤 수행한다. 오래된 run/operation 재시도가 사람의 Done, 재오픈 또는 다른 상태를 자동으로 덮어쓰면 안 된다.

## 5. 상태 전이 요약

| 카드 | 진행 중 | 조율자/시스템 완료 조건 | 사용자 단계 |
| --- | --- | --- | --- |
| 계획 카드 | Doing | 필수 작업 전체 완료 + 최종 통합 검증 통과 시 Review 제출 | 실제 결과 검토 후 Done 또는 새 수정 작업 요청 |
| 작업 카드 | Doing | 조율자 검수 + 필요한 통합 + 현재 결과에 대한 검증 통과 시 Done | 보통 개입 불필요. 수정이 필요하면 새 작업 카드를 요청 |

표는 기본 자동화 정책이다. 사용자의 직접 Vikunja 변경은 위 전이를 자동 실행하지 않고 외부 상태 변경 절차를 따른다.

## 6. 필요한 이력과 안전 조건

- workspace의 부모 binding 하나, 명시적 area allowlist, 각 area의 상태 매핑 및 binding revision
- 계획 카드와 작업 카드의 Vikunja identity 및 실제 하위 task 관계
- 계획 개정, 필수 작업 목록 snapshot, 각 카드 역할과 담당 worker/run
- 검수 결과, 통합 대상, 최종 통합 HEAD/fingerprint, 자동·수동 검증 evidence
- Review submission ID/회차, 제출 당시 하위 작업 집합 및 사용자 결정
- 상태 변경의 expected state, operation ID, 원격 재조회 결과, 사람이 선택한 reconciliation 조치

Vikunja task relation의 교차 프로젝트 허용 여부와 API/token scope는 대상 인스턴스 계약에서 먼저 검증한다. 하위 프로젝트 접근 가능성만으로 task 관계 생성 권한이 있다고 가정하지 않는다. 생성·관계 연결·상태 이동의 각 단계는 멱등 operation으로 기록하고, 불확실한 결과에 POST/PUT을 무조건 반복하지 않는다.

## 7. 인수 기준

1. 저장소는 부모 프로젝트 하나에 바인딩되고, 부모 아래 명시 등록된 하위 보드만 작업 대상으로 사용한다.
2. 하위 보드의 작업 카드는 실제 계획 카드의 하위 task 관계를 가지며 관계 실패가 누락된 채 성공으로 보고되지 않는다.
3. 작업자 종료만으로 작업 카드가 Done이 되지 않는다. 조율자의 검수·통합·검증이 필요하다.
4. 모든 필수 작업과 최종 통합 검증이 통과한 경우에만 계획 카드가 Review로 제출되고 `done=false`로 남는다.
5. 사용자의 명시적 결정 없이 계획 카드가 Done으로 전환되지 않는다.
6. Review 이후 수정은 새 작업 카드를 추가하고 이전 카드·Review 회차 이력을 보존한다.
7. 사람이 상태를 강제 전환하면 감지·비파괴 충돌 처리·가져오기/적용 선택을 제공하며 자동 원복하지 않는다.
8. 네트워크 실패 뒤 재시도, 동시 조율자, 접근 철회, 카드 삭제, 검증 후 코드 변경이 중복 카드나 오래된 Review 제출을 만들지 않는다.
