## 추가 콘솔 근거 — 같은 run의 새 복구 검증 스크립트 승인

사용자 제공 로그에서 #9의 동일 run `616ed95ab13d` 결과를 이어 검토하던 조율자가 `rtk node /tmp/handrail-review-quiz-recovery.cjs /home/dyhwang23/.local/share/...` 실행에 대해 다시 ‘항상 허용’을 받았다. 이전 독립 검증은 `handrail-review-quiz.cjs`였고 이번 파일은 채점 직후 저장소 오류에 대한 재시도 검증용으로 설명됐다.

- **확인 사실:** worker 재실행이나 새 run 생성 없이 같은 결과를 추가 검증하는 단계에서도 실제 사용자 승인이 있었다. 동일 run에 대해 앞선 기록과 합쳐 최소 네 번의 승인 상호작용(Handrail 시작 동의, 복구 준비, 독립 검증, 추가 복구 검증)이 사용자 제공 로그에 나타난다.
- **제한:** 새 스크립트명은 확인되지만 이전 허용 규칙 전문, 신규 검증의 전체 명령 인자와 실행 권한 차이는 이 발췌에 없다. 단순 파일명 변경이 유일한 원인이라고 단정하지 않는다. 이번 검증의 실행 결과도 발췌에 없다.
- **설계 반영:** 프로젝트 검증 정책은 최초 테스트뿐 아니라 위임 범위 안의 오류 재현·추가 회귀·복구 검증도 다룬다. 새 검증 스크립트가 기존 경로·프로세스·네트워크 권한 안에서 동작하면 재승인을 요구하지 않는 방향을 검토한다. 검증 내용과 코드 fingerprint는 새로 기록하며 새 외부 접근 등 권한 확대가 있을 때만 추가 동의를 받는다.
- **회귀 후보:** 같은 run의 검수 도중 검증 스크립트를 추가하고 조율자 세션을 재개해도 기존 프로젝트 권한이 유지되는지 확인한다. 세션 중단과 승인의 직접 인과관계는 이 로그만으로 확정하지 않는다.

HR-NEXT-005/007/009/011의 연결 근거로 수집한다. 개발 범위는 미확정이다.

보고된 worker 테스트 통과 뒤 조율자가 독립 검증하는 단계까지 같은 위임 범위에서 준비되어야 한다. 권한 표는 worker 구현뿐 아니라 준비 주체와 조율자 검증 주체를 포함한다. 이 사례는 승인 재사용, 의존성 복원, 독립 검증을 연결한 수용 시나리오 후보다. 구현·배포 범위는 아직 확정하지 않는다.

## 세 번째 피드백 — 작업 #8 수정 라운드의 실행 패킷 충돌

사용자 제공 로그: `run review --verdict revise` 이후 `run revise 32d508f90f02`가 running을 반환했으나, 후속 inspect에 `Supervisor failed: Refusing to overwrite existing CONTEXT.md`가 표시됐다. recover는 failed 및 worktree_preserved=true를 반환했다. 이 로그에서 수정 실행의 추가 authorize 요청은 없었다.

코드 대조(실행 재현 아님):

- `run_workflow.revise()`는 같은 worktree를 사용하며 round를 올린 뒤 running으로 전환하고 supervisor를 시작한다.
- `_write_packet()`은 이전 RESULT.md/result.json/journal.md를 제거하지만 CONTEXT.md는 남긴 채 `context_packet.write_context()`를 호출한다.
- `write_context()`는 O_EXCL로 파일을 생성하므로 기존 CONTEXT.md가 있으면 로그와 같은 오류를 발생시킨다.
- 패킷 작성은 worker 실행보다 앞선다. 따라서 해당 오류는 Cursor의 구현 실패와 구분해야 한다.
- 현행 recover는 failed 상태의 worktree 보존을 알리지만 이 준비 오류를 수정하거나 worker를 다시 시작하지 않는다.

후보: HR-NEXT-010에 회차·시도별 패킷 관리와 준비 단계 실패 복구를 추가하고, HR-NEXT-008에서 supervisor 시작과 worker 시작을 구분한다. 경로·symlink 보호와 이전 회차 이력을 유지한다. revise/resume/준비 도중 실패/첨부파일 포함/중복 요청을 향후 회귀 시나리오로 수집한다.

추가 관찰:

- 브라우저 재현 스크립트·증거가 /tmp에 있다. 해당 증거가 worker에게 실제 전달됐는지는 미확인이다. 후속 실행의 허용 경로 안에 검증 스크립트·환경·코드 fingerprint·결과를 연결하는 방안을 검토한다.
- 사용자 프로젝트의 지연 응답·입력 차단 오류 자체는 Handrail 결함과 구분한다. Handrail의 과제는 그 재현 근거를 수정 작업과 검증에 전달·보존하는 것이다.
- 주간 사용량 경고가 있었으나 한도 때문에 실패했다는 증거는 없다. 사용량 한도에 따른 중단·재개는 HR-NEXT-011의 후보로 유지한다.
- 향후 작업 Done 이후 수정은 신규 카드 정책을 따른다. 현행 RC4 revise 결함의 복구와 앞으로의 카드 정책 변경을 구분한다.

- **승인 출처 분리:** `authorize …`는 Handrail의 one-run 동의이며, `git add/commit`, `ps`, 의존성 복사, `node --test`에 표시된 승인은 조율자 호스트의 도구 실행 승인이다. 계획 위임만으로 후자를 해결할 수 없다. 준비 단계에서 필요한 명령·경로·네트워크를 명시하고 호스트가 지원하는 범위의 정책 설정을 안내한다. 광범위한 명령 접두사 허용을 해결책으로 삼지 않는다.
- **복수 계획 일괄 위임:** 이번 요청은 계획 #4–#6과 작업 #7–#12를 포함한다. 단일 계획뿐 아니라 명시적으로 나열한 계획·회차를 한 번에 확인할 수 있도록 설계한다. 무제한 프로젝트 전체 승인은 피하고 각 run의 위임 출처와 범위를 유지한다.
- **의존성·검증 사전 준비:** 새 worktree에 `node_modules`가 없어 실행 중 조율자가 복사했다. 실행 전에 lockfile·패키지 관리자·캐시·설치 네트워크·테스트의 로컬 리슨 및 쓰기 경로를 점검한다. 의존성 복사 가능 여부와 재현성은 별도로 검증하며 무조건 복사하지 않는다. 기본 테스트 실패 원인은 로그만으로 확정하지 않는다.
- **실행 관측 개선:** 반복 `run inspect`의 로그 꼬리가 비어 있고 조율자가 `ps`와 런타임 소스를 직접 조회했다. 현재 `workers.execute()`는 `communicate()` 완료 후 출력 파싱을 하므로 실행 중 이벤트가 노출되지 않는다. 비밀정보를 제거한 진행 이벤트, 마지막 활동 시각, 실행 단계, 결과 제출 여부, 경과 시간, 다음 권장 행동을 제공한다. 프로세스 생존과 실제 진척을 구분하며 무출력만으로 강제 종료하지 않는다.
- **결과 제출의 확정 시점:** `result.json` 작성 후에도 프로세스가 살아 있었고 코드가 변경됐다. 파일 존재만으로 완료 판정하지 않는다. provider 완료 신호·프로세스 종료·산출물 검증·코드 fingerprint로 최종 제출을 확정하고 그 시점을 작업 Done의 기준으로 삼는다. 비정상 종료 시 보존·복구 경로를 제공한다.
- **작업 중 검수와 수정 경계:** 실행 중인 worktree를 조율자가 변경하거나 그때의 테스트를 최종 검증으로 재사용하지 않도록 한다. 읽기 검토는 잠정 결과로 표시하고 제출이 확정된 코드에 검증 근거를 고정한다. 완료한 작업에서 발견한 결함은 새 하위 작업으로 연결한다.
- **도움말·진단:** 승인 미리보기 저장 위치, 실행 단계별 명령, 환경 준비 상태와 복구 방법을 CLI에서 제공해 `/tmp`에 수동 미리보기를 만들거나 내부 Python 소스를 읽는 필요를 줄인다. `Cannot open audit interface`는 원인 미확정 환경 진단 항목으로 기록한다.

회귀 시나리오: 복수 계획·Codex/Cursor 작업을 위임한 뒤 환경 준비부터 결과 수집까지 진행한다. 범위 내 반복 승인, 의존성 누락, 장시간 무출력, 결과 파일 작성 후 추가 변경, 테스트 실행 제약을 각각 재현하고 사용자 Review 이전에 멈추는 이유가 명확히 표시되는지 확인한다.

### 추가 피드백: 결과 형식 실패와 재실행 준비 오류

근거: 동일 작업 #7의 후속 콘솔 발췌. 최초 결과 JSON과 재실행용 임시 스크립트 전문은 제공되지 않았으므로 구체적인 형식 오류와 파일 준비 실패 원인은 미확정이다.

- **결과 계약 지원:** 실행 패킷에 결과 스키마·템플릿을 제공하고 워커가 제출 전에 검사할 수 있게 한다. 오류는 필드 경로·기대 형식·수정 방법으로 반환한다. 형식 실패와 구현/검증 실패를 구분한다. 보고서 형식만 잘못됐다면 코드를 보존한 채 제한적으로 제출을 복구하며, 실행하지 않은 검증이나 성공 상태를 만들어내지 않는다.
- **재실행 준비를 제품 기능으로:** 임시 Python 스크립트가 워커를 먼저 실행하고 소스·의존성을 복사한 뒤 `seed-ready.json`을 쓰는 흐름에서 FileNotFoundError가 발생했다. 정식 복구 경로는 이전 실행 종료 확인 → 복구 스냅샷·파일 해시 기록 → 새 worktree 및 의존성 준비 → 입력 검증 → 워커 시작 순으로 구성한다. 준비 실패 시 워커를 시작하지 않는다. 스냅샷은 원본 run과 연결하고 이전 실행의 보고서·승인 메타데이터를 새 실행의 근거로 복제하지 않는다.
- **승인 범위의 복구 입력 고정:** 보존 초안과 복구 지침도 실행 입력에 포함해 해시로 고정한다. 같은 위임 범위 안의 실패 재시도는 상위 위임을 사용하고, 입력·권한 범위가 확대되면 변경분을 확인한다.
- **확인 코드 UX:** 로그에서는 코드 마지막 문자가 빠졌으나 대화상 동의로 처리했다. 코드는 인증 수단이 아니며 실제 사용자 동의와 실행 요청 연결이 핵심이다. 자연어 동의 처리 조건과 복수 미리보기의 모호성 처리 규칙을 명확히 하고 실제 사용자 답변을 그대로 보존한다. 정확한 코드 입력을 요구하는 화면과 자동 보정 동작이 모순되지 않게 한다.
- **실패 후 상태 명확화:** 복구 스크립트 실패가 이미 시작한 워커의 종료를 의미하지 않는다. 관리 명령으로 준비 단계·워커 생존·최종 상태를 함께 보여주고, 준비 실패의 정리·중단·재개를 중복 없이 처리한다. 현재 로그의 빈 꼬리 출력만으로 실행 성공이나 중단을 단정하지 않는다.

추가 회귀 시나리오: 잘못된 결과 필드의 진단 및 제한적 복구, 준비 도중 실패 시 워커 미기동, 기존 프로세스 생존 시 중복 실행 차단, 복구 입력 변경 감지, 동일 위임 내 재시도, 불완전한 확인 코드와 여러 대기 요청의 구분. Done 이후의 수정은 신규 작업 카드로 만들되 제출 전 실패 재시도는 동일 카드의 시도 이력으로 보존한다.
