## HR-NEXT-012 — 새 저장소 초기 설정의 사전 점검·오류 복구

근거: 사용자가 v0.4를 새 프로젝트에 적용하며 공유한 로그에서 다음 절차 실패가 확인됐다.

- 플러그인 캐시 경로를 고정 경로로 추측해 `SKILL.md` 조회가 실패했다. 실제 설치에는 중첩된 `handrail/handrail/0.4.0/...` 경로가 있었다.
- `.agents/AGENTS.md`가 있다고 가정해 읽기를 시도했지만 대상 저장소에는 파일이 없었다.
- 두 실패가 `&&`로 연결돼 있어 경로 하나가 틀릴 때마다 나머지 독립 점검도 실행되지 않고, 여러 차례 수동 경로 수정이 필요했다.
- 마지막 CLI 호출도 종료 코드 2와 도움말 일부만 보여 초기화/연결/설정의 다음 단계가 분명하지 않았다.

개선 후보:

1. Handrail 스킬/플러그인 리소스는 고정 설치 경로를 전제하지 않고, 플러그인 메타데이터·실제 설치 위치를 우선 사용한다. 없거나 여러 개면 검색 결과와 선택 기준을 진단에 표시한다.
2. 저장소 루트와 Git 상태를 먼저 확정하고, `AGENTS.md`, `.agents/AGENTS.md`, README 등 선택적 문서는 존재 여부를 확인한 뒤 읽는다. 파일 부재는 오류로 처리하지 않는다.
3. 독립적인 읽기 전용 점검은 한 단계의 실패로 중단하지 않도록 수행하고, 결과를 존재/부재/실패로 구분해 요약한다. 실제 setup이나 Vikunja 쓰기 전에는 필요한 입력·대상·변경을 안내한다.
4. 초기 설정 명령은 실패 시 실제 사용 가능한 명령과 복구 절차를 출력한다. `help`/`status` 같은 진단과 외부 상태 변경을 일으키는 setup 동작의 종료 코드·효과를 명확히 구분한다.

수용 기준 후보:

- 설치 경로가 중첩되거나 버전 디렉터리가 바뀌어도 번들된 스킬과 CLI를 찾아 안내한다.
- 선택 저장소에 선택 문서가 없어도 저장소 식별·상태 확인 및 나머지 진단을 계속한다.
- 읽기 전용 사전 점검만으로 외부 Vikunja 상태를 바꾸지 않으며, 연결 전에 필요한 값과 대상 프로젝트/보드를 표시한다.
- 잘못된 경로·미설치 플러그인·미연결 상태 각각에 대해 다음 조치가 실행 가능한 형태로 제시된다.

범위 메모: 제공된 로그만으로는 최종 CLI 실패의 구체 원인과 어떤 setup 단계까지 완료됐는지 확인할 수 없다. 이를 확정 결함으로 단정하지 말고 재현 과정에서 명령 인자, cwd, stderr 및 종료 코드 전체를 수집한다. 이 항목은 개선 후보 기록이며 구현 착수나 외부 보드 변경 승인을 뜻하지 않는다.

2026-10-02 적용 결과: 새 Express Git 저장소에서 plugin cache가 `.../handrail/handrail/0.4.0/...`처럼 추가로 중첩된 실제 설치를 확인했다. 고정 경로로 skill을 다시 읽으려 한 시도와 기존 CLI의 `help setup` 호출이 실패했고, status는 v0.4 runtime에서 과거 `0.3.0-rc.4`를 보고했다. `help setup`과 런타임 버전 보고를 추가했다. 0.4.1 재설치 뒤에도 모델이 `.../cache/handrail/0.4.1/skills/...`를 추측해 SKILL.md를 읽으려 하여 실패했다. 스킬은 이미 대화에 로드되므로 재독을 금지하고, launcher는 제공된 active SKILL.md 경로나 `codex plugin list`의 source 경로로 확인하도록 강화했다. 선택 문서 존재 여부 자동 수집과 독립 점검 집계는 미구현이다.

## HR-NEXT-013 — 현재 경로 기반 connection 이름과 프로필 식별

2026-10-02 사용자 요청에 따라 구현했다. `setup`/`connection setup`에서 `--name`이 생략되면 실행 시점의 현재 디렉터리 마지막 경로 구성요소를 프로필 이름으로 사용하며, 예를 들어 `/project_workspace/handrail_workspace`에서는 `handrail_workspace`를 사용한다. 사용자가 `--name`을 준 경우에는 그 값을 유지한다.

프로필 선택 화면은 `이름 (profile-id)`로 식별한다. `connection list`와 setup 결과에도 같은 display name을 제공하고, 현재 프로젝트 status의 연결 표기도 동일한 형식으로 맞춘다. 이름 중복을 새로 금지하지 않으며 ID가 동명이인을 구분한다.

## HR-NEXT-005 — 계획 회차 단위 실행 권한 위임

상세 검토: [프로젝트·전역 권한 정책](../../docs/permission-policy-review.md). 권한을 프로젝트별 또는 사용자 전역으로 기록하고, 동일 범주의 요청에 재사용하며, 실행 중 새로 승인한 추가분을 이후 CLI 실행에 적용하는 절차를 검토한다. 파일 형식·CLI 적용 방법은 미확정이다.

목표: 구체화된 계획을 사용자가 위임하면, 정해진 범위의 실행마다 별도 확인 코드를 요구하지 않고 Review까지 진행한다.

- RC4의 실행 미리보기·`workspace-auto`·입력 고정 검사를 확장한다. [현행 정책](../../docs/worker-authorization-policy.md).
- 단일 계획 회차와 명시적으로 선택한 복수 계획 회차를 지원하는 방안을 검토한다.
- 사용자 추가 요구: 여러 계획 카드를 한 번에 개발 의뢰했다면 선택된 계획·회차를 하나의 위임으로 기록하고 부모 계획·하위 작업 전환마다 다시 승인받지 않는다. 기존 사용자 지시와 권한이 충분하면 별도의 묶음 승인도 추가하지 않는다. 개별 명세는 위임에서 파생하고 계획별 Review는 유지한다. 구현 범위·일정은 계속 미확정이다.
- 프로젝트 실행 정책에 CLI·모델, 작업·네트워크 경로, 허용 동작, 실행 한도를 정하고 사용자 위임과 연결한다.
- 범위 내 작업 카드 생성, 실행·재시도, 검수·검증, 로컬 통합, 카드 동기화 권한을 파생한다. 개별 run은 명세·입력·코드 기준을 계속 고정하고 실제 위임 출처를 기록한다.
- 이미 받은 개발 위임과 별개인 반복 동의를 없앤다. 실제 사용자 답변을 보존하고 자연어 동의·불완전한 코드·여러 대기 요청의 모호성을 처리한다.
- 범위 확장, 새 권한, 한도 초과, 사람의 상태 변경 충돌은 별도 처리한다. Review 이후 수정 요청을 새 회차 위임으로 연결한다.

미결정: 위임의 유효기간·취소·한도, 수정 회차 승인 방식, 복수 계획 변경 시 재확인 단위. Handrail의 위임 기록은 호스트 권한을 부여하지 않는다.

## HR-NEXT-006 — 카드 상태와 Review 열 정책

사용자 합의 방향:

- 저장소당 부모 프로젝트 하나를 유지하고, 연결 시 부모 보드에 Review가 없으면 생성한다.
- Review가 이미 있으면 이를 찾아 사용한다. 없을 때 Handrail 연결의 API token이 해당 Vikunja 프로젝트/view에서 bucket 생성 권한을 가지면 Review bucket을 생성한다. 생성이 거부되거나 권한이 없으면 생성 권한을 요구하지 말고, 사용자에게 해당 보드의 Review 열을 직접 추가해 달라고 안내한 뒤 다시 확인한다.
- Todo, Doing, Done은 이 온보딩에서 사용자가 하나씩 고르는 대상이 아니다. 기존 열 이름/ID를 읽어 식별하고, 불확실하거나 중복된 경우에만 사용자에게 해결을 요청한다. 정상 Review 자동 처리 뒤에는 프로젝트·Kanban view와 필요 시 기존 상태 열 매핑만 확정한다.
- 작업자용 하위 보드에는 Review를 요구하거나 자동 생성하지 않는다. 기본 상태는 Todo/Doing/Done이고, Review bucket이 이미 있으면 선택 상태로 연결할 수 있다.
- 부모 보드는 요구사항 plan card와 종합 Review를 관리한다. 하위 보드는 필요한 worker work card를 두는 선택 기능이며 부모 단독 사용도 유지한다.
- 하위 작업카드는 해당 작업의 상태·run·완료를 추적하는 이력 항목이다. 추가 작업은 새 카드로 만들어 기존 Done 카드 이력을 덮어쓰지 않는다.
- 작업 카드는 성공적인 최종 결과 제출이 확정되면 Done으로 전환해 실행 이력으로 보존한다.
- 조율자의 검수·통합·전체 검증은 별도 근거로 유지하며 계획 Review의 필수 조건으로 삼는다. 작업 Done만으로 계획 Review를 허용하지 않는다.
- Done 이후 보완·수정은 신규 하위 작업 카드로 기록한다. 제출 전 실패 재시도는 동일 카드의 시도 이력으로 보존하는 방안을 검토한다.
- 계획 최종 Done은 사용자 직접 처리 또는 명시적 지시로 수행한다. 사람의 강제 전환은 기존 동기화 절차를 유지한다.

구현 진단: 이전 v0.4 설정은 프로젝트 및 manual Kanban view 선택 뒤 네 상태를 모두 대화형으로 매핑했고, Review가 없으면 연결이 중단됐다. 이는 이미 합의된 자동 Review 정책이 온보딩에 반영되지 않은 불일치였다.

## HR-NEXT-010 — 정식 재시도·복구

- 추가 결함 근거: 작업 #8의 `run revise`가 기존 `CONTEXT.md` 생성 충돌로 worker 기동 전에 실패했다. 현재 코드에서 기존 파일을 남기는 `_write_packet()`과 배타적 생성(`O_EXCL`)을 요구하는 `write_context()`의 충돌을 확인했다. 회차·시도별 실행 패킷 분리 또는 소유권·해시를 확인한 안전한 재사용을 검토한다. 단순 덮어쓰기로 기존 경로 보호를 제거하지 않는다.
- 준비 단계와 worker 실행 단계를 구분한다. `run revise`의 즉시 `running` 응답이 수정 worker 기동 성공으로 오인되지 않도록 한다. 준비 실패는 원인·보존 자료·재개 방법을 제공하며 `recover`가 상태만 반환하는 경우와 구분한다.
- 이전 프로세스 종료 확인 → 복구 스냅샷 및 해시 → 새 실행 경로·의존성 준비 → 입력 확인 → 워커 시작 순서를 제공한다.
- 준비 실패 시 워커를 시작하지 않는다. 이미 시작된 실행의 정리·중단·재개도 상태와 함께 제공한다.
- 초안·복구 지침을 입력으로 고정하고 원본 run과 연결한다. 과거 보고서·승인·검증 근거를 새 실행의 성공 근거로 복제하지 않는다.
- 동일 위임 범위의 실패 재시도는 파생 권한을 이용한다. 완료 작업의 수정은 신규 카드 규칙을 따른다.
- 임시 Python 스크립트나 워커 시작 후 파일 복사·마커 대기에 의존하지 않는 복구 경로를 만든다.

미결정: 기존 worktree 재사용과 새 worktree 복원 선택, 스냅샷 보존·정리, 재시도 한도. 재실행·응답 유실에도 중복 worker를 만들지 않는다.

범위 확정 시 검토할 수용 시나리오 후보:

1. 합의된 단일·복수 계획을 위임한 뒤 범위 내 반복 승인 없이 Review까지 진행.

구현 경계:

- Cursor에서의 스킬 발견·설치·실행 경로·작업 디렉터리·설정 재개 방법을 호스트 연동 계층으로 정의한다.

- Cursor → Codex와 Cursor → Cursor를 실제로 검증한다. 승인·검증·Done 조건은 기존 계약을 유지한다.
- 양쪽 호스트에서 같은 사용자 설정·workspace binding·run 형식을 읽는다. 같은 repo에 두 manager가 접근해도 잠금 규칙을 공유한다.
- 배포 형식은 양쪽의 현행 플러그인 규격과 로딩 확인을 근거로 정한다. 공통 코어를 agent별로 복제하지 않는다.

완료 조건:

1. 새 Cursor CLI 세션에서 스킬 발견과 번들 `status` 호출을 확인한다.
2. 같은 호스트의 A/B 저장소를 오가며 각 부모 보드·명세·run이 섞이지 않는다.
3. 두 worker provider에서 모델 선택, 결과 반환, 검증, 리뷰, 로컬 통합을 확인한다.
4. 취소·인증 실패·모델 미지원·CLI 재시작에서 run과 복구 근거가 남는다.
5. Codex/Cursor가 동시에 같은 repo 쓰기를 시작하면 하나만 점유한다.

첫 구현 전 C0로 MCP 없는 최소 플러그인의 스킬 발견·번들 스크립트 호출·cache 비쓰기를 확인한다. CLI JSON(C1), 공통 잠금(C2), 실제 전체 흐름(C3)은 별도 결과로 기록한다. [Grok 검토 반영 결과](CURSOR_REVIEW.md)를 따른다.

### Codex와 Cursor CLI 공동 개발

사용자의 제안을 반영한 권장 방식이다. 구현을 요청받은 범위 안에서 역할을 분담한다.

| 담당 | 작업 |
| --- | --- |
| Codex | 공통 서비스·CLI 계약 정리, 변경 범위와 산출물 지정, 통합·독립 검토 |
| Cursor CLI worker | Cursor 호스트의 스킬·플러그인·권한·세션 흐름 조사, 연동 계층 구현·리뷰 |
| 실제 Cursor 오케스트레이터 세션 | 사용자 대화에서 Handrail 호출과 두 worker 위임 흐름 수용 검증 |

먼저 읽기 검토로 제약을 찾고, 승인된 구현 작업을 분리한 worktree에 위임한다. 같은 repo의 쓰기 run은 순차적으로 처리한다. Cursor worker가 Vikunja 관리자 권한을 받거나 다시 worker를 위임하도록 하지 않는다. Cursor로 어댑터 코드를 작성한 사실만으로 Cursor 오케스트레이터 지원이 완료된 것으로 판단하지 않는다.

이번 설계 검토에는 사용자가 요청한 Cursor CLI의 `grok-4.7-high`를 실제 호출했다. [검토 결과](CURSOR_REVIEW.md)와 [패키징 판단](PACKAGING_DECISION.md)을 기록했으며 실제 구현 완료와 구분한다.

## HR-NEXT-002 — MCP 필요성 평가

상태: 후속 평가. 서버 구현을 확정한 항목은 아님.

v0에서 Codex가 번들 CLI를 실행하면 설정·작업·run 조회 기능에 접근할 수 있다. MCP를 더해도 승인·명세·보드 경계가 대신 구현되는 것은 아니다. 긴 실행·취소·복구는 공통 서비스에서 구현한다.

다음 조건이 생기면 평가한다.

- 지원해야 할 클라이언트가 외부 도구를 MCP로만 호출할 수 있다면 그 클라이언트 지원에는 MCP가 필요하다.
- 여러 호스트에 도구 검색·구조화된 입력/오류 규격을 제공하는 비용이 CLI 연동보다 작아진다.
- 원격 실행 서비스 요구가 확정돼 로컬 파일·shell 접근 모델을 바꿔야 한다.

완료 조건: 대상 호스트와 필요한 도구를 선정하고 CLI 유지와 MCP 비용을 비교한 결정 기록을 남긴다. 채택하면 동일 코어를 호출하는 얇은 stdio 서버부터 시작한다. 호스트별 설정 형식·의존성 배포·도구 취소와 run 취소의 구분·토큰 입력 경로를 검증한다. 서버가 필요하다는 근거 없이 상시 HTTP 서비스나 자체 인증 서버를 만들지 않는다.

## HR-NEXT-003 — 요청에 따른 하위 프로젝트·보드 추가

상태: 2026-10-02 요청에 따라 구현·빌드 진행 중. RC4의 기존 area 등록에 `area create`를 추가해 사용자가 요청한 하위 프로젝트와 worker Kanban을 생성·검증·등록한다.

선행: 여러 workspace에서 각자의 부모 보드 하나를 사용하는 기본 흐름과 v2 adapter.

범위: 현재 Handrail 프로젝트의 부모 또는 등록된 하위 project 아래에 자식 project와 manual Kanban·Todo/Doing/Done 상태 열을 만들고 해당 workspace의 area로 등록한다. Review 열은 하위 보드에서 선택 사항이며 생성 필수 조건이 아니다. 기존 하위 보드의 읽기 연결도 제공한다. 부모 board 하나는 plan card와 최종 Review를 관리하며, 사용자 요청 전까지 자식 보드는 만들지 않는다. 작업카드는 작업의 지속 이력으로 남고, 추가 작업은 새 카드로 기록한다. 각 workspace는 부모 프로젝트 하나를 유지한다. 상세는 [PROJECT_HIERARCHY.md](PROJECT_HIERARCHY.md)를 따른다.

완료 조건:

1. 하위 보드 없이도 부모 하나에서 plan/work card 흐름을 사용할 수 있다.
2. A의 요청만 A의 지정 parent 아래 생성되며 B의 보드·binding은 바뀌지 않는다.
3. 부모 권한·token route permission 부족·동일 이름·응답 유실·부분 완료를 구분한다.
4. 생성은 기존 부모·사용자 뷰·공유 권한·카드를 수정하거나 삭제하지 않는다.
5. Review 없이 child board를 등록하고 Todo/Doing/Done으로 task 생성·이동·완료할 수 있다.
6. 활성 run과 binding 변경이 충돌하지 않으며 실패한 생성 작업을 중복 없이 조사·재개할 수 있다.

## HR-NEXT-004 — 계층형 카드 workflow와 외부 상태 동기화

상태: RC4에 계층형 카드·외부 상태 동기화 기반 구현 및 배포. 아래는 RC4 계약을 보존한 기록이며 신규 개발 항목 전체를 뜻하지 않는다. 부모 계획 Review 정책은 유지하고 하위 작업 보드에는 Review 열을 요구하지 않는다.

선행: HR-NEXT-003의 명시적 area 등록/조회 기반과 Vikunja task relation API 검증.

범위: 계획 카드는 부모 프로젝트에 두고, 구현·조사 작업 카드를 등록된 하위 보드에 두면서 실제 Vikunja 하위 task 관계로 계획에 연결한다. 조율자는 작업자 결과를 검수·통합·검증한 뒤 작업 카드를 Done 처리하고, 필수 작업 및 최종 검증을 모두 통과한 계획 카드를 Review로 제출한다. 사용자는 직접 또는 명시적 대화 지시로 계획을 Done 처리한다. Review 이후 변경은 새 작업 카드로 기록한다. 사람이 Vikunja에서 강제 전환한 상태는 자동 원복하지 않고 충돌로 감지해 가져오기/적용을 선택하게 한다. 세부 용어·workflow·인수 기준은 [PROJECT_WORKFLOW_AND_TERMS.md](PROJECT_WORKFLOW_AND_TERMS.md)를 따른다.

완료 조건:

1. 부모 binding은 저장소당 하나이며, 등록되지 않은 하위 보드와 다른 부모의 카드는 거부한다.
2. 작업 카드 생성과 계획 카드 관계 설정이 재시도해도 중복되지 않고, 부분 실패가 명확히 복구된다.
3. 워커 종료만으로 Done되지 않으며 조율자의 검수·통합·검증 증거가 작업 카드 완료에 연결된다.
4. 최종 통합 결과의 전체 검증이 최신 fingerprint에서 통과하지 않으면 계획 카드 Review 제출을 막는다.
5. 사람의 직접 상태 변경을 감지하고, 명시 선택 전까지 Vikunja 상태를 덮어쓰지 않는다.
6. 계획 Review 회차, 사용자 결정, 수정 작업 추가, 재제출 이력이 보존된다.
7. 과거 run/operation 재시도가 사람의 Done/재오픈 결정이나 최신 Review 회차를 덮어쓰지 않는다.
