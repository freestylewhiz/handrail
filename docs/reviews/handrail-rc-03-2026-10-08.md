# handrail_rc_03 최종 점검 — 개발 책임자의 채택·축소·제외 판단

상태: **조율자 회고·초안 대조 후 개발 책임자 재검토 완료 / 구현 대기**. 최초 초안은 [원본](handrail-rc-03-2026-10-08/initial-draft.md)으로 보존했다. 의견에 동의했다는 이유로 구현 범위를 확정하지 않는다. 아래 채택·축소·제외 판단이 개발 제안의 기준이며 제품 수정·개발 수용 완료를 뜻하지 않는다.

분석일: 2026-10-08. 대상 버전: `1.0.0-alpha.6+codex.20261008041952` / CLI `1.0.0a6`.

**주요 결론:** RC03은 중간 장애를 수동 복구한 뒤 최종 검증·사용자 수락까지 완료한 사례다. 첫 장애의 핵심은 작업자 신원 오탐, 실제 권한을 적용하지 않은 새 보고 채널, 계약 인계보다 빠른 active Attempt 전환이다. 조율자는 복구 계약 전달을 늦췄고, 지원되는 경로 추가를 충분히 탐색하기 전에 제품 소스 수정부터 요청했다. 제품의 복구 계약과 조율 절차를 함께 고쳐야 한다. 이후 정상 probe·재제출·검토·통합·검증은 성공했으므로 전체 실패나 일반적인 후속 실행 누락으로 결론 내리지 않는다.

검토한 11건을 같은 수준의 제품 결함으로 취급했던 중간 판단을 수정한다. **코드 수정 대상으로 채택하는 것은 RC03-01/02/03/05/06/08/10의 7건**이며, 01~03은 하나의 복구 계약 수정 묶음으로 개발한다. 04/11은 스킬·조율 절차 보완, 07은 기존 DEV-11의 근거다. 09는 독립 제어 시스템 개발로 채택하지 않고 02의 좁은 복구 안내에 흡수한다.

## 개발 책임자의 판단 기준

[철학](../philosophy.md), [현재 아키텍처](../architecture.md), [범위](../rebuild-scope.md)를 기준으로 **Handrail이 소유한 계약을 어겼는지**, **기존 경로를 보완하면 되는지**, **수정 결과를 관측할 수 있는지**로 판단했다. 대상 조율자의 의견은 경험 근거이며 제품 설계의 결정권을 대신하지 않는다.

- Handrail은 사용자 의도·권한 범위·실행 관측·검증·수락의 연결을 책임진다. 호스트 권한 집행, 외부 에이전트의 UI와 대상 앱의 정확성을 대신 소유하지 않는다.
- 조율자의 코드 의미 검토와 Summary 종합 책임은 유지한다. 자동화는 승인된 후속 작업을 이어주는 것이며 검토·검증 근거를 생략하는 기능이 아니다.
- 실패 이력과 현재 성공, 한 단계의 성공과 후처리 차단을 구분한다. 거절·불확실 결과를 숨기거나 전부 성공으로 만드는 방식은 채택하지 않는다.
- 새 daemon·전용 제어 프레임워크·피드백 큐를 기본 해법으로 삼지 않는다. 현재 계약과 스킬의 최소 보완부터 한다. 이미 요청된 DEV-11의 호스트 재개 조사와는 구분한다.

## 0. 대화 절차와 초안에서 달라진 판단

사용자 요청에 따라 기존 조율자 세션에 직접 메시지를 보냈다. 새 작업자를 만들거나 대상 프로젝트의 복구·수정을 요청하지 않았다.

1. **독립 회고:** 초안을 먼저 보여주지 않고 사용 중 개선·수정할 점, 조율의 어려움, 우선순위, 최종 결과를 질문했다. [답변 8건](handrail-rc-03-2026-10-08/dialogue-round1.json)을 받았다.
2. **초안 대조:** 기존 보고서 전체 경로를 전달하고 RC03-01~08의 동의·반박·누락, 15분 지연과 승인 횟수 해석, 자동 복구 경계를 질문했다. 조율자는 문서와 원 실행 기록을 읽고 [대조 의견 9건](handrail-rc-03-2026-10-08/dialogue-round2.json)을 보냈다.
3. **근거 재확인:** 새 제보를 로컬 DB·세션 출력·Handrail 소스와 대조했다. [최종 상태와 검사 로그 발췌](handrail-rc-03-2026-10-08/final-state-evidence.json)를 저장했고, 당시 반영 계획도 대상 조율자에게 회신했다.
4. **책임자 심사:** 이후 사용자의 철학·범위 유지 요청에 따라 제안을 재심사했다. 아래 09~11과 사용성 항목의 축소/제외는 이 문서 작성자의 최종 판단이며 상대 조율자의 합의로 가장하지 않는다.

## 3. 항목별 근거와 최종 처분

채택한 코드 항목에서 P1은 실행·완료 인계 차단, P2는 진단·현재 상태 결함, P3는 표시 결함이다. 절차 보완·기존 설계 근거·제외 항목에는 제품 결함 우선순위를 부여하지 않는다. 아래 번호는 분석 식별자이며 기존 DEV 항목의 완료 상태를 변경하지 않는다.

### RC03-01 / P1 — 보조 프로세스 종료를 작업자 교체로 오판

- **근거:** 기존 process identity의 PID는 `[1839511, 1839966]`, 오류 후 관측은 `[1839511]`이다. 주 프로세스의 PID·start ticks `768949552`·실행 파일·argv hash·cwd가 동일하고 provider session·pane·terminal도 동일하다. 저장된 전후 값으로 `reconcile_identity`를 호출하면 실제 `IDENTITY_STALE`가 재현된다.
- **원인:** [process.py](../../handrail/agentroom/process.py:32)는 Cursor 설치 경로를 가진 node 실행을 공급자 프로세스로 포함하고, 70행에서 전체 process identity의 동등성을 요구한다. 보조 프로세스의 생성·종료가 주 실행 교체와 같은 오류가 된다.
- **영향:** 정상 구현 중인 작업을 복구 대상으로 전환해 채널·권한·보고 흐름까지 흔든다. 실제로 정상 세션을 새 Attempt로 바꿨다.
- **수정:** 주 에이전트 실행을 launch receipt·프로세스 계보·provider session·boot/start identity로 식별하고 보조 프로세스 관측을 분리한다. 일부 PID가 겹친다는 이유만으로 무조건 연속성을 인정하지 않는다. 확정할 수 없는 경우 `unproven`으로 남기되, 확인된 동일 실행의 관측 보강과 실제 교체를 다른 경로로 처리한다.
- **수용 기준:** helper 생성/종료는 기존 Attempt 유지; 주 프로세스 재시작·PID 재사용·provider session 교체는 차단; 이번 저장 전후 값은 동일 실행으로 판별.

### RC03-02 / P1 — 복구 계획의 경로를 실제 실행 권한으로 적용하지 않음

- **근거:** 원래 Cursor 실행은 `.channel-11e2497e969349da`만 `--add-dir`에 포함했다. 복구된 Attempt는 `.channel-4500521ae8d2f64a`를 새 launch argv에 기록하지만 동일 PID `1839511`을 사용한다. 14:48의 worker probe는 새 채널의 `.report-ujmvsg0b`에서 errno 13으로 실패했다.
- **원인:** [service.py](../../handrail/agentroom/service.py:635)의 `recover`는 `prepare()`로 새 채널/launch 설정을 만들지만 실제 프로세스 재실행이나 실행 중 경로 갱신을 수행하지 않는다. **새 launch 계획 저장과 실행 적용이 분리되지 않았다.**
- **영향:** 복구 명령이 성공해도 작업자는 새 결과 경로에 쓸 수 없어 계속 진행하지 못한다.
- **수정:** 동일 실행 신원 보강은 채널을 유지한다. 실제 교체는 대상 제공자가 지원하는 정확한 경로 추가 또는 승인된 재실행으로 권한을 적용하고 worker probe로 확인한 뒤 활성화한다. `requested_launch`와 `applied_launch`를 분리하고 미적용 경로를 실효 권한처럼 기록하지 않는다. 필요한 경우 처음부터 해당 Attempt 전용 보고 루트 안에서 계약 세대를 교체한다.
- **수용 기준:** 같은 실행 복구에서 권한 확대 없이 제출 가능; 실제 교체는 새 채널 적용과 probe 성공을 확인; 적용 실패 시 기존 유효 기록을 먼저 폐기하지 않음.

### RC03-03 / P1 — 계약 전환 전에 기존 Attempt를 활성 수신 대상에서 제외

- **근거:** 14:32:39에 old Attempt가 replaced로 바뀌었으나 새 계약은 14:47:48에 전달됐다. 그 사이 작업자는 기존 지시로 구현을 마쳤다. 기존 채널에 `submission:4f72bd9c…`가 14:47:35 실제 저장돼 있고 backend transcript 27행도 같은 제출 ID와 커밋을 보고한다. 당시 DB에는 frontend 제출 한 건만 있었다. 후속 복구로 새 계약의 backend 제출 2건이 수신됐으며 이전 파일·커밋 자체는 삭제되지 않았다.
- **원인:** `recover`는 새 계약의 전달·수신·readiness보다 먼저 Work의 active Attempt를 전환한다. [tick](../../handrail/agentroom/handoff.py:189)은 active Attempt만 훑으며, [collect_submission](../../handrail/agentroom/handoff.py:116)은 직접 이전 Attempt를 읽어도 stale로 분류한다. 기존 제출의 보관·연결 및 계약 전환 상태가 없다.
- **영향:** 작업자는 제출 성공을 보지만 조율자는 제출 없음으로 기다린다. 수행한 코드를 잃지는 않았으나 정식 검토로 이어지는 인계가 끊겼다.
- **수정:** `recovery_prepared → contract_delivered → worker_ack/probe → active`의 단계적 전환을 둔다. 동일 실행이면 기존 계약 유지가 우선이다. 기존 제출을 발견하면 원문을 보존하고 lineage·SHA·의뢰·검토 근거를 확인해 재제출 또는 명시적 조정 경로로 연결한다. 이전 nonce를 현재 계약으로 무조건 인정하지 않는다. 장시간 구현 중인 작업자에게 계약 변경을 알리지 않고 기다리는 흐름을 스킬에서도 금지한다.
- **수용 기준:** 전환 전/중/후 제출이 모두 누락 없이 기록되며 중복 통합은 없음; 계약 미전달 상태를 즉시 표시; 오래된 유효 제출의 발견/조정 가능.
- **조율자와의 대조:** recover 응답에 bootstrap 전송 안내는 이미 있었다. 조율자는 프런트엔드 검수·통합, backend 관측·소스 검토·후보 브라우저 검사를 병행했고 14:42:10에 새 지시 파일을 준비했지만 14:47:48에 보냈다. 따라서 안내 자체의 부재나 15분 전체 승인 대기로 서술하지 않는다. 계약 전달·probe를 끝내지 않고 구현 종료부터 기다린 절차도 개선 대상이다. 이후 발생한 `WORKER_NOT_READY`를 14:32의 전송 실패 근거로 소급하지 않는다.

### RC03-04 / 절차 보완 — probe와 실제 보고 작성 도구의 권한 경계가 다름

- **근거:** 기존 채널은 14:26:37 Shell probe에서 write=true였다. 하지만 같은 경로의 `report.json`을 Cursor `Write` 도구로 작성할 때 14:45 승인 선택 화면이 발생했다. worker transcript 24행의 도구는 `Write`다. 이후 Shell 작성과 submit 기록이 있으므로 이를 단순한 OS 경로 쓰기 불가로 설명할 수 없다.
- **책임 판정:** probe는 `boundary=worker-tool-execution`의 파일 쓰기 관측이며 모든 제공자 편집 도구의 승인을 약속하지 않는다. Cursor Write 승인 자체를 Handrail 구현 결함으로 분류하지 않는다. 실제 사용할 보고 도구를 준비 단계와 완료 지시에서 일치시키는 것이 Handrail의 역할이다.
- **최소 보완:** 현재 보고 파일·`worker submit` 경로와 해당 도구 준비를 스킬에서 명확히 한다. 새 submit 입력 API나 Cursor 권한 제어기는 이번 사례만으로 개발하지 않는다. 별도 Write 도구가 꼭 필요할 때만 지원되는 정책 준비를 적용하며 거부를 우회하지 않는다.
- **수용 기준:** Codex/Cursor 각각 사전에 승인·적용된 보고 경로와 실제 사용할 도구 범위에서 probe뿐 아니라 보고 작성→submit까지 승인 재요청 없이 수행; 역할·도구별 준비 관측을 구분.

### RC03-05 / P2 — 보고 채널이 막히면 probe의 진단 결과까지 사라짐

- **근거:** worker가 새 채널 접근 거부를 보고했지만 조율자 tick은 `readiness: null`과 일반적인 `WORKER_WRITE_NOT_READY`만 반환했다. 새 채널에는 contract만 있었고 readiness 파일은 없었다.
- **원인:** [worker_io.py](../../handrail/agentroom/worker_io.py:43)는 경로별 probe 결과를 계산한 뒤, 거부될 수 있는 바로 그 채널에 `write_atomic(readiness.json)`을 호출한다. 이 마지막 쓰기가 실패하면 계산한 blocked 결과 대신 상위 `LOCAL_ACCESS_FAILED`만 남는다.
- **수정:** readiness 계산 결과와 채널 전달 실패를 별개로 출력·기록한다. 채널을 못 쓰면 stdout의 구조화된 실패 결과를 전달할 수 있어야 한다. 조율자는 이 결과를 worker 관측으로 보관하고 실제 probe 없이 ready를 만들지 않는다.
- **수용 기준:** 새 채널 쓰기 거부에도 어떤 경로가 통과/실패했는지와 보고 실패 경로를 보존; 대기 중인 미실행 probe와 실제 실패를 구분; probe를 승격 실행하지 않음.

### RC03-06 / P2 — 복구 상태와 사용자 안내가 모순됨

- **근거:** 복구된 Attempt는 `execution_phase=readiness`, 새 채널에는 readiness 없음인데, 문서 안에는 old Attempt의 `readiness.status=ready`가 그대로 복사돼 있다. provider activity는 `done`이다. 현재 [status](../../handrail/application.py:155)는 idle/done을 보고 “collects and reviews”를 안내하며, tick은 “Continue readiness or monitor worker”라는 일반 지시를 반환한다.
- **원인:** `dict(old, ...)` 복사 시 실행별 readiness를 제거하지 않는다. status는 phase·현재 계약·구체적인 blocker보다 provider activity에 의존한다. tick의 실패는 재시도 불가 상태도 backoff로만 다룬다.
- **수정:** 새 계약에는 이전 readiness를 과거 근거로만 보존한다. `activity`, `execution_phase`, `handoff_status`, `blocked_resource`, `resumer`를 분리하고 현재 계약의 관측만 준비 상태에 사용한다. 미전달·경로 미적용·probe 실패는 각각 필요한 행동을 반환한다.
- **수용 기준:** 이번 상태에서 “새 채널 권한 미적용 / probe 실패 / 호스트 설정 담당”을 표시; old ready와 현재 ready를 혼동하지 않음; 관측 polling은 유지할 수 있으나 해결 행동 없이 같은 비재시도성 작업을 반복하지 않음.

### RC03-09 / 독립 기능 제외 — 제공자 제어 명령의 전달 결과 수동 판독

- **제보·독립 확인:** 독립 회고 3/8. `rc03-add-recovered-channel-01`은 `worker.prompt`로 `/add-dir`를 전달했고 `agent_prompt_stalled` → `HERDR_STALLED`, uncertain=true를 남겼다. `rc03-add-dir-enter-01`은 동일 신원·화면 hash·정확한 Enter에 묶여 실행됐고, 이후 메시지는 관측 근거로 delivered에 조정됐다. 새 경로의 일반 probe 성공도 확인했다.
- **원인 확실성:** [Herdr 어댑터](../../handrail/interfaces/agentroom/herdr.py:131)는 stall을 불확실 전달로 분류하며 자동 재전송하지 않는다. 이 보호는 유지한다. 일반 대화 턴 조건으로 슬래시 명령 완료를 기다려 생긴 stall이라는 설명은 조율자의 가설이며 Herdr 내부 원인까지 확인한 것은 아니다.
- **책임자 판단:** 이 기록은 Handrail의 전송 실패 오판을 입증하지 않는다. 현재 계약대로 unknown을 보존하고 관측 후 resolve한 동작은 올바르다. 조율자가 불편했다는 이유로 Cursor/Herdr 제어 시스템을 새로 소유하지 않는다. 앞선 독립 P1 개발 제안은 철회한다.
- **반영 범위:** RC03-02의 복구 안내에 실제 지원되는 경로 추가, 전달 불확실 시 기존 resolve 절차, 적용 뒤 일반 probe를 명시한다. 실행 적용 자동화가 필요한 경우에도 승인된 제공자 어댑터의 좁은 기능으로만 검토한다. 범용 키 조작·슬래시 명령 완료 감지 프레임워크와 Herdr 서버/UI 변경은 제외한다.
- **확인 기준:** 불확실 전송 자동 재시도 금지와 현재 대상·관측·정확한 효과 확인을 유지하며, 경로 적용 후 실제 probe로 준비를 판정.

### RC03-10 / P2, 축소 채택 — 증거 미등록 진단과 단계별 결과 요약

- **제보·독립 확인:** 회고 5/8과 15:05:17 실행 출력. backend `work complete`는 `state=done`, verified=true를 저장했지만 exit 1을 반환했다. `followthrough.blocker`는 `WORKFLOW_REVISION_STALE`, expected=`51dda4c…`, observed=null이었다. Plan 증거 등록 후 Review 전환은 성공했다.
- **원인:** [CLI](../../handrail/cli.py:470)가 Work 완료 후 `advance_plan` 결과를 합치고, [exit_status](../../handrail/shared/results.py:2)가 중첩 followthrough의 blocked를 실패로 올린다. 증거가 아직 없는 경우도 [workflow 검증](../../handrail/workflow/service.py:133)의 “다른 revision” 오류로 나타난다.
- **책임자 판단:** Work Done과 followthrough blocked는 이미 별도 필드에 있으며, 후속 차단을 exit 1로 표시하는 것은 현재 계약에 부합한다. 종료 코드 자체를 결함으로 보거나 새 결과 프로토콜을 필수화한 앞선 제안은 과했다.
- **최소 수정:** revision=null이고 증거가 없는 경우에는 증거 미등록을 우선 진단한다. 기존 필드에 “Work 완료 / Plan 증거 필요 / 재개 대상”을 분명히 요약하고 스킬이 이미 완료한 단계부터 반복하지 않게 한다. 실제로 오래된 증거와 후처리 실패의 비정상 종료 코드는 유지한다.
- **수용 기준:** 이번 상태에서 “Work 완료 / Plan 증거 미등록 / 증거 기록 후 Plan 검증”을 즉시 판독; 재개는 남은 Plan 단계부터 진행; 진짜 revision 변경과 보드 전송 실패는 별도로 유지.

### RC03-11 / 스킬·작성 절차 보완 — Summary accepted 상태와 본문의 불일치

- **제보·독립 확인:** 회고 7/8. 15:10:53의 `summary prepare` 출력은 v2를 accepted로 표시하면서 영어·한국어 결과와 agent_context에 `Plan Review`, `user acceptance pending`을 남겼다. 조율자가 수정해 15:11:21 v3를 게시했다.
- **원인:** [summary lifecycle](../../handrail/summary/service.py:284)은 record_status·workflow_state·acceptance_id 등을 갱신하지만 `content_from`으로 기존 작성 본문을 그대로 다시 쓴다. 조율자가 쓴 당시 상태 문장과 자동 메타데이터의 갱신 책임이 분리되지 않았다.
- **책임자 판단:** [현재 아키텍처](../architecture.md#summary의-데이터-경계)는 모델이 본문·번역을 종합하고 CLI는 형식·상태·버전·전송을 관리하도록 나눈다. CLI가 기존 서술을 보존한 것 자체를 결함으로 단정하지 않는다. 반면 [Summary 스킬](../../plugins/handrail/skills/handrail/references/summaries.md)은 current draft가 있으면 summary-file 생략을 안내하므로, 메타데이터 최신성과 본문 최신성의 차이를 명확히 해야 한다.
- **최소 보완:** 수락 완료를 기록한 뒤 조율자가 본문과 Agent Context의 현재 상태·검증 한계를 확인하고 필요할 때 같은 카드에 갱신한다. 수락 대기 같은 변동 상태의 중복 서술은 줄이고 구조화된 현재 상태를 참조한다. 자동 의미 수정·번역 엔진·임의 문자열 치환은 개발하지 않으며 사용자 수락을 다시 받지 않는다.
- **수용 기준:** Review→사용자 수락→Done에서 영어·한국어·Agent Context의 현재 상태가 일치; 과거 Review 사실은 과거로 표시; 외부 편집·충돌·번역 누락을 보존/진단; 같은 수락 재시도에 버전·댓글 중복 없음.

## 4. 조율의 어려움과 절차 개선

| 조율자가 겪은 어려움 | Handrail에서 할 일 | 조율 절차에서 할 일 |
| --- | --- | --- |

피드백 예약은 경험 의견으로 보존하되 **현재 구현 backlog로 올리지 않는다**. room keep/close는 실제로 별도 선택으로 처리됐으므로 새로운 정리 기능도 만들지 않는다. 대상 앱의 body 없는 요청·CSRF·chmod·브라우저 동작을 Handrail 기본 정책으로 일반화하지 않는다. Handrail에는 프로젝트별 기준과 최종 검증 증거를 연결할 책임만 남긴다.

## 5. 구분해서 볼 사항

### 정상 동작 및 유지할 관문

- 보드 선택·지침 생성·frontend/backend 보드 배정은 진행됐다. 사용자 요청에 명시된 모델을 사용했고 frontend 완료 인계는 약 8초 안에 수집됐다.
- 조율자는 frontend 소스 검토·병합·빌드·화면 검사를 실제 이어갔다. backend 미완료 상태에서 Plan Done이나 전체 테스트 통과를 만들지 않았다.
- 신원 확인, 검토된 SHA 통합, probe를 승격 실행하지 않는 관문 자체는 유지한다. 수정 대상은 신원 판단의 정확성과 복구·권한 적용·제출 프로토콜이다.
- 최초 세션이 제품 소스 수정을 별도 범위로 구분한 것은 타당하다. 다만 조율자도 인정했듯 지원되는 `/add-dir` 복구 탐색은 부족했다. 실제로 설치본 수정 없이 정확한 채널 추가와 일반 probe로 복구했다. 별도 제품 개발 동의가 반드시 필요한 장애였다고 설명하지 않는다.

### 구현 프로젝트의 문제와 Handrail 개선 근거

로그아웃·삭제 요청의 Content-Type/body 합의 차이, JSON 파일의 private mode, root 환경에서 쓰기 실패 검증이 어려웠던 문제는 대상 서비스의 구현·테스트 사항이다. 이를 Handrail 서버 기능 결함으로 분류하지 않는다.

다만 Handrail 자동 검수 설계에는 다음을 반영할 근거가 된다.

- 병렬 작업자에게 전달하는 API 계약에 body 없는 요청·헤더·오류·권한 시나리오까지 포함하고 통합 검사에서 확인한다.
- frontend Work의 넓은 UI 기준에 소스/빌드 통과를 기록하면서 실제 연동을 Plan에 미룬 점은 거짓 Plan 완료가 아니다. 그러나 어떤 동작 검증이 어느 기준에서 대기 중인지 구조화하지 않으면 Work Done을 완전한 UI 검증으로 오해할 수 있다. DEV-11의 기준별 필수 검사·미검증 분리를 보강한다.
- 초기 browser candidate 검사는 병합된 frontend와 당시 backend를 임시 환경에서 조합해 수행했다. 후속 실행에서는 최종 canonical `51dda4c…`에서 `rc03-final-api-01`, `rc03-final-browser-01`, `rc03-final-storage-01`을 정식 `command.run`으로 실행하고 기준별 증거와 연결했다. 세 기록 모두 revision_before=revision_after, clean_after=true, exit 0이다. 따라서 최종 정식 검사 부재라는 지적은 유지하지 않는다.

### 자동 복구의 범위와 관측 한계

기존 승인된 저장소·모델·실행 주체와 확인된 세션 연속성 안의 진단, 정확한 경로 적용, 계약 전달, 일반 probe, 재제출 수집을 자동 복구 대상으로 설계한다. 실제 실행 교체나 범위 추가는 기존 정책과 비교하고 실효 권한을 다시 확인한다. 무조건 재시작·busy 작업 강제 중단·포괄 권한·probe 승격·old nonce 자동 수락·설치 소스 패치는 이 범위에 포함하지 않는다.

이번 성공은 해당 Cursor 세션의 복구 사례다. 모든 제공자·CLI/IDE에서 최초 승인 1회만으로 자동 복구된다는 검증이 아니며, 이번 재검토에서 서비스나 권한을 재실행해 확인하지 않았다. 서비스 종료·방 유지 결과는 대상 조율자의 실행 로그와 회고에 근거한다.

## 7. 검증 근거와 미실행 범위

- `process.py`, `service.py`, `handoff.py`, `worker_io.py`, `setup/access.py`, `application.py`의 소스 SHA-256과 설치본이 모두 일치했다. 따라서 위 실행 결함은 오래된 설치본만의 차이로 설명되지 않는다.
- 재검토에서 `summary/service.py`, `shared/results.py`, `cli.py`, `interfaces/agentroom/herdr.py`도 소스/설치본 SHA-256 일치를 확인했다.
- 저장된 전후 process identity를 순수 함수에 넣어 `IDENTITY_STALE` 재현, 주 프로세스 레코드 일치, 새 채널의 원래 launch 범위 미포함, 새 Attempt에 old readiness 잔존을 확인했다.
- 초기 worker 제출 파일과 DB 수신 기록으로 “기존 채널 제출 있음 / 당시 현재 backend 수신 없음”을 확인했다. 이후 새 계약 재제출 2건과 최종 통합·검사·수락을 확인했다. nonce나 비밀값은 보고서에 복사하지 않았다.
- URL 렌더러의 순수 함수 재현을 확인했다. live 보드 표시·Cursor 권한 설정 재현·통합 서비스 테스트는 수행하지 않았다.
- 제품 코드를 수정하지 않았으며 대상 저장소의 서버 실행, worker 구현 지시·복구, 보드 쓰기, 권한 추가, Git 병합을 수행하지 않았다. 사용자에게 허가받은 기존 조율자와의 회고·초안 대화 및 이 저장소의 보고서/개발 추적 문서 갱신만 수행했다.
