# Codex Astra High · Worktree 배치 1차 의견

+1차 권고는 C, 즉 canonical checkout 밖의 영속적인 sibling 전용 worktree 루트입니다. 전제는 사용자가 등록한 개발 workspace 안에 해당 루트가 있
고, 조율자의 실제 host 권한이 그 경로를 포함한다는 것입니다. 부모 디렉터리가 존재하거나 쓰기 가능하다는 사실만으로 승인됐다고 간주해서는 안 됩
니다.

예를 들면 <개발루트>/app을 canonical checkout으로, <개발루트>/.handrail-worktrees/<workspace-id>/…를 작업 소스 저장소로 사용합니다. 관리자 권
한 기록·토큰·상태·감사 이력은 계속 private 관리자 저장소에 둡니다. Worker에는 자신의 worktree만 작업 쓰기 범위로 부여합니다.

기존 A 배치는 자동 이전하지 않고 유지합니다. B는 project-only sandbox에서 외부 영속 루트를 마련하기 어렵고 프로젝트의 도구 간섭을 검토한 경우
의 명시적 예외로 허용합니다. D는 폐기 가능한 임시 작업에만 사용합니다. E는 이 선택을 구현하는 결정 정책으로 채택하되, 실행 때마다 임의로 위치
를 바꾸는 자동 최적화로 만들지 않는 것이 좋습니다.

이 판단은 철학 문서 (docs/philosophy.md)의 검수 후 통합·Review 보존·추적성과, 구조 문서 (docs/architecture.md)의 private 관리자 상태 분리를 함
께 적용한 것입니다. 실제 프로젝트의 개발 도구와 배포 동작을 훼손하지 않는 것도 같은 수준의 요구사항으로 봤습니다.

A~E를 두 관점에서 비교하면 다음과 같습니다.

조율자의 “프로젝트 내부를 기본, 홈은 옵션” 제안에는 부분적으로 동의하지만 기본값으로는 반대합니다. test_6에서 관찰한 특정 쓰기 제한을 낮추는
효과는 있지만, 그 한 가지를 전체 배치 정책의 기준으로 삼기에는 비용이 큽니다.

첫째, Git ignore는 Git의 추적 여부를 다룰 뿐 모든 watcher·패키징·배포 도구의 제외 정책을 대신하지 않습니다. 내부에 worker 두 명의 소스와
node_modules가 생기면, 도구 구성에 따라 파일 탐색량과 빌드 문맥이 크게 늘어날 수 있습니다. 이것은 Handrail 내부 구현 문제가 실제 프로젝트 개발
속도와 산출물에 영향을 주는 경로입니다.

둘째, 상위 설정 탐색이나 workspace 탐색을 사용하는 도구에서는 내부 worktree가 canonical checkout의 설정·의존성을 의도치 않게 참조할 가능성도
검토해야 합니다. 검증이 통과해도 격리된 후보 자체가 준비된 것인지, 상위 환경에 기대어 성공한 것인지 구분하기 어려워질 수 있습니다. C와 A도 환
경 의존성을 없애지는 않지만 canonical checkout 내부 중첩을 피할 수 있습니다.

셋째, B로 옮겨도 .git의 별도 읽기 제한, private 관리자 상태 쓰기, Herdr 제어 접근, 설치 네트워크는 남습니다. test_6의 행 553과 1399는 각각 Git
공용 관리 영역과 worktree 쓰기의 다른 실패입니다. 위치 변경 하나로 “추가 승인 해결”이라고 설명하면 다시 사용자 기대를 어기게 됩니다.

반대로 C도 공짜는 아닙니다. project-only sandbox 사용자는 초기 설정을 한 번 더 해야 할 수 있고, 대형 개발 workspace 전체를 승인하면 범위가 과
도해질 수 있습니다. 따라서 C의 장점은 넓은 부모 쓰기 권한이 아니라, 프로젝트에 간섭하지 않는 정확한 영속 경로를 등록하는 데 있습니다. 조율자에
는 필요한 canonical·전용 저장 루트만, worker에는 개별 worktree만 허용해야 합니다.

권장 결정 규칙은 다음과 같습니다.

1. 기존 실행은 저장된 경로를 우선합니다. 기본값 변경이나 host 변화 때문에 실행 중·Review 중 worktree를 자동 이전하지 않습니다. 경로가 없어졌으
   면 복구 대상으로 표시합니다.

2. 신규 실행은 명시적으로 등록된 배치 설정을 먼저 검증합니다. 저장소가 제공한 설정은 배치 제안일 수 있지만 권한의 근거가 될 수 없습니다.

3. 설정이 없고 승인된 영속 개발 workspace가 있다면 C를 선택합니다. 이름 충돌을 피하도록 workspace ID와 workflow·실행 시도 ID를 사용합니다.

4. 그 전제가 없으면 기존에 승인된 A를 사용합니다. C나 A에 대한 권한이 확인되지 않으면 후보와 필요한 차이를 제시합니다. B로 조용히 우회하지 않
   습니다.

5. B는 프로젝트 도구 간섭과 보존 정책을 확인한 명시적 선택으로 허용합니다. D는 중단 후 복구가 필요 없는 작업이나 재생성 가능한 산출물에 한정합
   니다.

이 정책에서는 ‘기본 배치 C’와 ‘어느 환경에서도 C를 강제로 생성’하는 행동이 분리됩니다. 필요한 전제조건이 없는 환경은 설치·권한 준비가 필요한
상태로 설명해야 합니다.

현재 소스에서는 다음 변경이 필요합니다.

• 소스 저장 위치와 관리자 상태 위치를 분리하는 공통 resolver가 필요합니다. herdr_workflow._worktree() (handrail/herdr_workflow.py:235)는 XDG의
  herdr-worktrees를 직접 만들고, run_workflow.start() (handrail/run_workflow.py:509)는 별도의 worktrees 경로를 계산합니다. 두 workflow가 같은
  배치 정책과 ownership 검증을 사용하도록 바꾸되 runs.root() 전체를 소스 위치로 이동해서는 안 됩니다. 그 아래에는 private 실행 기록도 있습니
  다.

• 경로가 존재한다는 것과 소유한 worktree라는 것을 구분해야 합니다. 현재 Herdr _worktree()는 경로가 이미 있으면 그대로 반환합니다. workspace·작
  업·시도 ID, Git common directory, 기준 커밋, symlink 여부를 확인해야 합니다. run_preparation.owned_worktree() (handrail/
  run_preparation.py:18)의 검사는 참고할 수 있지만, 고정된 XDG 경로 비교를 등록된 배치와 불변 소유 기록 검증으로 바꿔야 합니다.

• checkout과 canonical root의 구분을 유지해야 합니다. workspace.resolve() (handrail/workspace.py:19)는 현재 checkout과 등록된 canonical root를
  구분하고 Git common directory를 대조합니다. 이 구분을 유지해야 worker에서 명령을 호출했다고 통합 대상이나 저장 루트가 바뀌지 않습니다. 동일
  저장소의 여러 checkout은 공용 Git 저장소 충돌도 함께 관리해야 합니다.

• preflight는 역할별 실제 경로를 반환해야 합니다. permission_adapters.host_preview() (handrail/permission_adapters.py:221)에 선택된 배치와 정
  확한 root를 전달하고, manager 작업·worker 소스 작업·provider 실행 상태의 권한을 분리해야 합니다. 현재 preview의 필요 권한 목록은 실제 host
  적용을 입증하지 않습니다.

• 검수·통합·검증의 Git 쓰기 요구를 명시해야 합니다. gitops.fingerprint() (handrail/gitops.py:12)는 임시 index를 사용하지만 git add와 write-
  tree를 실행합니다. 따라서 “실제 index를 건드리지 않는다”는 것이 “파일시스템 쓰기가 없다”는 뜻은 아닙니다. review()·integrate()에는 Git 공용
  객체 저장소 접근이 필요하고, finish()는 canonical checkout에서 검사를 수행합니다. Worker 위치를 바꿔도 통합 checkout의 의존성 준비와 검증 권
  한은 별개입니다.

• 삭제·이동·migration을 기록된 작업으로 다뤄야 합니다. 단순 디렉터리 이동으로는 Git 등록, private registry, 승인된 절대 경로, 활성 pane의 cwd
  가 함께 정합화되지 않습니다. 기존 실행은 보존하고 신규 실행부터 새 배치를 적용하는 방식을 기본으로 삼아야 합니다. 삭제는 통합 여부뿐 아니라
  미반영 변경·활성 프로세스·Review 보존 요구까지 확인해야 합니다.

수용 기준은 두 관점을 동등하게 반영해야 합니다. Handrail 쪽에서는 재시작 후 같은 실행·경로·명세·승인을 복원하고, 경로 교체나 다른 Git 저장소를
거부해야 합니다. 프로젝트 쪽에서는 canonical 빌드·검색·배포 문맥에 worker 후보가 뜻하지 않게 들어가지 않아야 합니다. 어느 배치든 worktree별 의
존성·산출물의 디스크 비용은 남으므로, 위치 선택과 별도로 사용량·보존 현황을 보여줘야 합니다.

추가 승인 최소화의 원칙은 사용자 동의 재사용과 host 적용 확인을 각각 수행하는 것입니다. 이미 승인된 프로젝트별 영속 저장 루트 아래의 새 작업
디렉터리는 기존 위임이 실제로 포괄한다면 매번 다시 묻지 않아야 합니다. 그러나 승인 기록이 있다고 host가 해당 경로를 허용하는 것은 아닙니다. 반
대로 host가 부모 workspace를 허용한다고 worker가 모든 sibling 프로젝트를 수정해도 되는 것은 아닙니다.

초기 설정에서는 필요한 소스 루트·Git common directory·private 상태·제어 접근을 한 번에 구체적으로 제시하고, 이후에는 변경된 능력만 확인하는 편
이 좋습니다. 기존 승인이 충분하면 새 질문 없이 진행하고, host 적용에 재시작이 필요하면 그 사실을 구분해 안내해야 합니다. /tmp로 이동하거나
sandbox를 해제해 질문을 없애는 방식은 승인 최소화로 평가하지 않겠습니다.

상대 검토자에게는 세 가지 쟁점의 반론을 요청합니다.

1. B를 기본으로 삼는다면, Git ignore 이외의 IDE·watcher·패키징 간섭을 어떤 조건으로 검증하고, 프로젝트별 설정 비용을 누가 부담해야 합니까?

2. project-only sandbox에서 C의 초기 설정 비용이 B의 장기 간섭 비용보다 크다고 판단하는 구체적인 사용자군이 있습니까? 그 경우 B를 기본으로 전
   환할 명확한 조건은 무엇입니까?

3. 승인과 위치의 안정성을 위해 기존 실행 경로를 고정하고 새 실행에만 배치 변경을 적용하는 정책에 동의합니까? Review 중 이동을 허용한다면 보존
   해야 할 증거와 사용자 동의의 최소 범위는 무엇입니까?

이번 라운드에서는 브리프, 지정된 철학·구조·권한 정책 문서와 관련 소스를 읽고 기존 evidence 판단을 재사용했습니다. 상대 의견은 읽지 않았으며 변
경·실행 실험·추가 에이전트 실행은 하지 않았습니다.
