HERDR_ENV 미설정은 곧바로 연결 불능이나 권한 부족을 뜻하지 않지만, 외부 조율을 지원하려면 Handrail이 caller 환경 대신 명시적으로 고정한 연결
대상·실행 정체성·사용자 승인 범위를 검증해야 합니다.

실제 이름은 HERDR_ENV입니다. HERDER_ENV는 이번 자료에서 사용자가 지칭한 이름이며, 별도의 기능을 가진 변수라는 근거는 없습니다.

설치 skill은 HERDR_ENV=1을 pane 내부 실행 여부를 확인하는 조건으로 사용하며, workspace·tab·pane 변수는 caller 문맥으로 설명합니다. 반면 연결은
선택한 session, socket 문맥, 명시적 machine 등의 영향을 받습니다. 변수 자체가 연결 주소나 인증 credential이라는 근거는 없습니다. 실제 인증·접
근 통제 전체를 이번 자료만으로 설명할 수도 없습니다.

관찰된 CLI·서버 버전은 0.9.1이고 protocol 호환 상태와 socket 경로가 기록돼 있습니다. 이것은 수집 당시 관찰입니다.
endpoint_protocol_generation: 1을 서버 재시작마다 바뀌는 incarnation ID로 해석해서는 안 됩니다.

무시 가능 여부는 “변수 하나를 무시한다”보다 다음 규칙으로 정리하는 편이 정확합니다.

• pane 내부 조작에서 caller 문맥이 필요한데 없다면 중지해야 합니다. --current, 생략된 대상, 다른 클라이언트의 focused pane을 추측해서 대신 사
  용하면 안 됩니다.

• 명시적으로 승인된 외부 조율에서는 미설정만을 중단 사유로 삼지 않을 수 있습니다. 기존 사용자 지시, 정확한 연결 대상과 agent 범위를 확인하고
  재사용해야 합니다. 이번 관찰에는 기존 검토 agent들과 토의하라는 명시적 지시가 있습니다.

• 설치 skill의 외부 금지 규칙과 외부 조율 계약의 차이는 공개적으로 정리해야 합니다. 사용자 지시가 이미 충분한데 같은 동의를 반복 요구할 이유는
  없습니다. 그러나 “CLI가 성공했으니 skill의 모든 제약을 무시한다”는 결론도 부적절합니다.

• 환경 변수 위조는 해결책이 아닙니다. HERDR_ENV=1을 넣어도 실제 caller pane이나 승인 범위가 생기지 않습니다.

• 읽기와 제어를 구분해야 합니다. 범위 안의 상태·화면 조회는 진단에 사용할 수 있지만, 지시·키 입력·workspace 종료에는 해당 동작의 권한과 대상
  정체성이 필요합니다. 기존 agent와 대화하라는 지시는 그 workspace를 닫으라는 승인까지 포함하지 않습니다.

현재 Handrail의 핵심 문제는 환경 변수 검사가 없다는 사실보다 외부 제어 대상을 충분히 고정하지 않는 구조입니다. HerdrClient (handrail/
herdr_transport.py:14)는 session을 받을 수 있지만, flow._client() (handrail/herdr_workflow.py:80)는 기본 HerdrClient()만 만듭니다. _run()은
subprocess 환경을 별도로 지정하지 않으므로 호출 환경을 상속합니다. 따라서 실행 위치나 상속된 routing 문맥이 달라졌을 때 다른 대상에 붙을 가능
성을 관리해야 합니다. 실제 오접속이 관찰됐다는 뜻은 아닙니다.

또한 _ensure_space()는 저장된 workspace ID를 조회해 dictionary가 반환되면 기존 공간으로 취급합니다. start()는 pane·이름·worktree·모델을 저장하
지만 provider session 정체성이나 연결 대상까지 묶어 보존하지 않습니다. 이후 collect()와 keys()는 주로 저장된 agent 이름을 사용합니다. 명시 ID
는 focused pane 의존성을 줄이지만, 서버 범위와 현재 점유 프로세스까지 증명하지는 않습니다.

제품 수정 백로그는 다음과 같습니다.

1. P1 — 내부 caller 모드와 외부 조율 모드를 명시하십시오.

   근거는 설치 skill의 중지 규칙, HerdrClient.__init__/_argv/_run, flow._client()입니다. 외부 모드에는 local session 또는 지원되는 remote
   selector와 사용자 승인 출처를 저장하고, discovery부터 후속 명령까지 같은 routing을 사용해야 합니다. 상속 환경은 무조건 제거하기보다 연결을
   바꾸는 항목을 식별해 통제해야 합니다.

   수용 기준: HERDR_ENV가 없어도 승인된 외부 대상을 사용할 수 있고, 모호한 focused/current 대상에는 제어 명령을 보내지 않아야 합니다. 연결 실
   패 때 다른 서버나 Local로 자동 전환해서는 안 됩니다. 실제로 없는 서버 식별 필드를 검증했다고 기록해서도 안 됩니다.

2. P1 — agent 이름을 실행 정체성과 결합하십시오.

   근거 함수는 _ensure_space(), start(), collect(), recover(), keys()입니다. 연결 선택, workspace·pane, agent 이름, provider, 관찰 가능한
   provider session, 승인 worktree, Handrail 실행 시도를 함께 기록해야 합니다. 명령 직전에는 의미 있는 조합을 재검증하고, 교체된 프로세스는 복
   구 절차로 채택해야 합니다.

   수용 기준: 다른 서버의 같은 이름, 같은 pane의 새 점유자, 다른 cwd의 agent를 기존 worker로 자동 취급하지 않아야 합니다. API가 조건부 제어를
   지원하지 않는다면 조회와 전송 사이의 교체 가능성이 남는다는 한계를 표시해야 합니다. 이름에 접두어만 추가하고 완전한 식별이 해결됐다고 선언
   해서는 안 됩니다.

3. P1 — 지시 전달과 실행 상태를 분리하십시오.

   agent_prompt() (handrail/herdr_transport.py:196)는 working/blocked/done을 대기 조건으로 사용합니다. 설치 skill은 별도의 5초 활동 관문과
   lifecycle 대기가 특정 턴을 식별하지 않는다는 한계를 설명합니다. 따라서 timeout을 늘리는 것만으로 stall을 해결할 수 없습니다.

   _send_instruction()의 반환 결과를 확인하지 않고 start()·prompt()가 running으로 저장하는 부분도 개선해야 합니다. blocked가 정상 결과로 반환
   되는 경우 실행 중으로 오표시할 수 있습니다.

   수용 기준: 전송 의도, 입력 제출, 활동 관찰, 응답 수집을 구분해야 합니다. 지시별 ID·내용 hash·대상 시도를 저장하고, timeout 후 자동 중복 전
   송을 금지해야 합니다. agent_not_ready 같은 오류의 재시도 가능성은 문자열 검색만으로 판단하지 말고 해당 버전의 미전송 의미를 확인해야 합니
   다.

4. P1 — 통신 상태와 개발 진척을 독립적으로 표시하십시오.

   근거는 collect(), status(), _idle(), review(), finish()입니다. 현재 collect()는 화면과 저장된 상태를 반환하며, status()의 다음 담당자는 주
   로 Kanban 상태에 의존합니다.

   수용 기준: 연결 가능 여부, 마지막 관찰 시각, agent lifecycle, 최신 지시 처리 상태, 변경·검사 증거, 카드 단계를 구분해야 합니다. 조회 실패는
   “작업 실패”가 아니라 “관찰 불가”로 표시하고 마지막 확정 상태를 보존해야 합니다. Worker가 idle이 돼도 검수·통합·검증 전에는 개발 완료로 보고
   하지 않아야 합니다.

5. P1 — blocked UI와 종료 동작에 동작별 권한을 적용하십시오.

   근거는 keys()와 accept()·_close_space()입니다. keys()는 reason을 요구하지만 그 문자열 자체가 승인 증거는 아닙니다. 화면에 보이는 질문, 수행
   할 키의 의미, 기존 승인 범위를 연결해야 합니다.

   수용 기준: 기존 승인이 정확히 덮는 응답은 다시 묻지 않고 처리할 수 있어야 합니다. 새 능력이나 모호한 삭제·설치 요청은 별도로 판단해야 합니
   다. 외부에서 채택한 검토 agent는 생성 소유권과 종료 권한을 분리하고, 계획 완료가 관계없는 workspace 종료로 이어지지 않아야 합니다.

6. P2 — 응답 수집과 진척 알림을 조율 업무에 맞추십시오.

   agent_read()는 visible 화면이 비어 있지 않으면 그대로 반환하므로 완료 응답이 화면 밖에 있어도 추가 수집을 하지 않습니다. 화면 일부만으로
   “응답 없음”을 판단할 수 있습니다.

   수용 기준: UI 승인 확인에는 visible, 결과 수집에는 적절한 recent 자료를 사용하고 수집 범위·누락 가능성을 표시해야 합니다. 지원되는 변화 번
   호나 제한된 주기 조회로 불필요한 반복 수집을 줄이되, 침묵 시간으로 실패나 진행률을 만들어내서는 안 됩니다. 파일 출력 fallback은 해당 작업의
   쓰기 허용 범위에서만 사용해야 합니다.

외부 조율의 정상 흐름은 승인된 대상 확인 → 연결·정체성 확인 → 지시별 전송 기록 → 변화 관찰 → 응답과 산출물 검수 → 통합·검증 → 사용자 판단이어
야 합니다. 환경 변수 유무는 첫 진입 문맥의 정보로 남기고, 이 흐름 전체의 권한이나 성공을 대신하지 않게 해야 합니다.

상대 모델에는 다음 세 쟁점의 반론을 요청합니다.

1. 명시적 외부 조율 지시가 있을 때 설치 skill의 blanket stop을 어떤 공식 외부 모드 계약으로 대체해야 합니까?

2. 서버 incarnation이나 조건부 제어 API가 확인되지 않은 환경에서, 이름·pane·cwd·provider session 중 어떤 조합을 최소 요건으로 삼고 어떤 경우
   제어를 중지해야 합니까?

3. PTY의 전달 불확실성과 특정 턴을 식별하지 못하는 wait를 유지하면서, 중복 지시 없이 신뢰할 수 있는 진척 보고를 제공할 최소 계약은 무엇입니까?

이번 판단은 지정된 관찰 파일, 설치 skill 사본, Handrail 소스·문서와 기존 evidence에 근거합니다. 관찰 파일의 성공 기록을 직접 재현하지 않았으
며, 환경 변경·worker 조작·명령 실행 실험은 하지 않았습니다.
