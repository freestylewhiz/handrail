# handrail_test_6: 쓰기 권한 문제 별도 상세 보고

작성일: 2026-10-06. [두 모델 종합 보고](report.md)의 권한 관련 상세 근거다. 목적은 Handrail의 실행 설계와 사용자 사용성 개선이다.

## 1. 무엇이 실제로 막혔나

**조율자 Codex의 샌드박스에서 Herdr worktree에 쓰려다 실패한 것이 확실히 관찰됐다.** 이를 “Herdr 전체에 쓰기 권한이 없다” 또는 “파일 소유권이 잘못됐다”로 일반화하면 진단이 부정확해진다.

조율자의 실효 프로필은 다음과 같았다. 근거는 [contexts](evidence/01a10e6f-contexts.jsonl)다.

| 자원 | 당시 조율자 경계 |
| --- | --- |
| `/project_workspace/handrail_poc/handrail_test_6` | 프로젝트 쓰기 허용 |
| `/tmp` 및 임시 디렉터리 | 쓰기 허용 |
| 프로젝트의 `.git`, `.agents`, `.codex` | 별도로 읽기 전용 |
| `/home/dyhwang23/.local/share/handrail/...` | 조율자의 쓰기 허용 루트에 포함되지 않음 |
| 네트워크 | 제한됨 |

Handrail은 `herdr_workflow._worktree`에서 다음 위치에 worker 작업 트리를 만든다.

```text
/home/dyhwang23/.local/share/handrail/projects/
  be9720f2a8734176a14bd91aecc5b7ea/herdr-worktrees/23/work-24/
```

worker를 그 경로에서 시작하는 것과 조율자 자신이 그 경로에 파일을 쓰는 것은 다른 실행 권한이다. Herdr로 터미널을 만들었다고 조율자의 바깥 샌드박스가 확장되지는 않는다.

## 2. 실패와 성공의 직접 근거

아래 시각은 한국시간이며 `L`은 원본 rollout 행이다. [명령 snapshot](evidence/01a10e6f-commands.jsonl)의 `line` 필드로 확인한다.

| 09:53:55, L1399 | `vite.config.js.timestamp-*.mjs` 생성 EROFS | 조율자가 worktree의 Vite 설정 옆에 임시 파일을 쓸 수 없음 |

| 09:56:21, L1507 | raw `herdr agent prompt`: EPERM | Herdr 제어 접근 오류. 어떤 syscall·자원인지 출력만으로 확정 불가 |

| 10:04:20, L1665 | 통합 checkout의 finish: `vite: command not found` | 이것은 쓰기 거부가 아니라 통합 검사 환경의 의존성 부재 |

설정 파일을 `/tmp`로 복사하는 우회는 모듈 탐색 문제를 만들었고, 설치 버전에서 지원하지 않는 옵션도 시도됐다. 이러한 탐색은 조율자의 판단 비용이었다. Handrail이 오류의 실행 주체·쓰기 대상·실패 단계를 먼저 제공했다면 줄일 수 있는 비용이다.

## 3. Handrail에서 부족했던 부분

### 실제 작업 경로와 사전 점검 경로가 다르다

`cli.dispatch`의 preflight는 일반 run 경로인 `.../worktrees`를 전달한다. 실제 Herdr 작업은 `.../herdr-worktrees/<plan>/<task>`에서 실행된다. 이미 preflight 기능은 존재하지만 Herdr의 정확한 필요 권한을 안내하지 못했다.

저장소가 writable이라는 사실만으로 충분하지 않다. worktree, Git common directory, Handrail 상태 디렉터리, 패키지 캐시, Herdr 제어 채널과 원격 보드 접근을 각각 다뤄야 한다. 현재 `host_preview`가 호스트 준비 완료를 보장하지 않는다는 점도 유지해야 한다.

### Herdr에 기존 권한·준비 기능이 연결되지 않았다

`permissions.py`에는 grant/delegation과 계획·명세·검사 범위 고정 기능이 있고 `run_preparation.py`에는 의존성 준비가 있다. 그러나 Herdr 시작 경로는 이 기능을 직접 사용하지 않는다. worker의 설치 승인 요청을 조율자가 거절한 뒤 manager 경계에서 설치하고, 나중에는 통합 checkout을 또 준비해야 했다.

기존 코드에 함수 호출 하나를 추가하는 수준으로 끝나지는 않는다. frontend/backend처럼 구성요소별 작업 경로, 새 manifest 생성 시점, 설치 스크립트 변경, 통합 검사 준비를 표현할 계약이 필요하다.

### 읽기처럼 보이는 작업도 쓰기·네트워크를 요구한다

`collect`는 터미널 화면을 읽지만 원격 카드 상태를 확인하고, 로컬 lock과 수집 결과를 기록한다. 사용자에게는 상태 확인인데 실제로는 여러 권한을 요구하는 구조다. 로컬 snapshot 읽기, 실시간 관찰, 결과 저장, 원격 동기화를 별도 동작으로 제공할 필요가 있다.

### 오류가 다음 행동으로 이어지지 않는다

EROFS, Herdr EPERM, API 연결 실패, 의존성 부재가 각기 다른 원인인데 조율자가 문자열을 보고 직접 추론했다. 오류 출력에 `실행 주체 / 작업 / 자원 / 거부된 경계 / 기존 승인 / 필요한 변경`이 있으면 불필요한 우회 명령과 재질문을 줄일 수 있다.

## 4. 네 가지 승인·권한을 구분해야 한다

| 층 | 의미 | Handrail이 재사용할 근거 | 기술적 한계 |
| --- | --- | --- | --- |
| 사용자 작업 동의 | 어떤 개발·검토를 맡겼는가 | 사용자 지시와 범위·위임 출처 | 그 지시만으로 OS 접근이 열리지는 않음 |
| Handrail grant/delegation | 어느 계획·작업·모델·종류를 허용하는가 | 범위, revision/cycle, 만료·철회 상태 | Herdr 경로와 연결해야 효과가 있음 |
| 조율자 host escalation | 바깥 실행 환경이 무엇을 허용하는가 | 호스트가 실제 적용한 경로·행위 규칙 | 내부 provider 설정으로 바깥 정책 변경 불가 |
| worker UI 승인 | 개별 worker 도구가 무엇을 실행하는가 | provider별 실효 정책과 작업 범위 | manager 권한이 worker에 자동 전파되지 않음 |

같은 작업을 맡겼다는 이유로 이 네 층을 하나의 `approved=true`로 합치면, 실제 접근이 안 되는데 준비됐다고 표시할 수 있다. 반대로 같은 사용자 의도를 각 층에서 반복 질문하면 사용성이 나빠진다. **동의의 재사용과 실행 권한의 적용 결과를 각각 기록하는 설계**가 필요하다.

## 5. 권한 요청을 줄이는 구체적인 제품 설계

### 단기: 필요한 경계를 먼저 계산하고 동일 범위 질문을 없앤다

1. 사용자 지시에서 이미 확정된 작업 범위·모델·effort·위임을 기록한다. 미정 필수 사항만 한 번에 묻는다.
2. plan/task별 실제 경로와 작업 목록을 계산한다. 예: 이 계획의 worktree 쓰기, 저장소 Git 작업, 특정 Vikunja origin 접근, 승인된 구성요소 설치·검사.
3. 필요 권한과 현재 허용을 비교해 차이만 표시한다. 사용자의 동의와 호스트 적용 여부를 따로 보고한다.
4. 의존성 준비를 관리 단계로 수행한다. 같은 manifest·스크립트·argv·실행 경계의 재시도는 기존 승인을 재사용한다.
5. 상태 조회와 감사 기록을 정리한다. 조회에 불필요한 네트워크·쓰기 의존성을 없애고 중복 사전 댓글을 줄인다.
6. 대기 메시지에 누구의 어떤 응답이 필요한지 적는다. 사용자 확인, worker 실행 완료, 호스트 승인 대기를 구분한다.

예시 사용자 요약은 다음처럼 구성할 수 있다. 이는 제안 문구이며 현재 구현된 화면은 아니다.

> 이 계획에는 frontend/backend 작업, 지정한 두 모델, 로컬 설치·검사가 포함돼 있습니다. 기존 지시로 진행합니다. 현재 호스트에는 계획 worktree 쓰기와 보드 접속 허용이 추가로 필요합니다. 아래 적용 결과를 확인한 뒤 진행합니다.

호스트가 개별 확인을 요구하면 해당 UI를 사용해야 한다. “한 번의 동의로 모든 호스트에서 이후 클릭 0회”는 보장할 수 없다.

### 중기: 계획 범위를 검사하는 관리 실행 인터페이스

관리 명령이 임의 shell 문자열을 그대로 실행하지 않고 작업 ID에서 승인된 argv·cwd·자원을 해결하도록 한다. 모델 입력이나 변경된 프로젝트 파일로 실행 범위가 바뀌면 차이를 평가한다. 허용 기록에는 사용자 지시 출처, 계획 cycle, 행위·자원, 적용 주체, 만료·철회, 관찰 시각이 필요하다.

작업 트리 배치는 두 선택지를 호스트별로 지원할 수 있다.

- 호스트가 정확한 외부 경로를 허용할 수 있으면 해당 계획의 worktree와 상태 경로만 적용한다.
- 호스트가 별도 작업 루트를 제공하면 Handrail의 worktree 위치를 그 루트에 배치하도록 설정한다. Git common directory와 상태 저장 경계는 추가로 확인해야 한다.

경로 이동만으로 모든 권한 문제가 해결되지는 않는다. `.git`, 네트워크, Herdr 제어 접근은 각자의 경계가 있다. Python 실행기 전체, raw Herdr 전체, 사용자 홈 전체를 허용하는 방식은 범위를 제대로 표현하지 못한다.

## 6. 수용 기준과 측정

- 동일한 유효 승인 범위의 재시도·검증·상태 확인에서 **Handrail이 추가 동의를 묻는 횟수 0회**.
- 사전 점검이 출력하는 경로와 실제 생성·빌드 경로 일치.
- 호스트 적용 결과가 없으면 준비 완료로 표시하지 않음.
- 권한 오류와 의존성 오류를 다른 원인 코드로 보고.
- 순수 로컬 상태 조회는 쓰기·네트워크 없이 수행.
- 새 경로·목적지·실행 능력, 만료·철회, 최종 사용자 완료 판단은 구분해 처리.
- 요청 생성 수, 자동 허용 수, 사용자 클릭 수, 거부 수, 승인 대기 시간을 별도 측정.

이번 주 세션에는 escalation을 포함한 tool call **98건**, 명시적인 `require_escalated` 지정 **103곳**이 있다. 한 call에 여러 명령이 포함될 수 있다. 실제 사용자가 98회 또는 103회 클릭했다는 뜻은 아니다. 따라서 현 자료로 승인 클릭 감소율을 제시하지 않는다.

## 7. 판단 범위

확실한 부분은 조율자 쓰기 루트와 Herdr worktree의 불일치, Vite 임시 파일 EROFS, 다른 실행 경계에서 같은 빌드의 성공, 통합 checkout 준비 누락이다. 파일 소유권·chmod 문제, Herdr EPERM의 정확한 자원, 실제 클릭 횟수는 확인되지 않았다.

권장 우선순위는 [HR6-U01 사전 점검 → HR6-F05 준비 → HR6-U02 승인 재사용](report.md)이다. 이 세 가지를 함께 연결해야 사용자가 권한 문제를 매번 해석하고 해결 방법을 묻는 부담을 줄일 수 있다.
