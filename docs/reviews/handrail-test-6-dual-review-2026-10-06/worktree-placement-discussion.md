# Handrail Worktree 배치: 두 모델 교차 토의 결과

2026-10-06. 기존 Herdr 분석 workspace `wW`의 Codex GPT-6-Astra High와 Cursor Grok 4.7 High에게 1차 독립 판단을 받은 뒤, 상대 의견·질문과 조율자의 소스 확인 결과를 전달해 2차 교차 토의를 진행했다. 새 에이전트는 생성하지 않았다.

## 최종 권고

**작업 소스는 원본 checkout 밖의 영속 전용 루트를 우선한다. 신규 개발 환경에는 같은 개발 작업공간의 별도 루트를 권장하고, 배치 설정이 없는 기존 환경은 현재 XDG 위치를 유지한다.** 프로젝트 내부 배치는 명시적 예외로 지원하며 `/tmp`는 임시 산출물에 사용한다.

이것은 제품 개선을 위한 설계 권고다. 현재 구현의 위치나 실행 중인 worktree를 변경한 것은 아니다.

조율자의 직전 답변인 “프로젝트 내부 `.handrail/worktrees`를 기본값으로 삼자”는 권고를 수정한다. 이 배치는 project-only sandbox에서 내용 쓰기 권한을 재사용하는 이득이 있지만, 원본 프로젝트의 빌드·검색·의존성 탐색과 작업 보존에 미치는 비용을 충분히 반영하지 못했다.

## 1. Handrail 목표·구조 관점

[제품 철학](../../philosophy.md)은 요구사항, 작업, 변경, 검증, 사용자 결정을 연결하고, 조율자가 검수 후 통합하며 Review 이후에도 이력을 보존하는 것을 목표로 한다. 위치 선택에도 다음 조건이 필요하다.

- **검수 전 소스와 원본 checkout 구분:** 작업자의 후보를 검토하고 명시적으로 통합한다. 디렉터리 배치도 이 구분을 이해하기 쉽게 해야 한다.
- **영속성과 재개:** 미통합 변경과 Review 중인 작업은 세션 종료 후에도 복원할 수 있어야 한다.
- **프로젝트·실행 정체성:** 같은 이름의 저장소, 여러 checkout, 계획·시도가 섞이지 않도록 Git common directory와 private registry, workspace·실행 ID를 사용한다.
- **관리 상태와 소스 분리:** 승인 기록·토큰·잠금·관리 이력은 관리자 영역에 남긴다. worker의 작업 경로 변경 때문에 이 데이터 전체를 이동하거나 worker 쓰기 범위를 넓혀서는 안 된다.
- **예측 가능한 복구:** 실행 경로를 기록하고 고정한다. 권한 오류나 기본값 변경 시 다른 위치로 조용히 옮기지 않는다.

이 조건은 원본 checkout 밖의 영속 루트와 잘 맞는다. 다만 외부 worktree도 Git common directory를 공유하므로 독립 백업이나 완전한 보안 격리를 뜻하지 않는다. [Git worktree 공식 문서](https://git-scm.com/docs/git-worktree)

## 2. 실제 구현 프로젝트 관점

프로젝트 내부 worktree는 이미 허용된 쓰기 범위를 활용하기 쉽다. 그러나 Handrail을 도입한 프로젝트가 추가로 관리해야 하는 설정이 생긴다.

| 영향 | 내부 배치에서 고려할 점 | 외부 전용 루트의 효과와 한계 |
| --- | --- | --- |
| Git 상태·변경 수집 | 제외 누락 시 nested repository가 상태·fingerprint에 영향을 줄 수 있음 | canonical checkout 내부 중첩을 피함 |
| IDE 검색·파일 감시 | 작업자 수만큼 코드·의존성이 탐색에 포함될 가능성 | repo 단위 탐색에서는 분리되지만 상위 workspace를 열면 여전히 포함될 수 있음 |
| Docker·배포 | repo 전체 context에 worker 소스·의존성이 포함될 가능성 | context가 repo일 때 외부 루트를 분리할 수 있음 |
| 의존성·상위 설정 탐색 | 원본 checkout의 패키지나 설정에 기대어 검사가 성공할 가능성 | 원본 checkout이 ancestor가 되는 관계를 없앰. 상위 개발 환경의 영향은 남음 |
| 정리·이동 | 원본 디렉터리의 수동 삭제·이동에 작업 소스 수명도 결합됨 | 소스 배치를 분리하지만 Git 관리 영역과의 연결은 계속 필요 |
| 권한 설정 | project-only sandbox에서 내용 쓰기 요구가 줄 수 있음 | 별도 루트 허용이 필요할 수 있으므로 초기 준비와 재사용이 중요 |

Docker는 build context 제외에 `.dockerignore`를 사용한다. 따라서 Git에서 무시한 디렉터리가 Docker에서도 빠진다고 가정할 수 없다. [Docker 공식 문서](https://docs.docker.com/build/concepts/context/#dockerignore-files)

Node CommonJS는 로컬에 의존성이 없으면 상위 `node_modules`를 탐색한다. 따라서 내부 배치에서는 원본 checkout의 의존성을 우연히 사용하는 경로가 생길 수 있다. **이는 공식 동작에 근거한 위험 시나리오이며 test_6에서 재현한 장애는 아니다.** [Node 공식 문서](https://nodejs.org/api/modules.html#loading-from-node_modules-folders)

외부 루트 자체가 모든 격리를 해결하지는 않는다. worker별 쓰기 범위, 설치·검사 환경, 호스트의 실효 권한은 별도로 관리해야 한다.

## 3. 두 모델의 토의 과정

| 쟁점 | Codex Astra 1차 | Cursor Grok 1차 | 2차에서 확인된 공통 판단 |
| --- | --- | --- | --- |
| 우선 배치 | 승인된 개발 workspace의 외부 루트(C) | 정책(E)을 두고 무설정 위치는 현재 XDG(A) | 신규 권장 구조 C와 무설정 동작 A를 구분 |
| repo 내부(B) | 일괄 기본값에 반대, 예외 허용 | 일괄 기본값에 반대, 예외 허용 | 내용 쓰기의 이득은 인정하되 도구 간섭을 고려해 명시적 선택 |
| 임시 루트(D) | 일반 Review·resume worktree에 부적합 | 임시 인덱스·산출물용 | 영속 작업의 기본 위치로 사용하지 않음 |
| 권한 요청 최소화 | 정확한 루트와 작업 범위의 기존 승인 재사용 | 초기 경로 등록과 승인 재사용 | 사용자 의도·제품 승인 기록·host 적용을 구분 |
| 기존 실행 | 기록된 경로 고정 | 기록된 경로 고정 | 자동 이전하지 않고 별도 migration으로 처리 |

Codex는 2차에서 “C 기본”이라는 표현을 신규 환경의 권장 구조로 한정했다. Cursor는 신규 사용자에게 C를 권장하되 정확한 경로가 등록되지 않았다면 A를 유지하는 데 동의했다. 두 최종 답변은 상대의 1차 의견에 대한 답변이며, 조율자가 공통 부분과 남은 차이를 대조했다.

**남은 해석 차이:** Cursor는 checkout 외부라는 물리적 분리를 현행 정책의 강한 요구로 읽었다. Codex는 별도 작업 소스·실행 정체성·제한된 쓰기 범위·검수 후 통합을 핵심 조건으로 보며, 내부 linked worktree도 예외로 가능하다고 봤다. 종합 권고는 후자를 따른다. 내부 배치 자체를 Git 격리 파괴나 권한 우회로 단정하지 않는다.

## 4. 신규 사용자에게 권장할 구조

다음은 제안 구조이며 현재 자동 생성되는 구조가 아니다.

```text
사용자가 등록한 개발 작업공간/
├── app/                         # 사용자의 원본 checkout
└── .handrail-worktrees/
    └── <workspace-id>/           # 이 프로젝트에 허용한 영속 작업 루트
        └── <workflow>/<execution-id>/
            └── 작업 소스

사용자 비공개 Handrail 저장소/
└── 설정·승인 기록·실행 상태·잠금·감사 이력
```

개발 작업공간 전체를 쓰기 허용하라는 의미가 아니다. 조율자는 이 프로젝트의 정확한 작업 루트와 필요한 Git 관리 영역을 사용하고, worker는 자신의 실행 디렉터리를 쓰기 범위로 삼는다. 저장소 부모가 있다는 이유만으로 승인된 개발 작업공간으로 간주하지 않는다. 다른 저장소 안에 외부 루트를 만들어 간섭을 옮기는 것도 피한다.

이 구조는 프로젝트별로 귀속·관리하면서 원본 checkout의 하위 디렉터리에는 넣지 않는 방법이다. 실제 위치는 별도 볼륨이나 사용자가 지정한 영속 경로일 수도 있다.

## 5. 결정 규칙

1. **이미 실행 기록이 있으면 기록된 경로를 사용한다.** 새 설정을 소급 적용하지 않는다. 경로 소실은 복구 대상이다.
2. **신규 실행에 명시적 배치 설정이 있으면 해당 루트를 검증한다.** 설정·승인 출처, 저장소 identity, symlink·중첩, 실제 host 적용을 확인한다.
3. **설정이 없으면 현행 XDG 경로를 유지한다.** 이것은 위치 기본값이며 접근이 허용됐다는 뜻이 아니다. 신규 환경 안내에서는 외부 영속 루트를 우선 권장할 수 있다.
4. **선택한 경로의 권한이 부족하면 환경 준비 상태로 전환한다.** repo 내부나 `/tmp`로 자동 대체하지 않는다.
5. **repo 내부는 명시적 선택으로 지원한다.** Git·watcher·빌드·패키징 제외와 보존 정책을 프로젝트에 맞게 정한다. 매 실행마다 별도 경고 동의를 추가하는 방식으로 만들지 않는다.
6. **일반 작업 worktree는 영속 저장한다.** `/tmp`는 재생성 가능한 임시 파일에 사용한다.

기존 XDG 경로를 유지하는 것은 현재 구조가 본질적으로 잘못됐다는 결론을 피하기 위해서이기도 하다. test_6의 핵심 결함은 그 경로에 필요한 조율자 권한·준비를 연결하지 못하고, 사전 점검이 실제 경로를 안내하지 않은 점이다.

## 6. project-only sandbox에서의 사용자 경험

외부 루트가 모두 막히면 첫 환경 준비 시 다음을 한 번에 보여준다.

- 현재 선택된 영속 worktree 루트와 필요한 내용 쓰기.
- Git common directory에 필요한 관리 작업.
- private 상태·Herdr 제어 접근과 필요한 설치·네트워크 작업.
- 기존 사용자 지시·승인으로 이미 포함된 범위와 실제 host 적용이 안 된 부분.

이미 충분히 승인된 범위는 다시 묻지 않는다. 미설정 부분은 현재 XDG 경로를 허용하거나, 정확한 외부 루트를 등록하거나, 프로젝트 내부 배치를 명시적으로 선택할 수 있게 한다. 호스트가 해당 경로를 허용하지 않으면 적용 미완료 상태를 정확히 표시한다.

이후 같은 루트의 새 작업 디렉터리는 기존 승인 범위가 실제로 포괄할 때 재사용한다. 새 계획의 작업 위임·새 Review cycle 판단과 변경 없는 저장 위치 승인을 구분한다. 호스트의 승인 UI나 재시작 요구까지 Handrail이 없앨 수 있다고 약속하지 않는다.

한 종류의 명령이 성공했다고 생성·설치·검사·Git 쓰기가 모두 허용됐다고 표시해서도 안 된다. 정책 정보와 실제 작업 결과는 확인한 능력별로 기록한다. 넓은 Python·Herdr prefix 대신 자원과 검증된 작업 범위를 재사용 계약으로 삼는다.

## 7. 구현 백로그로 연결할 항목

| ID / 우선순위 | 구현 범위 | 수용 기준 | 기존 백로그 연결 |
| --- | --- | --- | --- |
| HR6-W01 / P1 | 소스 배치 resolver와 private 소유 기록 분리. Herdr·legacy run·owned_worktree가 같은 정책 사용 | 기존 경로 유지, 새 설정은 신규 실행에 적용. 이미 존재하는 다른 저장소·symlink·다른 실행 경로를 채택하지 않음 | F02, U01 |
| HR6-W02 / P1 | 실제 루트 기반 사전 점검과 승인 재사용 | 미리보기와 실행 경로 일치. source/Git/state/control 권한 구분. 이미 승인된 같은 범위 재질문 없음. 거부 시 조용한 위치 대체 없음 | F05, U01, U02 |
| HR6-W03 / P1 | 경로 고정·재개·이동·정리 계약 및 프로젝트 간섭 수용 기준 | Review 중 자동 이전 없음. 이동 시 Git 등록·실행 기록·프로세스·승인 경로 정합성 보존. canonical 검사에 후보 소스가 섞이지 않음 | F01, F03, F07 |

주요 수정 지점은 `herdr_workflow._worktree`, `run_workflow`의 경로 계산, `run_preparation.owned_worktree`, `cli` preflight, `permission_adapters.host_preview`다. `runs.root()` 전체를 소스 루트로 바꾸면 private 실행 기록까지 이동하므로 분리해야 한다.

현재 Herdr `_worktree`는 경로가 이미 있으면 그 경로를 반환한다. 새 배치 정책과 함께 Git identity·소유 기록을 검사하는 방어가 필요하다. `workspace.resolve`의 canonical checkout과 현재 checkout 구분은 유지한다.

## 8. 정정과 검토 한계

- Cursor 1차의 “IDE 검색이 삭제한다”는 표현은 2차에서 철회됐다. 검색·인덱싱과 삭제를 구분한다.
- `git clean -fdx`가 nested worktree를 일반적으로 삭제한다는 주장은 미검증으로 제외했다. Git은 중첩 저장소에 대한 별도 강제 조건을 문서화한다. 이번 작업에서는 삭제 실험을 하지 않았다. [Git clean 공식 문서](https://git-scm.com/docs/git-clean)
- `capture_seed`의 `.handrail/` 검사는 worktree 기준 변경 파일의 상대경로다. worktree의 절대 부모 경로에 `.handrail`이 있다는 이유만으로 거부되는 것은 아니다. 해당 1차 주장은 두 모델 모두 정정했다.
- repo 내부 배치의 권한 이득은 인정한다. 사용자에게 공개된 정상적인 승인 범위 재사용을 우회로 부르지 않는다.
- Docker·상위 의존성 간섭은 설계 위험 시나리오이며 이번 test_6에서 관찰한 장애로 집계하지 않는다.
- 토의·코드 읽기·공식 문서 대조만 수행했다. 구현·프로젝트·칸반·기존 worktree를 변경하거나 테스트·설치·서버를 실행하지 않았다.
