# handrail_test_6: 두 모델 독립 검토와 Handrail 개선 백로그

작성일: 2026-10-06. 분석 관점은 Handrail의 기능·신뢰성 및 사용자 사용성이다. 테스트 프로젝트의 구현 문제를 수정하는 작업은 포함하지 않는다.

## 결론

가장 먼저 개선할 부분은 **Herdr 실행 경로에서 실제 실행 권한·의존성 준비·복구·완료 처리를 일관되게 관리하는 것**이다. 사용자가 승인한 범위를 제품이 기억하고 해당 실행에 적용할 수 있어야, 조율자가 실패할 때마다 권한 설명과 실행 명령을 다시 조립하는 일이 줄어든다.

대상 개발은 최종 성공했다. #24·#25가 Done이 됐고, 후속 API 점검과 사용자의 실행 확인을 거쳐 #23도 Done이 됐다. 그러나 완료 명령의 분기, 남은 작업공간, 과거 실패가 섞인 현재 상태, 기능 기준보다 좁은 검증 계약은 성공 이후에도 남은 Handrail 개선 과제다.

권한 개선의 목표는 **이미 승인된 동일 범위의 반복 질문을 없애고, 실제로 새로 필요한 권한만 설명하는 것**이다. Handrail의 승인 기록과 바깥 호스트의 실행 허용은 별도로 추적해야 한다.

## 1. 기능 개선 백로그

우선순위 P1은 다음 개선 주기의 우선 후보, P2는 후속 후보다. 이 보고서는 구현 착수나 수용 기준 통과를 뜻하지 않는다.

### HR6-F01 · P1 · 실행 방식에 맞는 완료 경로 통합

- **현상·근거:** L1859·1878·1970에서 일반 `plan verify/submit-review/accept`를 사용했다. `cli.dispatch`는 `kanban`을 직접 호출하지만, workspace 종료는 `herdr_workflow.accept`에만 있다. 카드가 Done이어도 Herdr의 종료 절차가 빠졌다.
- **영향:** 조율자가 유효한 명령을 선택했는데 제품 전체의 완료 결과가 달라진다. 사용자는 남은 관리 작업을 따로 물어야 한다.
- **개선:** 계획에 실행 방식과 후처리 담당을 기록하고, 공통 명령이 그 담당으로 연결되게 한다. 카드 승인과 자원 정리를 별도 단계로 저장한다.
- **수용 기준:** 지원하는 어느 완료 진입점에서도 동일한 후처리를 수행한다. 종료 실패는 `Done / cleanup_pending`으로 표시한다. 기존 사용자 승인으로 정리만 재시도하며 카드 이동·댓글을 중복 생성하지 않는다.
- **분류:** 관찰된 제품 결함. 명령 혼용은 조율자의 실수지만 정상 성공으로 누락을 허용하는 부분은 제품 책임이다.

### HR6-F02 · P1 · 소실 worker를 복구하는 공식 경로

- **현상·근거:** L623 전후 prompt stall, L633·657 전후 `agent_not_found`. `recover`는 기존 agent 조회·읽기에 성공해야 하므로 소실 상태를 처리하지 못한다. 새 pane 생성 후 복구했으나 저장 pane은 이전 값이다.
- **개선:** 실행 시도 ID, agent/session/pane 식별자, 지시 전달 상태, 실행체 존재 상태를 분리한다. 동일 작업·모델·명세·worktree와 중복 실행 부재를 확인해 재연결한다. CLI 업데이트 진행도 준비 상태로 표현한다.
- **수용 기준:** raw `herdr agent start` 없이 복구할 수 있고 식별자가 함께 갱신된다. 새 빈 프롬프트만으로 이전 지시가 미전달됐다고 판단하지 않는다. 전달 불확실성이 해소되지 않으면 중복 지시를 보내지 않는다.
- **분류:** 관찰된 복구 공백. 자동 업데이트가 소실의 유일 원인이라는 주장은 미확정이다.

### HR6-F03 · P1 · 현재 상태와 실패 이력 분리

- **현상·근거:** 최종 #24는 `status=complete` 및 성공 evidence를 가지면서 최상위 `checks`에는 과거 Vite 실패, `last_error`에는 시작 오류, `pane_id`에는 과거 pane을 보존한다. `finish` 성공 경로가 실패 시 저장한 `checks`를 정합화하지 않는다.
- **개선:** 시도별 이력은 보존하고 현재 상태는 마지막 유효 결과에서 계산한다. 오류 해소 여부와 외부 상태의 관찰 시각을 표시한다.
- **수용 기준:** 실패 후 성공 시 현재 검사는 성공으로 일관되며, 과거 실패는 이력에만 표시된다. 저장된 상태와 실제 관찰 상태를 구분한다.
- **분류:** 관찰된 코드·데이터 정합성 결함.

### HR6-F04 · P1 · 완료 기준별 증거 연결

- **현상·근거:** 명세에는 CRUD·오류 응답·재시작 보존이 있지만 승인 검사는 backend 구문 검사와 frontend 빌드다. 댓글 151의 Review 기준도 이 검사들로 축소된다. 댓글 150의 후속 스모크 성공은 별도 서술로 남는다.
- **개선:** 기능 기준별 ID에 자동 검사, 수동 관찰, 사용자 검토 증거를 연결한다. 구문/빌드 통과, 기능 확인, 사용자 승인을 각각 표시한다.
- **수용 기준:** 필수 기준의 증거가 빠지면 미확인으로 표시한다. Review에 원래 기능 기준과 남은 확인 항목이 나온다. 하나의 일반 문장을 모든 수동 검사 통과 증거로 자동 적용하지 않는다.
- **분류:** 관찰된 검증 계약 공백. 최종 앱이 실패했다는 판단은 아니다.

### HR6-F05 · P1 · 구성요소별 의존성 준비를 Herdr에 연결

- **현상·근거:** worker 설치 프롬프트, manager 설치, worktree 빌드, 통합 checkout의 `vite: command not found`가 이어졌다. `herdr_workflow.start/finish`는 기존 `run_preparation.prepare_dependencies`를 사용하지 않는다. 기존 준비 함수도 그대로는 frontend/backend 구조를 충분히 처리하지 못한다.
- **개선:** 구성요소별 manifest·lockfile·설치 argv·cwd·캐시·실행 주체를 준비 계약으로 관리한다. worker와 통합 검사 환경을 모두 포함한다. 최초 생성 프로젝트는 manifest가 생긴 뒤 준비 단계를 진행할 수 있어야 한다.
- **수용 기준:** 승인된 준비 범위 안에서는 설치 요청을 worker에게 반복 전달하지 않는다. 준비 실패와 검사 실패를 구분한다. manifest나 실행 스크립트가 바뀌면 차이를 평가한다. 모든 설치를 무조건 시작 전에 실행하도록 고정하지 않는다.
- **분류:** 관찰된 준비 경로 누락.

### HR6-F06 · P1 · 완료 재시도의 증거 고정

- **근거:** `finish`는 호출마다 `checked_at`을 포함한 evidence를 다시 만든다. `kanban.complete_herdr_work`는 pending/완료 evidence와 완전 동일성을 요구한다. 원격 반영 뒤 로컬 저장이 끊기면 재호출의 새 evidence가 충돌할 수 있다.
- **개선:** 검사 결과와 operation ID를 먼저 고정하고, 재시도는 원격 반영·로컬 확정 단계부터 재개한다. 재검사는 별도 시도다.
- **수용 기준:** 검사 후, 원격 이동 후, Kanban 저장 후, Herdr 저장 전의 중단을 복구해도 동일 증거로 완료한다. 소스 변경 시 이전 증거 재사용을 거부한다.
- **분류:** **정적 분석 후보. 이번 세션에서 발생한 장애로 집계하지 않음.** 후속 장애 주입 검증이 필요하다.

### HR6-F07 · P2 · 완료 후 자원 보존·정리 계약

- **현상·근거:** L1981에서 사용자가 정리 여부를 물었다. L1990에 worktree 두 개가 남아 있다. Herdr workspace 종료와 git worktree 삭제는 서로 다른 작업이며 현재 `accept`는 후자를 하지 않는다.
- **개선:** pane, worktree, 미리보기 프로세스, 재생성 가능한 의존성, 임시 데이터, 사용자 데이터를 자원 목록으로 관리한다. 계획 시작 시 합의된 보존 정책을 재사용한다.
- **수용 기준:** 완료 보고에 남은 자원·이유·정리 상태가 나온다. 통합 여부와 미반영 변경을 확인한다. 사용자 데이터 삭제는 별도 권한을 따르며, 단순 Done으로 삭제를 추론하지 않는다.
- **분류:** 관찰된 사용성·수명주기 공백. worktree 보존 자체는 결함으로 단정하지 않는다.

## 2. 사용자 사용성 개선 백로그

### HR6-U01 · P1 · 실제 실행 경로에 맞는 사전 권한 점검

- **현상·근거:** preflight는 일반 `.../worktrees`를 안내하지만 Herdr는 `.../herdr-worktrees/23/work-24`를 쓴다. `.git/index.lock` EROFS(L553), Vite 설정 옆 임시 파일 EROFS(L1399), Herdr EPERM(L1507·1567), 원격 API 연결 실패는 서로 다른 경계다.
- **개선:** plan/task/실행 방식을 입력받아 실제 경로와 행위를 계산한다. 저장소, Git common directory, 계획 상태, worktree, Herdr 제어 접근, 패키지 캐시, 네트워크 목적지, 필요한 로컬 포트를 한 화면에 보여준다. 오류에 실행 주체·행위·자원·정책 경계를 붙인다.
- **수용 기준:** 안내 경로와 실제 사용 경로가 일치한다. `필요 / 허용 확인 / 미확인 / 거부`를 구분한다. 사전 점검 자체는 호스트 정책을 바꾸지 않는다. 같은 EROFS에 출력 폴더 변경 등을 반복 제안하지 않는다.

### HR6-U02 · P1 · 기존 승인 재사용과 제한된 관리 실행 인터페이스

- **현상·근거:** `permissions.py`에는 grant/delegation이 있지만 Herdr 시작 경로는 이를 직접 조회·소비하지 않는다. 사용자 동의, Handrail 정책, host escalation, worker 승인이 분리돼 있다.
- **개선:** 사용자 지시의 출처, 승인 범위, 계획 revision/cycle, 모델, 경로, 작업 종류, 설치 argv를 실행 시도에 연결한다. 관리 명령은 계획·작업 ID에서 경로를 해결하고 허용된 작업을 검증한다. 호스트가 지원하는 적용 방식과 실제 적용 여부를 별도 기록한다.
- **수용 기준:** 유효한 기존 승인 범위의 재시도·상태 조회·검증에서 Handrail이 새 대화 확인을 요구하지 않는다. 변경된 범위만 설명한다. host 허용을 적용하지 못했는데 적용됐다고 표시하지 않는다. 임의 shell·cwd·목적지를 실행하는 포괄 권한으로 구현하지 않는다.
- **승인 출처 보완:** 포괄 구현 지시, 명세 승인, 부모 위임을 구분해 기록한다. 명세마다 새 답변이나 해시 확인을 강제하는 제안은 채택하지 않는다. 기존 지시가 범위를 충분히 포함하면 그 근거를 재사용한다.

### HR6-U03 · P1 · 부작용 없는 로컬 상태 조회

- **현상·근거:** `collect`는 화면을 읽지만 `_plan`을 통해 원격 상태를 조회하고, 직렬화 잠금과 `_save`로 로컬 상태를 쓴다. 화면 확인도 네트워크·파일 쓰기 권한에 의존한다.
- **개선:** 로컬 snapshot 조회, Herdr 실시간 관찰, 관찰 결과 저장, 원격 동기화를 분리한다. `cached_at/observed_at`을 표시한다.
- **수용 기준:** 로컬 조회는 네트워크와 쓰기 권한이 없어도 작동하고 파일을 바꾸지 않는다. 실시간 관찰은 필요한 Herdr 제어 권한만 요구한다. 오래된 자료를 최신 상태라고 표시하지 않는다.

### HR6-U04 · P1 · 감사 기록 중복 제거와 한눈에 보이는 진행 요약

- **현상·근거:** 부모 댓글 47건에 조율자 설명과 자동 이벤트가 함께 쌓였다. 예를 들어 댓글 113/114, 115/116에는 같은 행동을 설명하는 수동·자동 기록이 겹친다. `_event`는 자동으로 부모 댓글을 생성하고 스킬은 사전 댓글을 요구한다.
- **개선:** 관리 명령이 감사 기록을 책임지고 조율자는 추가 판단만 쓴다. 상세 저널을 먼저 내구성 있게 저장하고 operation ID로 원격 동기화한다. 사용자에게는 단계·블로커·다음 행동 요약을 제공한다.
- **수용 기준:** 정상 행동 하나에 별도 수동·자동 사전 댓글을 둘 다 요구하지 않는다. 동기화 중단 시 감사 이력을 잃지 않는다. 자식 카드에서도 해당 작업의 상태·증거 위치를 찾을 수 있다.

### HR6-U05 · P1 · 필요한 질문을 조기에 묶고 대기 대상을 명시

- **현상·근거:** Grok effort 선택이 상당한 작업 후에 사용자에게 제시됐다. compaction 뒤 legacy run과 Herdr 명령이 섞였다. 이번 분석 조율에서도 이미 허가한 Herdr 의뢰를 다시 확인하려 해 사용자가 “누구의 무슨 응답”인지 물었다. 마지막 사례는 원본 테스트 세션과 분리된 추가 관찰이다.
- **개선:** 미정인 필수 선택만 초기에 질문한다. 이미 지정된 모델·범위는 재질문하지 않는다. 재개 자료에 실행 방식, 모델, 승인 출처, 정확한 경로, 미해결 블로커, 다음 명령을 저장한다. 대기 상태는 `대상 / 필요한 응답 / 이유 / 계속 가능한 일`로 표현한다.
- **수용 기준:** “응답 대기”만 표시하지 않는다. 필요한 선택이 미정인 worker만 시작을 보류하고 독립적인 승인 작업은 진행할 수 있다. 세션 재개 후 올바른 workflow로 이어진다. 기존 사용자 권한을 먼저 확인해 불필요한 동의 질문을 없앤다.

### HR6-U06 · P2 · 설정·바인딩과 준비 상태 안내 개선

- **현상·근거:** 초기 설정 세션에서 긴 설치 경로 복사, 대화형 바인딩 재시도, 토큰의 채팅 입력이 있었다. 로컬 `ready`와 원격 접속 가능 상태가 구분되지 않아 혼동했다.
- **개선:** 안정된 짧은 실행 진입점, 비밀값 전용 입력, 프로필 선택 후 비대화형 재시도, 한글 표시 이름과 내부 slug 분리를 제공한다. bound/remote_reachable/worker_ready/verification_ready를 구분한다.
- **수용 기준:** 사용자가 버전 캐시 절대경로를 조립하지 않는다. 토큰은 대화·승인 문구에 포함되지 않는다. 연결 실패 후 이미 선택한 프로필을 다시 고르지 않아도 된다.

### HR6-U07 · P2 · Review에 실행 확인 방법 포함

- **현상·근거:** Review 제출 후 사용자가 서버 실행을 다시 요청했다(L1892 이후). 검토용 서버가 꺼져 있었고 기본 포트 충돌로 다른 포트를 사용했다.
- **개선:** 검토할 통합 HEAD, 기능 기준별 증거, 검토 URL 또는 서버가 꺼져 있다는 사실, 실행 방법, 미확인 항목, 종료·보존 정책을 한 번에 제시한다.
- **수용 기준:** 사용자가 검토 시작 방법을 다시 묻지 않아도 된다. 미리보기 실행이 승인 범위 안이면 그 권한을 재사용하며, 범위 밖이면 필요한 차이만 확인한다. 임의의 기존 프로세스를 종료하지 않는다.

## 권장 진행 순서와 측정

1. **첫 개선 묶음:** U01 실제 경로 preflight, F05 의존성 준비, U02 승인 재사용. 권한 마찰에 직접 대응한다. 기존 지시 재사용과 대기 대상 표시(U05)는 스킬 수정에 함께 반영한다.
2. **같은 주기의 신뢰성 수정:** F01 완료 경로, F02 복구, F03 현재 상태 정합성. 조율자가 관리 명령을 벗어나는 경우를 줄인다.
3. **다음 묶음:** U03 순수 조회, U04 감사 요약, F04 기능 기준별 증거, F06 중단 복구. 이어서 F07·U06·U07을 적용한다.

측정 항목은 (a) 동일 승인 범위의 불필요한 대화 재확인, (b) host 요청/자동 허용/실제 클릭/거부/대기 시간, (c) raw 명령 복구 횟수, (d) 권한 미준비로 실패한 실행, (e) 완료 후 상태 불일치, (f) 중복 댓글이다. 각각 별도로 기록한다. 이번 자료만으로 승인 클릭 감소율을 계산할 수는 없다.

목표 수용 기준은 유효한 동일 범위에 대한 **Handrail의 추가 동의 질문 0회**, raw 복구 0회, 현재 상태 모순 0건이다. 호스트 승인 횟수는 적용 가능한 지원 방식별로 측정한다. 새로운 자원·범위, 철회·만료, 최종 사용자 완료 판단은 구분해 다룬다.
