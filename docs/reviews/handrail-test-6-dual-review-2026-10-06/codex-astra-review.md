# Codex GPT-6-Astra High 독립 검토 원문

Herdr 터미널의 완료 응답을 보존한 자료다. 화면 줄바꿈을 포함하며, 아래 판단은 검토자 원문이다. 채택·수정 여부는 `report.md`를 따른다.

REVIEW_COMPLETE_ASTRA

검토 결과, 이번 개발은 후속 검증과 사용자 확인을 거쳐 완료됐지만, Handrail의 실행 수명주기와 상태 관리까지 일관되게 마감되지는 않았습니다. 개
선 우선순위는 권한을 넓히는 것보다 완료·복구 경로를 통합하고, 이미 승인된 작업을 정확한 실행 범위 안에서 재사용하도록 만드는 데 있습니다.

아래 ‘행’은 evidence에 보존된 원본 rollout 행 번호입니다. 별도 표시가 없으면 주 세션 01a10e6f를 뜻합니다. 댓글은 부모 카드 #23의 댓글 ID입니
다.

핵심 판단은 다섯 가지입니다.

1. 초기 실패와 최종 성공을 구분해야 합니다. #25는 구문 검사 후, #24는 통합 checkout의 빌드 재검사 후 Done이 됐습니다. 이후 API CRUD·재시작 저
   장성 점검과 사용자의 실행 확인이 있었고, #23도 명시적 지시로 Done이 됐습니다. 전체를 ‘개발 실패’로 평가할 근거는 없습니다.

2. 일반 plan 명령이 Herdr 수명주기를 우회합니다. 실제 최종 처리는 herdr accept가 아닌 plan accept였습니다. 카드 완료는 성공했지만 Herdr
   workspace 종료 기록은 없습니다. 조율자의 명령 선택 실수와 제품의 방어 장치 부족이 함께 드러났습니다.

3. verified가 보장하는 범위가 사용자 완료 기준보다 좁습니다. 승인된 자동 검사는 백엔드 진입점 구문 검사와 프론트엔드 빌드뿐입니다. CRUD·오류
   응답·영속성·브라우저 조작은 이 두 검사로 보장되지 않습니다.

4. 복구 후 상태가 완전히 정합화되지 않습니다. #24는 새 pane에서 성공했지만 저장된 pane ID는 이전 값이며, 완료 상태 옆에 과거 실패 체크와 시작
   오류가 남아 있습니다.

5. 반복 권한 마찰은 여러 경계가 겹친 결과입니다. 주 세션에는 escalation을 포함한 tool call 98건이 있습니다. 이는 사용자 클릭 98회가 아닙니다.
   실제 클릭 수, 자동 허용 수, 승인 대기 시간은 자료로 확정할 수 없습니다.

시간 흐름도 중요합니다. 한국시간 09:23경 Frontend 시작 실패 이후 09:46경 같은 카드·worktree에서 복구됐습니다. Backend는 09:51경 Done, Frontend
는 10:04경 통합 빌드까지 통과해 Done이 됐습니다. API 스모크와 저장성 점검은 그 뒤에 수행됐고, 10:10경 Review 제출, 10:17경 사용자 승인으로 부
모 Done이 이뤄졌습니다. 따라서 Backend의 초기 미검증 상태와 후속 통합 점검 성공을 동시에 기록해야 합니다.

기능 개선 백로그는 다음과 같습니다. P1은 우선 수정 대상, P2는 후속 개선 대상입니다.

4. F4 · P1 — 현재 상태와 실패 이력을 분리하십시오.

   현상·원인: 최종 #24 worker에는 status=complete와 성공한 evidence.checks가 있지만, 최상위 checks에는 이전 vite: command not found가 남아 있

   분류·영향: 관찰된 코드·데이터 정합성 결함입니다. 성공과 실패가 병렬로 노출돼 사용자와 다음 조율자가 상태를 다시 해석해야 합니다.

   태에는 관찰 시각을 붙이십시오.

   수용 기준: 실패 후 성공하면 현재 검사 상태는 성공 하나로 결정돼야 합니다. 과거 실패는 이력으로 조회돼야 하며, 미관찰 상태와 실제 실행 중 상
   태를 구분해야 합니다.

5. F5 · P1 — 완료 처리 재시도가 동일한 증거를 사용하게 하십시오.

   정적 분석상 결함 후보: finish()는 호출 때마다 검사를 수행하고 checked_at과 출력을 포함한 새 evidence를 만듭니다. 반면 complete_herdr_work()
   (handrail/kanban.py:633)는 pending 또는 완료 evidence와의 동일성을 요구합니다. 원격 Done 처리 후 응답·로컬 저장이 끊기면, 다음 호출이 새 증
   거를 만들어 KANBAN_OPERATION_CONFLICT 또는 KANBAN_DONE_IMMUTABLE로 막힐 수 있습니다.

   분류·영향: 이번 세션에서 해당 장애가 발생했다는 증거는 없습니다. 코드 경로에서 확인한 복구 위험입니다. 현재 lifecycle 테스트는 완료 함수를
   mock하므로 이 경계를 충분히 검증하지 못합니다.

   제안: 검사 결과와 operation ID를 먼저 불변 기록으로 저장하고, 재시도는 원격 반영·로컬 확정부터 재개하십시오. 재검사는 별도 시도로 시작해야
   합니다. worker_completion 댓글도 완료 의도와 실제 완료 결과를 구분해야 합니다.

   수용 기준: 검사 후, 원격 이동 후, Kanban 저장 후, Herdr 저장 전의 각 중단 지점에서 재개해도 동일 증거로 완료돼야 합니다. 중복 검사·댓글·상
   태 이동 없이 복구되고, 소스가 바뀌면 기존 증거 재사용을 거부해야 합니다.
