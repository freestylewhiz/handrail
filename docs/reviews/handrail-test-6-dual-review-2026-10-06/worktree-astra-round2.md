# Codex Astra High · Worktree 배치 교차 토의 최종 의견

+WORKTREE_ROUND2_FINAL_ASTRA

합의 가능한 정책은 “무설정 기본은 A 유지, 신규 환경의 권장 구조는 C, 선택과 중단 규칙은 E”입니다. 제 1차의 “C 기본” 표현은 승인된 영속 개발 루
트가 마련된 신규 환경의 권장값으로 한정하겠습니다. 모든 설치에서 설정 없이 C를 선택한다는 의미라면 철회합니다.

이는 Grok의 호환성 우려를 받아들이면서, 실제 프로젝트의 빌드·검색·배포 문맥 밖에 작업 소스를 두자는 제 판단을 유지하는 안입니다. 상대의 2차 응
답은 아직 보지 않았으므로 양측 최종 합의로 단정하지는 않습니다.

상대가 제기한 세 질문에는 다음과 같이 답합니다.

1. B가 줄이는 권한은 무엇인가?

   우선 worktree 내부의 소스·의존성·빌드 임시 파일 쓰기입니다. 조율자의 기존 host 정책이 그 하위 경로를 실제로 허용할 때 이득이 있습니
   다. .handrail 등에 별도 제한이 있다면 그 이득도 확인해야 합니다.

   Git common directory 쓰기까지 해결되지는 않습니다. test_6의 행 553은 .git/index.lock 쓰기 실패이고, 행 1399는 worktree의 Vite 임시 파일 쓰
   기 실패입니다. 서로 다른 능력입니다. 관리자 상태, Herdr 제어 접근, 설치 네트워크도 남습니다. 이 점에서는 Grok과 동의합니다.

   다만 기존에 승인된 프로젝트 쓰기 범위를 활용하는 것 자체를 우회나 숨김이라고 부르는 데는 반대합니다. 위치와 영향이 공개되고 승인 범위에 부
   합하면 정상적인 권한 재사용입니다. 문제는 위치를 조용히 바꾸거나 작업 범위를 넓히는 경우입니다.

2. checkout 분리는 불변인가? 어느 계층이 worker 경계를 집행하는가?

   불변으로 둘 것은 별도 작업 소스, 실행별 정체성, 승인된 worker 쓰기 범위, 검수 후 통합입니다. 물리적으로 checkout 밖이라는 조건은 강한 기본
   선호이며, 모든 예외를 금지하는 불변은 아닙니다. B도 Git linked worktree로서 논리적 독립성을 유지할 수 있습니다.

   따라서 “B이면 제품 규칙이 반드시 깨진다”는 주장은 과도합니다. Worker가 canonical 소스를 직접 수정하도록 허용하거나, 검수 전 후보가 통합 검
   증·배포에 섞이거나, 관리자 권한 기록을 worker 통제 아래 두는 경우에 구체적인 위반이 됩니다.

   집행은 provider adapter가 요청한 범위와 실제 provider·host 정책이 담당합니다. host_preview는 설명 도구입니다. 현재 adapter도
   host_ready=False를 반환하며, Herdr 시작은 별도 경로를 사용하므로 공통 권한 계약과 연결하는 구현이 필요합니다.

3. C의 루트를 저장소 부모에서 추론해도 되는가?

   부모 경로는 후보로 제안할 수 있지만, 승인된 개발 루트로 자동 채택해서는 안 됩니다. 사용자에게 이미 등록된 정확한 루트가 있으면 재사용하고,
   없으면 구체적인 경로를 제시해 초기 설정에서 결정해야 합니다.

   “저장소 부모 전체”를 쓰기 범위로 추가할 필요는 없습니다. 예컨대 <개발루트>/.handrail-worktrees/<workspace-id>만 manager의 저장 범위로 지정
   하고, worker에는 그 안의 자신의 실행 디렉터리만 부여합니다. 다른 저장소 내부를 후보로 삼아 간섭을 옮기는 것도 피해야 합니다.

1차 주장 중 확정 수준을 조정할 부분도 있습니다.

• 제 B 관련 주장은 위험 시나리오입니다. test_6에서 Docker 이미지 오염이나 상위 의존성 사용이 실제 발생했다는 증거는 없습니다. 소스 메모가 설명
  한 가능한 경로이며, 도구 설정·설치 상태·읽기 권한에 따라 달라집니다. C에도 상위 workspace 설정의 영향은 남습니다.

• git clean -fdx가 nested worktree를 일반적으로 삭제한다는 상대 주장은 채택하지 않습니다. 이번 조사에서 재현하지 않았고 중첩 Git 저장소 취급
  조건을 생략했습니다. IDE 검색이 작업 트리를 삭제한다는 표현도 근거가 없습니다. 검색·감시 비용과 삭제 위험을 구분해야 합니다.

• capture_seed()가 절대경로의 .handrail 때문에 충돌한다는 주장은 소스상 정정해야 합니다. capture_seed() (handrail/run_preparation.py:140)는
  worktree를 기준으로 얻은 변경 파일의 상대경로를 검사합니다. 외부 경로가 repo/.handrail/worktrees/…라고 해서 내부 frontend/app.js
  가 .handrail/…로 판정되지는 않습니다. 실제 변경점은 고정 XDG 경로를 요구하는 owned_worktree()입니다.

• A의 보존성도 독립 백업을 뜻하지 않습니다. 소스 파일이 checkout 밖에 남아도 Git common directory를 잃으면 정상적인 Git 작업·복구가 보장되지
  않습니다. 또한 디렉터리 모드 0700만으로 같은 계정의 worker나 외부 sandbox 경계를 집행할 수 없습니다.

제가 수용하는 최종 정책은 다음 순서입니다.

1. 기존 실행 경로를 고정합니다. 실행 중·중단 상태·Review 중인 작업은 저장된 경로와 Git 정체성으로 복구합니다. 새 기본값을 소급 적용하지 않습니
   다. 이동은 별도의 정합성 검증과 승인 범위 확인이 필요한 작업입니다.

2. 신규 실행은 명시적 설정을 우선합니다. 등록된 루트, workspace ID, workflow·실행 시도 ID, Git common directory를 검증합니다. 기본값을 바꿔도
   기존 실행 기록은 바뀌지 않습니다.

3. 설정이 없으면 A를 유지합니다. 승인된 C 설정이 이미 존재하면 C를 사용합니다. 신규 환경 안내에서는 C를 우선 권장하지만, 개발 루트가 확정되지
   않았다는 이유로 부모 경로를 자동 선택하지 않습니다.

4. B는 명시적 예외, D는 임시 산출물용입니다. B에는 Git 제외뿐 아니라 해당 프로젝트의 watcher·패키징·배포 설정 검토가 필요합니다. 일반적인
   resume·Review 대상 worktree를 /tmp로 옮기지 않습니다.

5. private state는 소스 배치와 분리합니다. 절대경로·권한 근거·소유 기록은 private registry에 저장합니다. .handrail/project.json은 저장소가 제
   안한 위치를 권한으로 승격하는 통로가 되어서는 안 됩니다.

설정 없는 project-only sandbox에서 A와 C가 모두 막히면, 첫 실행 전에 한 번의 환경 준비 단계로 전환해야 합니다. 매 계획마다 다른 위치를 시험하
거나 같은 권한 질문을 반복하는 방식에는 반대합니다.

구체적인 흐름은 다음과 같습니다.

• 조율자는 선택할 영속 worktree 루트와 Git common directory, 관리자 상태, Herdr 제어 접근을 구분한 요구 목록을 만듭니다. 설치·네트워크는 필요
  한 경우 별도 항목으로 넣습니다.

• 기존 사용자 지시와 저장된 승인이 덮는 범위를 먼저 확인합니다. 충분한 항목은 다시 묻지 않고, 새 능력만 구체적으로 제시합니다.

• 사용자 선택과 제품 승인 기록을 남긴 뒤 host에 적용합니다. 동의 기록과 적용 완료는 별도 상태입니다. 적용이 차단되면 requires_setup으로 남기고
  host 설정 단계로 인계합니다.

• 실제 실행 주체의 정책 정보와 승인된 작업 결과로 적용 범위를 확인합니다. 파일 모드나 os.access만으로 준비 완료를 선언하지 않습니다. 이번 토의
  에서는 그러한 확인 실험을 수행하지 않았습니다.

• 이후 동일 경로·능력의 승인은 재사용합니다. 새 계획의 작업 위임이나 새 review cycle에 필요한 판단이 있더라도, 변경 없는 저장 위치 승인까지 반
  복하지 않습니다.

넓은 python …handrail.py 또는 raw Herdr 명령 prefix 허용은 이 설계의 대안이 아닙니다. 관리 명령이 작업 ID에서 정확한 경로를 해결하고, 허용된
작업 종류와 자원 범위를 검증해야 합니다.

구현 우선순위는 세 가지입니다.

1. 공통 배치·소유권 계약: herdr_workflow._worktree, run_workflow, owned_worktree를 하나의 resolver와 불변 기록에 연결합니다. 기존 경로 호환과
   symlink·Git identity 검증을 포함합니다.

2. 실제 실행 경로 기반 권한 준비: cli preflight (handrail/cli.py:304)의 legacy 고정 경로를 없애고 manager·worker·host의 필요 능력, 승인 출처,
   적용 상태를 분리합니다.

3. 복구·migration·정리 계약: 경로 소실과 정책 변경을 구분하고, Review 보존·미반영 변경·활성 프로세스를 확인한 뒤 이동·삭제하도록 합니다. 프로
   젝트 도구 간섭도 수용 검사에 포함합니다.

남는 차이는 C를 얼마나 적극적으로 권장할지입니다. 저는 신규 개발 환경에서는 C를 우선 안내하되, 그것이 실제 추가 설정 부담을 만드는 project-
only 환경에서는 A의 좁은 경로 승인과 B 예외를 함께 비교해야 한다고 봅니다. 모든 환경에 C를 강제하거나 B를 일괄 기본값으로 삼는 정책에는 동의하
지 않습니다.
