### 근거 등급

1. **실제 결정:** diagnostic DB의 `ExecApproval`을 exec ID로 rollout의 CommandExecution과 연결한다. Approved, 규칙 추가 승인, Abort를 구분한다. Abort 한 건은 대응 완료 실행이 없어 명령을 추측하지 않았다.
2. **Handrail 동의:** assistant의 실제 authorize 요청과 뒤따른 user 답변을 연결한다. 사용자 인용 로그나 시스템 지침의 문자열을 동의 횟수로 세지 않는다.
3. **상승 요청:** response_item의 실제 도구 호출에서 중첩 exec_command 인자에 require_escalated가 지정된 호출식을 추출한다. reasoning과 복제된 item_completed를 이중 집계하지 않는다. 한 코드 호출식이 반복문에서 여러 번 실행되는 경우에는 한 식으로 기록한다.
4. **현재 규칙:** default.rules를 실행하지 않고 선언만 읽어 대상 실행 명령과 매칭되는 prefix를 추린다. 과거 적용 시점과 실제 규칙 선택을 증명하지는 않는다.
5. **사용자 제공 콘솔:** 실제 “You approved …” 표시가 있는 근거를 이전 [피드백 기록](../../handrail-dev-spec/v0/FEEDBACK_RC4_EXECUTION.md)과 연결한다. 로컬 결정 기록과 중복일 수 있으므로 단순 합산하지 않는다.

동적 템플릿이나 변수형 cmd는 CSV에 표시했다. 문자열 검색만으로 permission_denied 등을 찾은 signals는 코드·보고서 인용에서도 나올 수 있어 실제 차단 횟수로 집계하지 않았다. 일반 대화의 승인 관련 문장도 후보 목록으로 보존하되 승인 클릭으로 세지 않았다.

### 보존 범위의 한계

- RC3 진단 로그는 **10:19:59 이후**, RC4는 **15:49:03 이후**만 남아 있었다. 각각 1,000개 행이며 이보다 앞선 결정은 이 자료로 복원할 수 없다.
- rollout은 해당 세션의 처음부터 남아 있지만 승인 클릭 자체를 모두 기록하는 형식은 아니다.
- Codex worker의 ephemeral 실행과 Cursor 내부 대화·설치 상세는 이 저장 세션 집합에 없을 수 있다. 해당 이력까지 확인했다고 주장하지 않는다.
- 이 보고서는 살아 있는 로그를 시점별로 읽은 스냅샷이다. manifest의 파일 크기·해시·마지막 시각으로 범위를 고정했다. 원본 로그나 자격증명은 문서에 복사하지 않았다.

### 의존성 설치 피드백의 처리

사용자는 설치 승인도 반복되었다고 보고했다. 조율자 기록에서는 의존성 복사·복원 호출식 8개와 그 중 일부에 대한 실제 규칙 추가 승인을 확인했다. 수집한 직접 명령 요약에서는 npm install/ci 등 신규 다운로드 설치를 특정하지 못했다. worker 내부나 복구 스크립트 내부의 동작은 이 수치에 모두 드러나지 않는다.

따라서 이를 ‘설치 승인 없음’으로 해석하지 않는다. 정책은 다운로드, 캐시, 설치 경로, lifecycle script, 네이티브 빌드, 브라우저 설치까지 다루되 관측된 복원 사례와 아직 상세 미확인인 설치 사례를 구분한다.

## 6. 반복되는 원인

### A. Handrail의 one-run 동의가 계획 위임보다 좁다

이미 계획을 맡겼어도 새 카드와 복구용 새 run마다 동의를 요구한다. H004에서는 20분 35초의 답변 간격이 발생했다. H007은 다음 작업에서 같은 관문이 다시 나타난 사례다.

후보: 승인된 프로젝트 실행 정책과 계획 회차에서 run 권한을 파생한다. 새로운 파일 경로·목적지·동작 권한이 필요할 때만 차이를 확인한다. 명세·입력 고정과 사용자 최종 Review는 유지한다.

사용자 추가 요구: 여러 계획 카드를 함께 개발 의뢰하면 선택된 계획·회차 전체를 하나의 위임 묶음으로 처리한다. 부모 계획 전환이나 그 하위 작업의 시작 자체를 이유로 다시 승인받지 않는다. 이 사례의 계획 #4–#6 및 하위 #7–#12처럼 이미 함께 위임된 작업에서 적용할 요구다. 카드별 Review·완료 기록은 유지하고, 위임에 없던 계획 추가·새 권한·한도 확대만 별도로 판단한다.

### B. ‘항상 허용’에 run의 절대 경로가 포함되어 있다

D014와 D017의 승인된 prefix는 같은 `rtk node /tmp/handrail-review-quiz.cjs` 뒤에 **서로 다른 worktree 경로**를 포함한다. 현재 default.rules에도 두 규칙이 각각 남아 있다. D011과 앞선 task8 브라우저 규칙도 worktree별로 나뉜다.

앞선 prefix가 새 경로를 포함한 명령을 덮지 못한다는 점은 규칙 내용으로 확인된다. D019에서는 검증 스크립트명도 달라졌다. 같은 개발 검증 범주가 CLI의 문자열 규칙에서 서로 다른 요청이 되고 있다.

후보: 프로젝트 소유 worktree와 검증 실행 권한을 인식하는 관리 인터페이스·sandbox 설정을 제공한다. 고정 launcher 이름 하나를 무제한 허용하는 것으로 대체하지 않고 내부 정책 검사와 실제 플랫폼 경계를 함께 둔다.

### C. 조율자의 실행 환경이 준비되지 않았다

기록된 조율자 permission profile은 소스와 tmp 쓰기를 허용하지만 `.git`, `.agents`, `.codex`는 읽기 범위이고 네트워크는 restricted다. Handrail의 홈 아래 run/worktree 저장 경로도 표시된 write 항목에 없다.

이는 Git 쓰기, Vikunja 접근, 홈 아래 worktree 복원에서 조율자 상승 요청이 생기는 구조를 설명한다. 각 명령 실패의 유일한 원인으로 모두 검증한 것은 아니다. `workspace-auto`는 worker 실행 옵션이며 조율자 환경 준비를 대신하지 않는다.

후보: 시작 전 조율자·관리 프로세스·worker·검증 주체별 준비 상태를 검사하고 필요한 권한을 한 번에 안내한다.

### D. 임시 복구·검증 스크립트가 승인 대상을 계속 늘린다

카드별 seed, retry, browser, review, recovery 파일이 각각 다른 prefix로 저장된다. 의존성 준비도 새 worktree마다 임시 스크립트로 수행한다.

후보: 의존성 준비·초안 복구·검증 실행을 제품 기능으로 제공하고, 코드·환경·검증 근거를 기록한다. 실제 새로운 권한 요구와 새 파일명·run ID만 달라진 경우를 구분한다.

### E. 제품 내부 오류가 새 승인까지 유발한다

결과 계약 실패와 CONTEXT.md 충돌로 기존 작업이 새 run으로 복구되면서 승인 요청이 늘어난다. 권한 정책과 함께 패킷 회차 관리·제출 전 검사·제한적 보고서 복구가 필요하다.

### F. 현재 규칙은 좁은 예외와 넓은 예외가 혼재한다

해당 실행과 매칭되는 사용자 전역 rules에는 특정 PID·worktree·스크립트를 고정한 규칙과 `rtk ps`, `rtk env` 같은 넓은 prefix가 함께 존재한다. 생성 시점을 알 수 없으므로 이 프로젝트가 모든 규칙을 만들었다고 판단하지 않는다.

후보: 예외를 무작정 추가하기보다 프로젝트·주체·자원·행위로 기록하고 provider가 이를 구현할 수 있는지 확인한다. 기존 전역 규칙을 자동 삭제·변경하지 않는다. 현재 상태를 프로젝트별 승인 원장으로 가져오는 작업도 별도 설계가 필요하다.
